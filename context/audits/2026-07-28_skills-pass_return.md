## 4b. INSTRUMENT FINDING — "lock-free porcelain" has a MECHANISM on the device bridge, and I tripped it

**What happened.** I ran the opening and closing censuses as plain `git status --porcelain` through the device-bridge mount. On that mount git creates `.git/index.lock` to refresh the index and then **cannot unlink it** — `warning: unable to unlink '…/.git/index.lock': Operation not permitted`. The status output is correct, but **a zero-byte `index.lock` is left behind in the working repo**, and the next `git add` Nick runs would have failed with `fatal: Unable to create '.git/index.lock': File exists`. Both repos were affected.

**Caught and cleared before handing over.** The bridge cannot `rm` (`Operation not permitted`), but it CAN rename: both locks were moved to `.git/index.lock.stale-remove-me` (0 bytes, inert — git ignores unrecognized files under `.git/`). Verified afterwards: `ls .git/index.lock` → absent in both repos; the censuses below were then **re-run and re-confirmed with the lock-free form**, which leaves no lock at all.

**The mechanism, and the rule it mints.** The brief's standing law is *"lock-free porcelain only"* — that law has a concrete command form, and this lane learned it the expensive way:

```
git -C <repo> --no-optional-locks status --porcelain     # correct: takes NO index lock
git status --porcelain                                    # WRONG on the bridge: strands .git/index.lock
```

This is the §arc-disciplines rule 2 shape exactly — *"X stays out of the gate" needs a MECHANISM, not an intention* — applied to the lane's own instrument: "lock-free porcelain" was an intention until it named `--no-optional-locks`. **REC for the hub (env-model, the remote-Cowork bridge section, and every future lane brief that says "lock-free porcelain"): spell the flag.** A remote lane that omits it silently arms a commit failure in Nick's next command, and the failure surfaces on *his* keyboard, not the lane's.
