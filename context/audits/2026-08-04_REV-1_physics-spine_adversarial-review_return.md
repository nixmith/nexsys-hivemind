## §2 Findings (ranked)

### F-1 · HIGH · Value-match confirmation accepts non-causal reports: a periodic same-value report can CONFIRM a command that never executed (S-2 realized)

**FACT (source-certain).** The confirmation calculus is pure value-matching with no causality, freshness, or edge requirement:

- `StandardPendingCommandLedger.onStateReported` (`core/automation/.../StandardPendingCommandLedger.java:427–452`) evaluates every in-flight command on the subject entity whose `targetAttribute` matches the reported key and emits `state_confirmed` on `ConfirmationResult.CONFIRMED` — from ANY LIVE `state_reported`, whatever produced it.
- The on/off expectation is exact value equality: `StandardCapabilities.onOff()` declares `turn_on → ExactMatch(BooleanValue(true))` (`core/device-model/.../StandardCapabilities.java:143–150`), and `ExactMatch.evaluate` returns CONFIRMED on equality alone (`core/device-model/.../ExactMatch.java:24–28`).
- Periodic same-value reports DO reach the ledger: the ingestion dedup suppresses only sub-10 s twins on the same/successor TSN (`integration-zigbee/.../ReportDeduplicator.java:42, 81–88`), and its own javadoc pins the design intent — "a periodic reporter emitting an unchanged value on consecutive TSNs minutes apart is a genuine report, not a twin" (`ReportDeduplicator.java:26–28`). The R-9 field evidence corroborates: stateVersion advanced +9/45 min with `on` unchanged — same-value `state_reported` events flow in production.

**The trigger (input/state sequence for a false-positive CONFIRMED):** relay ON → an automation issues `turn_on` (toward the CURRENT state; nothing in the pipeline gates a no-op command) → the command is lost at delivery (the night-4 H-2b class, now field-PROVEN to occur) → within the confirmation window the device's periodic same-value report (`on=true`) arrives → `ExactMatch` matches → the ledger publishes `state_confirmed` (match_type "exact") citing that report as evidence. The record now claims CONFIRMED for a command that was never delivered.

**Pricing (honest, using the banked cadence).** Exposure is confined to commands toward the current state (an opposite-state periodic report cannot match). At the S31's measured ~4–5-min day cadence (R-9): per exposed command, P(coincidental confirm) ≈ window/cadence ≈ **5.19 s / ~300 s ≈ 1.7 %** on the capability's 5 s timeout (`StandardCapabilities.java:146`), rising to **≈ 10 %** at the 30 s pipeline default (`PendingCommandLedgerAssembly.java:50`) for any command whose capability carries no timeout. The blockR settle-caveat arithmetic is the same mechanism from the other side (143 ms case ≈ 0.05 %).

**Brand-claim adjudication (the highest evidence bar, both readings stated):**
- *State-truth reading:* **REFUTED as a violation** — the device genuinely IS in the commanded state and the confirm cites a real device report; no false state claim is made.
- *Execution-evidence reading:* **CONFIRMED as a violation** — `state_confirmed` is consumed downstream (M7.5a derivation, the dashboard's green CONFIRMED) as evidence the command *worked*; here it can mark a never-delivered command CONFIRMED, and in exactly the scenario where honesty matters most (silent delivery failure masked by a no-op coincidence). The S31 profile's own note shows the design assumed the discrete no-change case reads honest-timeout ("no-change commands produce no report (honest-timeout class...)" — `zigbee-profiles.json`, sonoff_s31_lite_zb notes); a minutes-scale periodic reporter defeats that assumption.

**Suggested disposition:** pre-freeze RULING on which reading the brand claim binds (the wire/docs should say which); the mechanical fix space is post-gate and overlaps S-1 — delivery evidence (S-1's seam) or an edge/freshness qualifier on value-match confirms (e.g. require a report newer than dispatch that constitutes a *transition* for toward-state commands, or annotate `state_confirmed` with a same-value/no-edge marker so the read side can render it distinctly). No retune of anything is implied. — *Confidence: high on mechanism (source-certain); medium on real-world frequency (depends on how often automations issue toward-current-state commands).*

### F-2 · MED · REPLAY does not re-derive supersession: a crash between the newer issuance and the superseded-disposition publish resurrects the superseded expectation on rebuild (format #15's class)

**FACT.** LIVE supersession mutates the index under the lock and publishes the `command_result(superseded)` disposition only after release (`StandardPendingCommandLedger.java:362–381` — `expireSuperseded` at :365–366, publications flushed at :380; LTD-11 publish-outside-lock). The REPLAY rebuild (`accumulateReplay`, :503–546) does NOT apply supersession on a replayed `command_issued` — it relies entirely on finding the recorded `superseded` disposition in the log (concluded via its causation = the expired command's own id, :519–534).

**The trigger:** command A (turn_on, entity E, attribute `on`) in-flight → command B issued on the same (E, `on`) → the ledger removes A and queues the `superseded` publication → **crash before the flush** (the window between lock release and durable publish; also covered by checkpoint-not-yet-advanced redelivery) → restart REPLAY: both A and B rebuild as in-flight (no supersession re-derivation) → at `onCaughtUp`, if A's deadline is still future, F-10 re-indexes A live (`classifyRestart`/`reindexLive`, :561–618) → a single matching `state_reported` now confirms **both** A and B (the :434 loop evaluates every matching in-flight entry) — a `state_confirmed` for a command the LIVE ledger had already superseded. If A's deadline passed, A instead renders `expired_on_restart`/timeout — a wrong-but-honest disposition for a superseded command.

This is precisely the multi-event crash-window class the brief names (scope C, format #15) surfacing inside scope A, and it is the narrow second hole in never-false-CONFIRMED's causal reading: the confirmed state matches, but the intent it confirms had been superseded. Window is milliseconds and requires a crash — LOW likelihood, MED because it touches the same brand surface as F-1. **Suggested disposition:** post-gate; either re-derive supersession during REPLAY (make the rebuild rule the same rule as LIVE — the pure-projection property argues for this), or accept + document the window as the log's honest prefix contract. The existing supersession tests (per the M9.4a banner) exercise the recorded-disposition path, not this window — worth one test either way. — *Confidence: high (path fully traced at source; not executed).*

### F-3 · MED · The zigbee sidecar (`zigbee-devices.json`) is written in place, non-atomically — a torn write silently discards the availability seed, evidence recency, learned zone types, and the interview cache

**FACT.** `ZigbeeDeviceCache.write` persists via `Files.writeString(file, json)` — truncate-and-write in place, no temp-then-move, no fsync (`integration-zigbee/.../ZigbeeDeviceCache.java:470–472`); it runs on the cycle thread (debounced ≤1/30 s, :62) and at shutdown (`flush()`, :390–401). A crash or power cut mid-write (this is a Pi on an SD card, with a nightly three-boot choreography multiplying shutdown flushes) leaves a partial file; the loader treats any parse failure as "corrupt cache is discarded" (`:648–649`).

**The trigger:** power loss during a debounced flush → next boot loads an empty cache → `availability_seeded: devices=0 ... unknown=N` — the WU-AVAIL-SEED mechanism (the very commit under review, 60d3ab5, which made this file load-bearing as the F2 producer) is silently defeated for that boot: every device re-enters tracking UNKNOWN, battery devices' silence clocks orphan (the F-14 class returns for one cycle), network-address hints and learned zone types are gone (all self-heal on traffic — degradation, not corruption). **The contrast that makes this a finding rather than a NOTE:** the adjacent `PersistentNetworkParameterStore` in the same module writes temp-then-move (`PersistentNetworkParameterStore.java:134–136`) and documents why (:32) — the discipline exists in-module and simply wasn't applied to the sidecar back when it was a pure warm-start optimization. WU-AVAIL-SEED promoted the file to availability truth without promoting its durability. **Suggested disposition:** small pre- or post-freeze mechanical fix (same temp-then-move idiom); no design question. — *Confidence: high.*

### F-4 · MED · The shutdown/watchdog race (S-4): the production loop is interrupt-invisible, and the reopen path carries no shutdown guard — the observed mid-death reopen is real, bounded, and fixable with one guard

Adjudicated in full under §3 S-4; summarized here for ranking. **FACTs:** (1) supervisor stop interrupts the run thread BEFORE `adapter.close()` (`StandardIntegrationSupervisor.stopRuntime`, :756–781; grace 10 s, :103); (2) the production loop's healthy branch contains no interruption point — the serial read is semi-blocking native (`JSerialCommByteChannel.java:16–20, 65–69`), locks are `ReentrantLock`, no sleeps — so the interrupt cannot stop it and every graceful stop burns toward the grace bound; (3) `attemptReopen()` (`ZigbeeIntegrationAdapter.java:818–851`) and the unhealthy-branch `watchdog.tick()` (:799–803) check `stopSignal` nowhere, and `markUnhealthy` arms an IMMEDIATE first attempt (`PortWatchdog.java:140–148`); (4) `adapter.close()` (:420–429) runs on a different thread than an in-flight `attemptReopen`, interleaving unsynchronized `transport.close()`/`transport.open()` on a documented not-thread-safe transport (`EzspAshTransport` javadoc) — worst identified outcome: a fresh channel opened after close is never closed (FD held to process death) and the NCP is left mid-handshake. **Next-boot state is protected by construction:** the ASH open path resets via RST/RSTACK, and the reopen path never writes the parameter store. **Suggested disposition:** post-gate hardening pair — a stop-guard at the top of `attemptReopen()`/before `tick()`, and/or reorder `stopRuntime` to close-before-interrupt (close()'s `countDown` is the loop's real stop signal). — *Confidence: high on the mechanics; medium on the exact in-window trigger of the observed night (see §3 S-4 residual).*

### F-5 · MED · `WriteCoordinator.submit` on an interrupted caller reports failure while the queued write still executes — an ambiguous outcome surfaced as a definite one

**FACT.** `PlatformThreadWriteCoordinator.submit` enqueues the work item, then parks on `future.get()`; on interrupt it throws `RuntimeException("Interrupted while waiting...")` — but the item **stays in the queue and executes** on `hs-write-0` regardless (`core/persistence/.../PlatformThreadWriteCoordinator.java:80–98`, :142–166 — nothing dequeues it). Every event publish rides this exact path (`SqliteEventStore.appendOnWriteThread` → `submit(EVENT_PUBLISH, ...)`, `SqliteEventStore.java:376`).

**The trigger:** `doTeardown` interrupts in-flight Run VTs precisely so they "finalize ABORTED rather than publishing into a tearing-down persistence layer" (`HomeSynapseCore.java:1187–1193`). A Run VT parked in `submit` on an event append at that moment sees a publish *failure* and finalizes accordingly — while the event **durably commits** moments later. Result: a log/record divergence born exactly in the window the teardown comment believes it is preventing (e.g. a `command_issued` that "failed to publish" per the run's own bookkeeping, yet exists in the log — and will be tracked, dispatched-on-replay-classified, and explained as a real command). Secondary exposure: any caller that treats the throw as "not written" and retries would double-write. **Suggested disposition:** post-gate; either drain-cancel the caller's item on interrupt, or document submit's contract as "interrupt = outcome unknown (likely committed)" and audit the few interrupt-adjacent callers. — *Confidence: high on mechanics; medium on observable impact (the divergence is real but narrow and shutdown-scoped).*

### F-6 · LOW · LIVE redelivery of `command_issued` self-supersedes: the retried delivery expires its own first tracking, publishes a `superseded` disposition naming *itself*, and silently restarts the window

**FACT.** `onCommandIssued` runs `expireSuperseded(target, attr, event.eventId(), ...)` before re-indexing (`StandardPendingCommandLedger.java:362–376`). On an at-least-once LIVE redelivery of the SAME `command_issued` (bus retry after a transient handler failure), the entry indexed by the first delivery — same event id, same attribute — is removed and a `command_result(superseded ... superseding command event <its own id>)` is recorded, then the command re-indexes with a **fresh deadline** (`clock.instant().plusMillis(timeout)`, :371). Effects: a nonsense self-superseded record in the log/explanations, and a quietly extended window. The disposition guard (:389–398) correctly prevents terminal-match damage from the loop-back. Narrow (requires a LIVE retry, which requires a throwing handler), no false verdict — LOW. **Disposition:** post-gate; make `expireSuperseded` skip entries whose commandEventId equals the incoming event id (one line), or accept + note. — *Confidence: high.*

### F-7 · LOW · `findReplayKey`'s no-causation fallback has neither the N-6 deterministic ordering nor the SD-4 disposition guard — a latent REPLAY/LIVE inequivalence, currently masked

**FACT.** LIVE `findPending` got the N-6 oldest-deadline determinism (M9.4a; `StandardPendingCommandLedger.java:665–702`), and LIVE `onCommandResult` got the SD-4 disposition guard (:389–398). The REPLAY twin got neither: `findReplayKey` (:704–719) falls back to insertion-order first-match, and `accumulateReplay`'s result branch (:519–534) concludes an entry on ANY non-acknowledged outcome, dispositions included. Masked today because every result producer chains causation (dispatch service, zigbee handler `publishResult` — `ZigbeeCommandHandler.java:336–350`; ledger dispositions use the expired command's own id by convention) and because disposition outcomes name commands that are structurally never tracked. This does not contradict the banked N-6/SD-4 criteria — it sits beside them: the LIVE half was fixed, the REPLAY half wasn't swept. **Disposition:** post-gate hardening + one rebuild-equivalence test; a NOTE-turned-LOW only because REPLAY-vs-LIVE equivalence is an explicit scope-A property. — *Confidence: high.*

### F-8 · LOW · One EZSP command timeout in cycle work bypasses the 3-miss keepalive tolerance and triggers an immediate reopen cycle

**FACT.** The keepalive path tolerates misses (counted internally, `EzspCoordinatorProtocol.maybeSendKeepalive`, :713–735; `KEEPALIVE_MISS_LIMIT = 3`, `ZigbeeIntegrationAdapter.java:153`), but any `EzspCommandTimeoutException` escaping cycle work (e.g. the availability ping's exchange when the NCP itself stalls — documented propagation, `ZigbeeIntegrationAdapter.java:546–549`) is caught at `productionLoop:795–798` and calls `watchdog.onAshLivenessLost()` directly — one timeout ⇒ unhealthy ⇒ immediate reopen attempt (`PortWatchdog.java:140–148`). Defensible (an NCP silent for a full command timeout is strong evidence), but it is a single-sample trigger for a disruptive multi-second recovery, and a plausible contributor to shutdown-window reopens (§3 S-4). **Disposition:** post-gate consideration — either route it through the miss counter or record the asymmetry as intended. — *Confidence: high on mechanics; the "intended vs. accident" question is Nick's.*

### S-4 — THE SHUTDOWN/WATCHDOG RACE: **PARTIAL** — real race, traced and bounded; one residual unknown

- **FACT — the noise is structural, not incidental:** the graceful stop cannot stop the production loop by interrupt (no interruption point in the healthy branch — enumerated: semi-blocking native serial reads that "do not respond cleanly to Thread.interrupt()" per the channel's own javadoc `JSerialCommByteChannel.java:16–20`; `ReentrantLock`; no sleeps/awaits). So `stopRuntime`'s interrupt (:773–775) is expected to be survived (the supervisor even has a WARN for it, :832–834), and the eventual `adapter.close()` (`ZigbeeIntegrationAdapter.java:420–429`) closes the port UNDER the in-flight read (`closePort()` from another thread unblocks it, javadoc :19–20) → `AshSession.pumpFrame` throws on n<0 (:411–416) → the `zigbee.transport_failed` WARN at every shutdown. **Answer to the brief's either/or: the WARN itself is benign by construction.**
- **FACT — a reopen strictly after `close()` is unreachable:** `close()` counts down `stopSignal` before touching the transport (:422–427), and `productionLoop` re-checks the latch before the unhealthy branch that calls `tick()` (:779, :799–803). The observed reopen therefore fired **inside the interrupt-to-close grace window** (up to 10 s, `DEFAULT_CLOSE_GRACE`, `StandardIntegrationSupervisor.java:103`) — a window in which the loop is fully alive, an unhealth signal arms an immediate reopen (`PortWatchdog.java:140–148`), and `attemptReopen` has no stop guard (:818–851): it will close/reopen/renegotiate/`resumeStored()` mid-death.
- **INFERENCE (medium confidence) — the residual:** the in-window unhealth trigger on the observed nights is not derivable from source alone; the candidates consistent with all constraints are a cycle-command `EzspCommandTimeoutException` under teardown-time load (the F-8 single-sample path) or a genuine port-death signal in the window. Closing this needs one log read (which token preceded the reopen: `zigbee.cycle_command_timeout`, `zigbee.transport_failed`, or `zigbee.port_unhealthy: cause=...` — the cause field literally names it) — a Pi-trip item, not a code read.
- **Hazard bound:** interleaved `close()`/`attemptReopen` on the not-thread-safe transport → leaked fresh FD until process death, NCP left mid-handshake, seconds of prolonged shutdown. **No next-boot corruption identified:** the open path re-syncs via ASH RST/RSTACK; the reopen path reads but never writes the (atomically-written) parameter store; the sidecar risk is the independent F-3. Disposition per **F-4**: stop-guard + ordering; cheap, post-gate.
