## §6 OBS for the hub (filed, not fixed — fence-respecting)

- **OBS-1 racing-writers residue (pre-existing class, narrowed not closed):** `ZigbeeIntegrationAdapter.close()` (`:421–428`) counts down `stopSignal` then calls `cache.flush()` WITHOUT joining the run cycle, so a cycle `maybeFlush()` write can structurally race the shutdown flush. With the mandated FIXED `.tmp` name, a true interleave could still move a partially-rewritten temp into place (writer A moves while writer B is mid-`writeString` on the same temp). NOT NEW: the pre-fix in-place concurrent `writeString` pair had the same mangle class (the old "each land a complete, valid file" comment was optimistic under true concurrency). The fix fully closes the F-3 single-writer crash class — the ruled scope — and narrows the race window to the move instant. Closing the race entirely would need a unique-per-write temp (orphan accumulation trade) or an io-serialization lock (beyond "temp-then-move ONLY"); left for a ruling if the hub prices the window as real.
- **OBS-2 platform note:** same-directory `Files.move` without ATOMIC_MOVE is a plain rename on both the Windows desk and the Pi (POSIX `rename(2)`, atomic w.r.t. observers) — the sidecar now shares the parameter store's exact crash posture; N-4's documented `synchronous=NORMAL` posture continues to govern power-cut tail durability (no fsync added anywhere, per the fence).
- **OBS-3 stale-temp lifecycle:** a crash between temp-write and move leaves at most ONE orphan `zigbee-devices.json.tmp`; the loader ignores it and the next write truncates and consumes it (self-healing, bounded) — recovery-tail-proven in test 2. No cleanup code added (idiom-faithful).
