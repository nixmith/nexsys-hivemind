# RS-1 — The Competitive Verdict-Honesty Study (returned 2026-08-18)

**The question under test, per the brief:** when a commanded device does not confirm execution, what does each platform RECORD and what is the USER SHOWN — and does ANY surface in the field distinguish *sent* vs *acknowledged* vs *confirmed-by-device-report*? Five questions per platform: Q1 the silence case · Q2 the vocabulary case · Q3 the dead-target case · Q4 the false-confirm case · Q5 the self-report case.

**The one-paragraph verdict (details and every citation below):** the sent/acked/confirmed distinction EXISTS almost everywhere in the field — in wire protocols (Matter invoke responses + subscriptions; HomeKit per-write acknowledgment; Zigbee ZCL command status; Z-Wave Supervision), in cloud APIs (Google's SUCCESS/PENDING/OFFLINE ladder; Alexa's DeferredResponse and per-property staleness stamps; SmartThings' ACCEPTED/COMPLETED/FAILED and per-device Offline results), and in fragments of UI (Apple's "No Response", Google's spoken apologies, Homey's error lines, Hubitat's command-vs-event ledger). What exists NOWHERE surveyed is the assembly: a durable, user-auditable, per-command record that says *dispatched at t0, acknowledged at t1, confirmed by the device's own report at t2 — or never confirmed*. Every platform collapses the ladder into a single undifferentiated tile state or a transient utterance; every platform's automation engine reports its own run as the unit of success rather than the device outcome; four of seven platforms ship at least one mechanism that displays assumption as fact; and no platform's history surface records a command that silently failed. The deterministic confirmation floor is MISSING from the field — while all of its raw materials are shipping, unassembled, at every layer below the user.

## §0 Falsifier headlines — the evidence AGAINST the study's premise, first

Per the brief: anything that would DISPROVE the differentiation thesis goes first, not buried. The premise at risk: *"no surface in the field distinguishes sent / acknowledged / confirmed."* Taken literally, that premise is FALSE, seven ways. Each headline below states the counter-evidence at full strength, then the precise point at which it stops. The distinction that survives all seven is stated at the end.

**FH-1 — The protocols already carry witness statements.** Matter commands are answered: an Invoke Response Action responds to each invoke with cluster-defined responses and global status codes SUCCESS (0x00) / FAILURE (0x01), and subscriptions deliver device-reported state on a liveness-bounded interval so the controller can maintain "a coherent snapshot or twin" of device state (Matter Core Specification 1.0, CSA doc 22-27349, §8.2.4/§8.10.1/§8.5, csa-iot.org/wp-content/uploads/2022/11/22-27349-001_Matter-1.0-Core-Specification.pdf, acc. 2026-08-18 — PDF-extraction wording flagged §6; SOURCE-GRADE [P-VERIFIED]). HomeKit writes are synchronously acknowledged per characteristic, with partial-failure statuses for bridged devices, and the framework's error taxonomy natively distinguishes ack failures: `timedOutWaitingForAccessory` "An accessory did not respond timely.", `readWritePartialSuccess` "An error indicating a partially successful read/write operation.", `actionSetExecutionPartialSuccess` "An attempt to execute the action set was only partially successful." (developer.apple.com/documentation/homekit/hmerror/code.md, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]). Zigbee: the field's own integration code checks per-command device status before writing state (zha lib, [HA-14] below). Z-Wave: Supervision CC reports WORKING/SUCCESS/FAIL per supervised command (docs.silabs.com/z-wave/latest/zwave-api/supervision, acc. 2026-08-17, SOURCE-GRADE [LANE]).
*Where it stops:* every one of these confirmations terminates inside the stack. No surveyed platform persists them per-command, exposes them to the user, or reconciles displayed state against them as a product behavior. The witness testifies at the wire; nothing on any user surface enters it into a record.

**FH-2 — Google ships the field's most complete outcome grammar, and its failures reach the user's ear.** The EXECUTE response status enum is a genuine dispatch/confirm ladder, verbatim: SUCCESS "Confirm that the command succeeded." · PENDING "Command is enqueued but expected to succeed." · OFFLINE "Target device is in offline state or unreachable." · EXCEPTIONS "There is an issue or alert associated with a command. The command could succeed or fail." · ERROR "Target device is unable to perform the command." (developers.home.google.com/cloud-to-cloud/intents/execute, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]). Dozens of error codes map to spoken user responses — "The following errors will produce the associated TTS on the device", e.g. deviceOffline → "Sorry, it looks like <device(s)> <is/are>n't available right now." (developers.home.google.com/cloud-to-cloud/intents/errors-exceptions, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]). A user who commands a dead device by voice hears a truthful apology, not a false OK.
*Where it stops:* every rung is the partner cloud's self-report — Google's own success metric is "A transaction is marked as a success if the Google Home platform receives a valid response indicating the intended action was fulfilled" (Home Vitals, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]); the asserted post-execution states are "used only for speech responses to the user and are not stored" (FAQ, acc. 2026-08-18 [P-VERIFIED]); PENDING has no documented reconciliation if the enqueued command dies; and none of the graded vocabulary reaches any user-visible record. §2.7.

**FH-3 — Alexa's protocol carries a complete staleness vocabulary, down to the millisecond.** Every state property a skill reports is stamped `timeOfSample` ("Time the endpoint detected the state change") and `uncertaintyInMilliseconds` — defined, verbatim: "This field represents the number of milliseconds after the endpoint last confirmed the property value." (developer.amazon.com/en-US/docs/alexa/device-apis/message-guide.html, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]). The response contract even distinguishes acknowledged-pending from complete: DeferredResponse then Response, where "A successful response confirms that the endpoint completed the requested action." (alexa-response.html, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]).
*Where it stops:* the staleness metadata is stripped before any user surface — no app view displays time-of-sample or uncertainty; "success" is whatever the skill asserts within 8 seconds with no runtime verification requirement found; and Amazon's own developer blog documents the verdict being wrong in BOTH directions (§2.3, [AX-6]). §2.3.

**FH-4 — SmartThings models per-device failure in its schemas, and its stock drivers are report-driven, not optimistic.** The Rules API execution result models, verbatim from the official SDK: `CommandExecutionResult = 'Success' | 'Failure' | 'Offline'` with `deviceId` (rules.ts, official smartthings-core-sdk, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]); the Devices API command enum is `'ACCEPTED' | 'COMPLETED' | 'FAILED'` (devices.ts, same, [P-VERIFIED]). And the platform's default Zigbee/Z-Wave Edge drivers emit the on/off event only from the device's own report — the official tutorial explicitly teaches "for real devices you should make a request to a device and wait for the response confirming the device was switched on before emitting this" (developer.smartthings.com/docs/devices/hub-connected/first-lua-driver, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]).
*Where it stops:* the vocabulary is schema-deep only — observed command responses return ACCEPTED even for devices the platform itself has marked offline (ANECDOTE-GRADE, raw API response in community thread, [ST-6]); a staff answer on the official forum states "There's not an endpoint available to obtain the execution status of the command yet" ([ST-7]); confirmation-before-emit is tutorial guidance, unenforced ("should", not must); and no user surface exposes any of it for automatic runs. §2.2.

**FH-5 — Homey MARKETS failure-routing, with a verdict-honesty example.** Advanced Flow's error lines are official, shipped, and marketed: "Advanced Flows can drag an 'error' line from any And- or Then-card. When the cards fail … the following cards can continue while using an Error-tag containing what went wrong." — and Athom's own canonical example is the study's scenario: "A great example to illustrate this new functionality is to send yourself a push notification when a smart lock fails to lock." (homey.app/en-us/news/introducing-advanced-flow/, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]). No other consumer platform surveyed markets that sentence.
*Where it stops:* the error line fires only when an app's card rejects; the SDK's success criterion is promise resolution, not device evidence — an app that resolves optimistically produces a green path over a dead device (demonstrated empirically: a powered-off wall plug produced "no failure to activate the wallplug, even when it is not connected", ANECDOTE-GRADE [HM-8]); unrouted errors vanish (no default sink, no Timeline entry, no push); and Athom's own wiki concedes the epistemics for its one-way radios: "you just have to assume they have been picked up and are being executed." ([HM-5], SOURCE-GRADE [P-VERIFIED]). §2.5.

**FH-6 — Hubitat keeps the field's only documented sent-vs-confirmed ledger.** The per-device Events page records BOTH command dispatches and device reports, with documented semantics: "A command is something sent to the device from the hub." vs "An event typically represents a change that actually happened.", and "Events typically follow successful commands" (docs2.hubitat.com/en/user-interface/devices/device-events, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]). The official troubleshooting guide even names the study's use case: use it "to determine … if the app sent a command but the device did not response [sic]" ([HU-2]). Transport truth is also user-visible in aggregate: the Z-Wave Details page defines RTT as time to "receipt of an acknowledgment packet from the device" ([HU-6], [P-VERIFIED]).
*Where it stops:* it is a forensic surface, not a verdict surface — nothing alerts on a command row with no following event row; Rule Machine's own docs concede "Sometimes, you will find that your rule, in fact, did execute as expected, but a device may not have responded as intended." ([HU-4], [P-VERIFIED]); rule "action" logs are written BEFORE execution; Supervision-based per-command confirmation is opt-in driver engineering, mostly community-authored; and the gap is patched by a six-year-old community app (Device Activity Check) rather than the platform. §2.6.

**FH-7 — Apple ships honest negatives and a durable audit surface — rationed by device class.** "No Response" is a real, immediate, truthful failure signal with its own support page (support.apple.com/en-us/102056, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]); locks and security-class accessories get a 30-day Activity list — with an unusually honest completeness disclaimer: "Activity cannot guarantee that events are captured in all circumstances. Network or power outages may result in lost events." (support.apple.com/en-us/105011, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]); and the lock tile visibly holds a pending "Unlocking…" state until device confirmation (ANECDOTE-GRADE [AP-7]).
*Where it stops:* Activity records state events, not command outcomes — a failed lock command leaves NO entry anywhere; lights, plugs, blinds and fans get no history surface at all; the displayed value is, in Apple's own words, "the last value that the system saw for the characteristic" (developer.apple.com/documentation/homekit/hmcharacteristic/value.md, acc. 2026-08-18, SOURCE-GRADE [P-VERIFIED]); automations have no run history and fail silently; and "No Response" is itself last-request-stale. Apple's rationing is itself evidence: the one device class where verdicts matter most to Apple (locks) is exactly the class that got a pending state and an audit log — the design concedes the need and confines the answer. §2.4.

**The synthesis that survives all seven, stated carefully.** The premise "no platform distinguishes sent/acked/confirmed" is false at the protocol layer, false in developer schemas, and partially false at scattered UI edges. What is TRUE, on the evidence of this study, is narrower and harder: **(a)** no surveyed platform maintains a durable, user-accessible, per-command record with distinct dispatched/acknowledged/device-confirmed states or an honest unconfirmed terminal state; **(b)** no surveyed platform reconciles the state it displays against subsequent device evidence as a product behavior with a defined truth-window; **(c)** every surveyed automation engine treats its own execution — not the device outcome — as the unit of success, and none records a per-action device verdict in any run history; **(d)** the marketed vocabulary of every platform collapses the ladder to a binary (worked / "isn't responding") with no pending state (one platform's lock-class spinner excepted), no staleness figure, and no post-hoc correction. The parts of a confirmation floor are shipping everywhere below the user; the floor itself is MISSING from the field. That formulation — missing, not inferior — is the D5-compliant form, and this study's evidence supports it at citation grade in both directions.

## §2 The comparison map

Format per platform: the five questions, each answered with citations; full verbatim quotes live in the §5 appendix under the bracketed IDs. Grades inline.

### 2.1 Home Assistant (open source — file:line at pinned tags; the deepest read, per brief priority)

**Q1 — the silence case.** A commanded device that never responds produces, at the engine layer, a *successful* action: the automation's service-call step succeeds the moment `hass.services.async_call(..., blocking=True)` returns, i.e. when the integration's handler returns — `core:homeassistant/helpers/script.py:1049–1092`, with the trace recording only the call *parameters* (`trace_set_result(params=params, …)`, `script.py:1080`); the core docstring defines blocking as "wait until service is executed", where "executed" is the handler, not the device (`core:homeassistant/core.py:2855–2879`) [HA-5][HA-6] SOURCE-GRADE. Whether silence surfaces at all depends entirely on the integration: MQTT publish succeeds at the broker regardless of the device; ZHA raises only on transport failure but **swallows device-refused commands silently** — if the Zigbee command's status response is non-success, the code logs at debug and `return`s without exception, so the action step still reports success (`zha-lib:zha/application/platforms/light/__init__.py:590–600`) [HA-14] SOURCE-GRADE; Z-Wave JS raises `HomeAssistantError` only on driver/server errors (`core:homeassistant/components/zwave_js/entity.py:421–436`) [HA-17] SOURCE-GRADE. What the user sees: the entity tile simply keeps its old state (non-optimistic paths); the automation shows "Last triggered" updated — a timestamp stamped BEFORE the actions run (`core:homeassistant/helpers/script.py:1994`) [HA-7] SOURCE-GRADE; the logbook entry says the automation "triggered" (`core:homeassistant/components/automation/logbook.py:34–36`) [HA-9] SOURCE-GRADE; the trace UI shows the step green: "Executed: {time}" (frontend en.json, `ui.panel.config.automation.trace.path.executed`) [HA-10] SOURCE-GRADE. Nothing records that no confirmation ever arrived. A dead mains-powered Zigbee device continues to *look* available for up to 2 hours (battery: 6) before the staleness heuristic marks it unavailable (`zha-lib:zha/application/const.py:78–79`; surfaced to users as the config strings "Consider mains-powered devices unavailable after") [HA-15][HA-10] SOURCE-GRADE.

**Q2 — the vocabulary case.** The complete user-facing outcome vocabulary at pinned frontend tag: "Executed: {time}" · "Finished at {time} (runtime: {executiontime} seconds)" · "Error: {error}" · "Still running" · "Last triggered" · state "Unavailable" [HA-10] SOURCE-GRADE. There is no *sent*, no *acknowledged*, no *confirmed-by-report* anywhere in the automation, trace, logbook, or entity surfaces; "Executed" means the handler returned (Q1). The one honest epistemic marker HA ships is entity-static, not per-command: `assumed_state` — "Return `True` if unable to access real state of the entity" (`core:homeassistant/helpers/entity.py:876–878`; developer docs: "based on our assumption instead of reading it from the device", developers.home-assistant.io/docs/core/entity/, acc. 2026-08-17) [HA-13] SOURCE-GRADE — a per-entity flag that changes the UI affordance, not a per-command verdict. The confirmation-vocabulary gap is a known, dormant architectural item: architecture discussion #740, "Unify optimistic states for entities at core level to prevent UI 'flipflops' and Voice Assistant errors", opened 2022-02-24, proposes marking state optimistic "until actual confirmation arrives" — last comment 2025-05-29, unanswered (github.com/home-assistant/architecture/discussions/740, acc. 2026-08-17) [HA-18] SOURCE-GRADE (repo artifact). Note what even the proposal is for: fixing UI flicker, not creating a verdict record.

**Q3 — the dead-target case.** Source-established, and sharper than expected: a service call targeting an **unavailable** entity does not error — the entity is *silently filtered out of the call*: `entity_candidates = [e for e in entity_candidates if e.available]` (`core:homeassistant/helpers/service.py:720`; same filter at :377/:393 in the deprecated helper) [HA-1] SOURCE-GRADE. The ONLY surface is a system-log warning: "Referenced <entities…> are missing or not currently available" (`core:homeassistant/helpers/target.py:151–154`) [HA-2] SOURCE-GRADE. No exception is raised, so: the action step succeeds, the run completes, "Last triggered" updates, the trace shows the step Executed, and the logbook says "triggered". The automation *reports a clean run while having done nothing to the dead device.* Contrast: when an integration DOES raise (e.g. Z-Wave transport failure), the default is the opposite failure mode — `continue_on_error` defaults to `False` (`core:homeassistant/helpers/script.py:539`), so one dead device **aborts every remaining action** in the automation, with the error visible only in the trace ("Error: {error}") and the log (`script.py:601–638`) [HA-3][HA-4][HA-10] SOURCE-GRADE. So HA's dead-target behavior is bimodal — silent skip (unavailable-filtered) or silent mid-run abort (raise) — and in neither mode is the user notified by default. Traces, the only forensic record, are capped at 5 per automation, FIFO-evicted (`core:homeassistant/components/trace/const.py:17` `DEFAULT_STORED_TRACES = 5`; `trace/util.py:93–94` `LimitedSizeDict(size_limit=stored_traces)`; docs: "The last 5 traces are recorded for all automations", home-assistant.io/docs/automation/troubleshooting/, acc. 2026-08-17) [HA-8][HA-22] SOURCE-GRADE.

**Q4 — the false-confirm case.** Named mechanisms, at source: **(a) MQTT optimistic mode** — after publishing the command, "# Optimistically assume that switch has changed state." `self._attr_is_on = True; self.async_write_ha_state()` (`core:homeassistant/components/mqtt/switch.py:156–160`; lights identical, `mqtt/light/schema_basic.py:869/887`); optimistic is **forced on** when no state topic exists (`switch.py:137–138`), and documented as the default in that case: "Flag that defines if switch works in optimistic mode. Default: `true` if no `state_topic` defined, else `false`." (home-assistant.io/integrations/switch.mqtt/, acc. 2026-08-17) [HA-11][HA-12] SOURCE-GRADE. Honesty credit where due: MQTT sets `_attr_assumed_state = bool(self._optimistic)` (`switch.py:116`, `schema_basic.py:324`), so the UI affordance discloses the assumption — but the state machine still records commanded-as-actual with no revert-on-silence and no timeout. **(b) Z-Wave JS barrier-signaling switch** — first-party comment, verbatim: "# this value is not refreshed, so assume success" then `self._state = True; self.async_write_ha_state()` (`core:homeassistant/components/zwave_js/switch.py:142–144`) [HA-16] SOURCE-GRADE. **(c) ZHA ack-equals-state** — state is written on the device's *command acknowledgment*, not its attribute report (`self._state = True` immediately after the SUCCESS status check, `zha-lib:…/light/__init__.py:592–600`) [HA-14] SOURCE-GRADE — acknowledged-grade truth presented identically to report-grade truth. **(d)** The general pattern is platform-sanctioned: `assumed_state` exists precisely because integrations legitimately cannot know, yet nothing distinguishes *those* entities' recorded history from device-evidence history downstream (recorder stores both identically).

**Q5 — the self-report case.** HA's own liveness self-report is real but process-grade: the Supervisor watchdog probes the Core API every 120 s and restarts Core after 2 missed probes — "Watchdog missed %s Home Assistant Core API responses in a row. Restarting Home Assistant Core!" (`supervisor:supervisor/misc/tasks.py:48,164–213`) [HA-19] SOURCE-GRADE. That is evidence-based (an actual probe) about the *process*, silent about whether automations fire or devices confirm. Device liveness is the staleness heuristic of Q1 (2 h/6 h, ZHA) — a timeout, not supervision. And the platform's memory of what happened is mutable and self-expiring by default: recorder `auto_purge` defaults `True`, `purge_keep_days` defaults **10** (`core:homeassistant/components/recorder/__init__.py:103–105`) [HA-20] SOURCE-GRADE — an ordinary read-write SQLite database with a built-in purge action; nothing tamper-evident, nothing durable beyond 10 days unless reconfigured. Demand-side (labeled, aggregate): users ask for exactly the missing floor — a 2023-10-23 feature request for a platform-wide "automatic check … if after a state change was requested the requested entity state is actually being reported by the device… after a configurable time" (community.home-assistant.io #630192, acc. 2026-08-18) and a 2024-12-09 ask for "a real time … notification if a Zigbee device … has not responded to a (on/off) command", answered with the DIY wait-then-check-then-notify pattern (community #808199, acc. 2026-08-18) [HA-21] ANECDOTE-GRADE (demand evidence only).

**HA net:** the most honest *forensics* in the DIY field (traces with per-step errors, availability states, assumed-state disclosure) and no verdicts: success means dispatched, dead targets are dropped or abort silently per integration, three named false-confirm mechanisms at source, a capped 5-run FIFO trace as the only record, and a 10-day self-expiring history.

### 2.2 SmartThings

**Q1 — the silence case.** The platform records a cloud-side acceptance and nothing else queryable: `POST /devices/{id}/commands` returns per-command `status`, and the observed synchronous status is ACCEPTED — including, per a user-pasted raw response, for a device the platform itself displayed as offline (`{"results":[{"id":"…","status":"ACCEPTED"}]}`) [ST-6] ANECDOTE-GRADE (raw output in community thread, acc. 2026-08-17). There is no per-command execution record to consult afterward: staff on the official forum, 2020: "There's not an endpoint available to obtain the execution status of the command yet" — recommendation: poll device state instead [ST-7] STAFF-ANECDOTE; no later documentation refuting this was found (§6). The History surface is an *event* store — the official SDK models history records as attribute events (capability/attribute/value/text/epoch; `history.ts`) [ST-8] SOURCE-GRADE — so a command that produced no device event leaves no trace in History. What the user sees: for already-marked-offline devices the app blocks control; for the undetected case, a stale tile — and Samsung's own support pages document the symptom class ("showing an incorrect status, appears offline, or doesn't respond to commands") with a manual remedy: "Tap Refresh on the device page" [ST-9] SOURCE-GRADE.

**Q2 — the vocabulary case.** The schema vocabulary is three-way twice over — Devices API `CommandStatus = 'ACCEPTED' | 'COMPLETED' | 'FAILED'`; Rules API `CommandExecutionResult = 'Success' | 'Failure' | 'Offline'` per `deviceId` inside `RuleExecutionResponse` (official smartthings-core-sdk `devices.ts`/`rules.ts`, acc. 2026-08-18) [ST-1][ST-2] SOURCE-GRADE [P-VERIFIED]. But: no retrieved documentation defines what any value *means* (the public API reference is a JS SPA that returned no text; §6); the observed dispatch-time answer is ACCEPTED (above); and no surface — app, History, Routines — exposes a sent/acked/confirmed lifecycle for any individual command. App History shows device events plus a "General" category for routine/scene runs, with community-reported omissions ("that history is really iffy. Sometimes it omits a ton of history") [ST-11 thread set] ANECDOTE-GRADE.

**Q3 — the dead-target case.** Routines fire at offline devices with no health gate — "The routines can also send commands to the device even if it is offline"; "automations and things don't care and will attempt to send commands anyway" [ST-12] ANECDOTE-GRADE (consistent across two threads incl. a prominent driver developer; no official statement either way found — §6). Official Routine documentation contains no failure, retry, or offline-target concept at all; its promise is unconditional: "When the conditions are met, the device will automatically perform that action!" (samsung.com Routines guide, acc. 2026-08-17) [ST-10] SOURCE-GRADE (absence + promise). The one outcome surface found is manual-run-only, undocumented, and unreliable in both directions: the app can report a manually-run routine "ran, but not everything worked correctly" — in the reported case listing ALL devices rather than the failing one, and flagging locks that had in fact executed ("Locks all lock, though."); a 2021 Scenes equivalent showed "Failed… ran but some devices didn't work" for scenes that had worked [ST-11] ANECDOTE-GRADE. For automatic executions: no notification, no failure entry, History shows the routine as having run.

**Q4 — the false-confirm case.** Split verdict, and the split is the finding. **Stock mesh drivers are report-driven** — the default Zigbee handler sends the on command and emits NO event; the switch event is emitted by the *attribute report* handler when the device reports (zigbee defaults doc), and Z-Wave defaults mirror this (SwitchBinary Set → event only on Report) [ST-5] SOURCE-GRADE [LANE]. The official tutorial then gives the game away in one sentence — the toy driver emits success in the command handler, with the caveat: "for real devices you should make a request to a device and wait for the response confirming the device was switched on before emitting this" [ST-3] SOURCE-GRADE [P-VERIFIED]. *Should.* `emit_event` carries no requirement of device evidence; platform "state" is defined as the most recent emitted event (`state_cache`, device API docs) [ST-3] SOURCE-GRADE. So: any custom/LAN/virtual driver may fabricate state at will, and **cloud-to-cloud (Schema) state is entirely partner-asserted** — the partner sends state updates and even its own health claim ("Always send the `st.healthCheck` Capability to indicate whether the device is online or offline") with no SmartThings-side probe [ST-13] SOURCE-GRADE [LANE]. The false-confirm risk for stock mesh devices is the stale-forever variant: report-backed state that nothing reconciles when reports stop (Q1's "incorrect status" support pages are the vendor's own acknowledgment of this class).

**Q5 — the self-report case.** The health model is documented and its verbs are honest about being predictions: ONLINE means "A device can be *expected* to respond to a command… or report an event"; UNHEALTHY = inactive past its health-check interval, "possibly offline"; OFFLINE = UNHEALTHY and "cannot be contacted"; marking happens when a device "does not respond in the specified amount of time" — with a stated blind-spot list ("Device health does not account for some issues… including joining or removing devices, device firmware updates, problems updating the device state on the client, and platform-event loss") (developer.smartthings.com/docs/devices/health, acc. 2026-08-18) [ST-4] SOURCE-GRADE [P-VERIFIED]. Who supplies the verdict differs by protocol: Zigbee/Z-Wave/Matter health is "automatically determined at the radio level" (driver calls to online()/offline() are *ignored* for these), LAN health is driver-asserted, cloud-to-cloud health is partner-asserted [ST-13] SOURCE-GRADE [LANE] — i.e., only the mesh path is first-party evidence; the rest is relayed self-report. In practice the verdict errs both ways: weeks-offline devices controllable by routine; recurring false "Hub is disconnected" notifications ("everything was working fine regardless") [ST-12/ST-16] ANECDOTE-GRADE. Cloud status: status.smartthings.com asserts per-region component status ("Hubs, Devices, and Automations" etc.); no methodology published [ST-14] SOURCE-GRADE [LANE].

**ST net:** the field's richest *dormant* schema vocabulary (two three-way enums including per-device Offline results) with no documented semantics, no queryable per-command outcome, event-only history, ungated routines with an unreliable manual-run-only failure toast, tutorial-optional confirmation discipline, and health verdicts that are first-party evidence on exactly one of three device paths.

### 2.3 Amazon Alexa (+ Ring, where distinct)

**Q1 — the silence case.** The verdict channel for a voice command is a single spoken error whose trigger is *skill response timing*, not device truth: Alexa waits 8 seconds for the skill's response, then says "Sorry, <device name> is not responding" — and Amazon's own developer blog documents the false negative: "If steps 4-7 takes more than 8 seconds, the customer will hear the 'Sorry, <device name> is not responding' message, **even though the light is turned off.**" (developer.amazon.com blog, 2020-12, acc. 2026-08-18) [AX-6] SOURCE-GRADE [P-VERIFIED]. A second variant is skill-asserted health: EndpointHealth-driven "isn't responding. Please check its network connection and power supply." [AX-7] SOURCE-GRADE [P-VERIFIED]. App surface: official banner wording could not be retrieved (amazon.com help pages robots-blocked; §6); user reports consistently show "Device is unresponsive" / "Server is unresponsive" banners [AX-9] ANECDOTE-GRADE. History surfaces (Voice History; the privacy-page "Smart Home Device History") record utterances and device usage; no source, official or community, describes either recording a *failure verdict* for a smart-home command (§6). Scheduled/triggered Routines: no failure feedback channel found at all — the only Routine push notifications are ones the user authors as actions [AX-10] ANECDOTE-GRADE + absence.

**Q2 — the vocabulary case.** The wire protocol has the full ladder, developer-only. Verbatim: "A successful response confirms that the endpoint completed the requested action." The staleness stamps — the exact honesty primitive — are stripped before display.

**Q3 — the dead-target case.** No official documentation of Routine execution semantics with an offline target was retrievable (help pages robots-blocked; developer docs silent; §6). **Q4 — the false-confirm case.** Structural: Alexa's "OK" is generated from the skill's self-composed Response; the docs *define* it as a completion claim ("confirms that the endpoint completed the requested action") but nothing machine-enforces that the device did anything — the lock interface even instructs skills by wall-clock: "If your hardware can lock in five seconds or fewer, send an Alexa.Response event", with no verification requirement found on the page (checked-absence) [AX-1][AX-8] SOURCE-GRADE ([AX-8] [LANE]). Enforcement is certification-time, not runtime [AX-8] SOURCE-GRADE [LANE]. App-displayed state is a relay of skill reports ("If you set `retrievable` to `false`, Alexa can't accurately display or respond when the customer asks for the state of their device") [AX-5] SOURCE-GRADE — third-party assertion presented as device truth, staleness metadata withheld. Documented false negatives (Q1) complete the both-directions picture.

**Q5 — the self-report case.** "Unresponsive" is timeout-inferred (8 s) or skill-asserted (EndpointHealth `connectivity: OK|UNREACHABLE`, with reason codes and a freshness rule — connectivity flips must be reported "in three seconds or less") [AX-7] SOURCE-GRADE [P-VERIFIED] — Alexa relays the skill's claim about the skill's own device. ### 2.4 Apple Home / HomeKit (+ Matter controller behavior)

**Q1 — the silence case.** The protocol layer *knows* immediately: HAP writes are synchronous request/response, and the framework has dedicated errors for silence — `timedOutWaitingForAccessory` "An accessory did not respond timely.", `accessoryNotReachable`, `accessoryPoweredOff` "An error indicating the accessory is off." What the user sees: a transient alert ("This accessory is not responding." per developer-forum report [AP-7] ANECDOTE-GRADE) and the tile label "No Response" — which has its own support page: "If 'No Response' appears next to a smart home accessory made by a manufacturer other than Apple, learn what to do." (support.apple.com/en-us/102056, acc. 2026-08-18) [AP-3] SOURCE-GRADE [P-VERIFIED]. That page is pure troubleshooting: parent-pass sweep confirms it contains **no mention of any log, history, notification, or record of failures** [AP-3] SOURCE-GRADE (verified absence). What is RECORDED: for general accessories (lights, plugs, fans, blinds) — nothing, anywhere, ever. (HMCharacteristic.value, acc. 2026-08-18) [AP-2] SOURCE-GRADE [P-VERIFIED]. *User surface:* one undifferentiated tile state plus transient "No Response" — no sent/acked/confirmed labels anywhere; the sole visible pending state is the lock's "Unlocking…" spinner awaiting device confirmation [AP-7] ANECDOTE-GRADE. **Q3 — the dead-target case.** Automations targeting unreachable accessories fail silently: Apple's automation guide documents no failure behavior, no notification, no history — parent-lane sweep of the guide found "no mention of what happens when automations fail, error logs, automation history, notifications about automation outcomes" [AP-8] SOURCE-GRADE (verified absence) [LANE]. **Q4 — the false-confirm case.** Apple's displayed state is honest-by-architecture *to the bridge*, and the bridge is the hole: HAP bridges answer for their devices, and the display faithfully renders bridge assertion indistinguishably from device evidence — the canonical case being Zigbee bulbs cut at the wall switch: the bridge's reachability flag clears only after "a few subsequent requests to the device go unanswered", so the platform "continues to show these lights as on" (homebridge-hue maintainer wiki, describing Hue-style bridge stacks) [AP-10] ANECDOTE-GRADE (well-corroborated maintainer documentation). **Q5 — the self-report case.** Home-hub status is a two-word assertion ("Connected"/"Standby") whose basis Apple nowhere documents (§6); it wedges falsely (hubs stuck in Standby, community-reported) [AP-11] ANECDOTE-GRADE. **AP net:** the strongest protocol-layer confirmation in the consumer field, an honest transient negative, and a durable audit surface *rationed to the liability classes* — with zero record of failed commands for any class, no automation history at all, bridge assertion displayed as device truth, and a 30-day self-expiring event list carrying its own no-guarantee disclaimer. Apple's per-class rationing (locks get pending states + activity logs; lamps get nothing) is the clearest single piece of evidence in this study that the industry understands verdict honesty as a *feature* — and prices it by consequence class rather than shipping it as a floor.

### 2.6 Hubitat Elevation

**Q1 — the silence case.** Uniquely in this field, the record distinguishes the two halves: the per-device Events page logs command rows ("command-on", marked and attributed — "Produced by" shows "the app or driver that called the command") AND device-report rows, with documented semantics: "A command is something sent to the device from the hub." / "An event typically represents a change that actually happened." / "Events typically follow successful commands" (docs2.hubitat.com Device Events, acc. 2026-08-18) [HU-1] SOURCE-GRADE [P-VERIFIED]. The official troubleshooting guide names the exact use: the Events page can determine "if the app sent a command but the device did not response [sic]" [HU-2] SOURCE-GRADE [LANE]. What the user sees live: dashboards are event-driven (websocket) — tiles do NOT flip optimistically; a tile shows an hourglass until a state event arrives, and with a silent device the hourglass persists or state stays stale [HU-3] SOURCE-GRADE (dashboard doc) + ANECDOTE-GRADE (hourglass behavior). **Q2 — the vocabulary case.** A documented two-tier vocabulary — command rows (sent) vs event rows (device-reported) — plus a physical/digital origin distinction on events ("physical" = paddle press at the device, "digital" = hub command) [HU-1] SOURCE-GRADE. No per-command *acknowledged* tier in any user surface: radio ACKs exist and are measured — Z-Wave Details defines RTT Avg as "the elapsed time between the sending of a packet and the receipt of an acknowledgment packet from the device", plus PER and Route Changes (acc. 2026-08-18) [HU-6] SOURCE-GRADE [P-VERIFIED] — but only as per-device aggregates, never tied to a specific command. Z-Wave Supervision (device-level execution confirmation) exists in the platform, with inbound handling mandatory for drivers ("It is critical that you send a supervision response…") and outbound encapsulation "optional… (not demonstrated in this driver)" [HU-5] SOURCE-GRADE [LANE]; per ex-staff and expert community posts, outbound supervision-with-retry is driver-by-driver opt-in engineering, largely community-authored [HU-5] ANECDOTE-GRADE/STAFF-ANECDOTE.

**Q3 — the dead-target case.** Silent continuation, conceded in the platform's own documentation: "Sometimes, you will find that your rule, in fact, did execute as expected, but a device may not have responded as intended." (Rule 5.1 docs, acc. 2026-08-18) [HU-4] SOURCE-GRADE [P-VERIFIED] — the platform's viewpoint is that the rule succeeded. No retry, no error path, no abort documented for non-responding mesh targets; community reports include a dead node degrading neighbors' delivery within the same action [HU-12] ANECDOTE-GRADE. No built-in offline detection for the general case: the standing patch is the community "Device Activity Check" app (since 2020-05-27, 21+ pages of thread activity) — notifications when devices haven't "checked in", built on the "Last Activity At" timestamp [HU-10] ANECDOTE-GRADE (the app's six-year lifespan is the demand exhibit).

**Q4 — the false-confirm case.** Tiles wait for device events (Q1) — the optimistic-tile mechanism is absent; the false-confirm risks are staleness-shaped: **(a)** Groups' "on/off optimization" suppresses commands to members that "already report as on" — stale reports suppress real commands [HU-7] SOURCE-GRADE [LANE]; **(b)** group-activator state and Zigbee group multicast trust prior reports/unacked multicast [HU-7] SOURCE-GRADE [LANE] + protocol-level inference (labeled); **(c)** legacy non-reporting devices exist and the platform ships a *poller app* because their state goes stale ("Older GE dimmers and switches are well known to have this problem") [HU-8] SOURCE-GRADE [LANE]; a community report shows a power-cycled plug that "reports 'on'" after loss — stale-state false-confirm in the wild [HU-12] ANECDOTE-GRADE.

**Q5 — the self-report case.** In-UI alerts exist for hub-level pathology ("Alerts and notifications, like the availability of an update or high hub resource usage") [HU-9] SOURCE-GRADE [LANE]; a low-memory auto-reboot watchdog demonstrably exists ("Hub memory is critically low, rebooting now" in a user's hub log) but is undocumented — staff, asked what triggers it: "That's the part we are still looking into", and in the cited case the reboot itself hung [HU-9] STAFF-ANECDOTE. No public cloud status page: status.hubitat.com does not resolve (checked 2026-08-17); the 2018 request for one was answered by a co-founder redirecting to localness [HU-9] STAFF-ANECDOTE. **HU net:** the field's only documented sent-vs-confirmed *ledger* — forensic, passive, unalerted — plus user-visible transport aggregates; and above it, an automation engine whose own docs concede rules "execute as expected" while devices don't respond, no offline supervision (six-year community patch), dispatch-time action logs, and hub self-report that is real but undocumented and cloud-status-free. Hubitat's marketing meanwhile uses "reliable" strictly as an availability/latency claim (§4.2).

**Q2 — the vocabulary case.** The field's most granular outcome grammar (FH-2): the five-value EXECUTE status ladder with PENDING as licensed optimism ("Command is enqueued but expected to succeed."), per-command errorCode "which will map to the errors presented to users", post-execution `states` "if available"; QUERY carries an explicit `online` reachability bit; Report State is mandatory ("You must implement Report State in order to submit a Cloud-to-cloud integration.") with the stale-state rationale stated ("Assistant needs to have the current state of a device, without requiring a round-trip to the device") [GH-1][GH-2][GH-3] SOURCE-GRADE [P-VERIFIED]. User reach: the TTS renderings reach the ear; the grammar itself — SUCCESS vs PENDING, code identities, Vitals, logs — appears on no user surface found; PENDING has no documented user-visible rendering distinct from SUCCESS and no documented reconciliation if the enqueued command dies [GH-1] SOURCE-GRADE (absence).

**Q3 — the dead-target case.** Design-time validation exists (an invalid script can't be saved) but validations are capability-based, not reachability-based [GH-9] SOURCE-GRADE [LANE]. Runtime: documentation goes silent — parent-lane keyword sweeps of the starters/conditions/actions reference for offline/unavailable/unreachable returned nothing, and the execution-logs page documents no failure vocabulary [GH-7] SOURCE-GRADE (verified absence) [LANE]. The Routine troubleshooting page concedes non-execution without promising notice ("A Routine may fail to run due to a number of reasons") [GH-7] SOURCE-GRADE [LANE]. Community threads report automations not running reliably and Routine activity not appearing in the documented history surface [GH-13] ANECDOTE-GRADE (titles; bodies robots-blocked, §6).

**Q4 — the false-confirm case.** Structural, end to end: the partner asserts outcome and post-state in one breath ("Your `EXECUTE` response should return the new state of the device after the execution."); SUCCESS is *defined* as the partner's confirmation; Google's own success accounting is receipt-of-claim ("A transaction is marked as a success if the Google Home platform receives a valid response indicating the intended action was fulfilled") [GH-1][GH-5] SOURCE-GRADE [P-VERIFIED]. No document describes Google independently verifying a claimed state against the device. The State Accuracy partner target ("State Accuracy >= 99.5% helps ensure users see correct results") is the quiet admission that displayed state is partner claim with a tolerated error budget [GH-5] SOURCE-GRADE [P-VERIFIED]. A per-command confirmation channel EXISTS as an optional notification feature: "Follow-up responses: A confirmation that a device command request succeeded or failed, for example when locking a door… Use these alerts for device commands that take time to complete." [GH-11] SOURCE-GRADE [LANE] — optional per-integration, absent from consumer marketing.

**Q5 — the self-report case.** How the app decides a cloud device is "Offline" absent partner push is undocumented (§6); partners are obligated to push offline state even after returning deviceOffline errors [GH-3] SOURCE-GRADE [LANE]. Status dashboards: status.nest.com exists (JS-only; component detail via third-party monitor only, §6). Local Home SDK is marketed as reliability with a *silent* fallback ("In the event that the local fulfillment path fails, your cloud fulfilment is used as a fallback execution path") — nothing tells the user which path ran [GH-10] SOURCE-GRADE [LANE].

**GH net:** the richest grammar, the strictest partner mandates, real spoken negatives — and a trust model in which "success" is defined as receiving the partner's claim, PENDING is spoken as success, the graded vocabulary stops at the developer console, and the one true per-command confirmation feature (follow-up responses) is optional plumbing no consumer surface advertises.

**The five absence statements (the market's missing floor, stated neutrally):**

1. **Q1 —** No surveyed platform records an unconfirmed command *as an unconfirmed command*, anywhere a user can later see. The honest negatives that exist (spoken errors, "No Response", NO_ACK popups) are all transient; every durable history in the field is an event store that a silent failure never enters. Seven of seven.
2. **Q2 —** No surveyed platform exposes a sent/acknowledged/confirmed distinction on a user surface. Six of seven carry the distinction in protocol or schema; one (Hubitat) persists a two-tier (sent/confirmed) forensic ledger without alerting on it; zero present the ladder, a pending state (locks at Apple excepted), or a staleness figure to users.
3. **Q3 —** No surveyed platform notifies the user by default when an automation's target is dead, and none records a per-action device verdict in any run history. The observed modes are: silent skip, silent mid-run abort, fire-anyway, and (one platform, manual runs only) an unreliable partial-failure toast. Seven of seven lack a default honest answer.
4. **Q4 —** Six of seven platforms ship at least one mechanism that displays commanded or asserted state as actual state without device evidence (optimistic writes, promise-resolution success, partner/skill self-report, bridge assertion, "assume success", unenforced driver emits). The seventh (Hubitat) — and SmartThings' stock-mesh path specifically — avoid fabrication but not staleness: report-backed state that nothing reconciles when reports stop. Zero platforms bound the staleness of what they display.
5. **Q5 —** Self-liveness reporting is evidence-based at the process/hub level on three platforms (HA's API-probe watchdog, Homey's heartbeat push, Hubitat's resource alerts) and asserted or third-party-relayed everywhere device truth is concerned (skill/partner/driver self-reports; "can be expected to respond"; undocumented "Connected"). No platform's self-report extends to the honesty of its own *records* — none marks displayed state as assumed vs reported per datum (HA's per-entity flag is the closest artifact), and none offers tamper-evidence or guaranteed retention for what it does record (10-day default purge; 30-day auto-delete with a no-guarantee disclaimer; 5-trace FIFO caps).

### 4.3 The verified-absence sweep — does anyone market verdict honesty? (refutation-welcome)

Nine targeted searches were run (2026-08-17; exact queries logged in the lane and reproducible): `smart home "confirm the device actually"` · `"command confirmation" home automation feature marketing` · `smart home "know when it fails" device command` · `"closed-loop" smart home control verification` · `smart home app "did it actually happen" verify` · `"verify the command" state confirmation feature` · `"the light actually turned on" confirmation sensor` · `Z-Wave Supervision command class confirm executed` · `openHAB autoupdate documentation state prediction`. Twenty-plus vendor pages checked (majors + Loxone, Control4, Crestron, Savant, Josh.ai, Shelly, Aqara, Bosch, Tuya, Brilliant, SmartRent, Level, Latch/DOOR).

**Result: no consumer-facing smart-home vendor was found marketing truthful command-confirmation, closed-loop execution verification, or tell-me-when-it-fails.** (Absence within search scope, not proof of absence market-wide — §6.) What the sweep surfaced instead, and it is the study's sharpest structural finding, is that the concept exists in exactly four non-consumer forms:

1. **Unmarketed protocol/API plumbing.** Z-Wave Supervision status enums (WORKING/SUCCESS/FAIL — docs.silabs.com, acc. 2026-08-17 [FD-13] [LANE]); Google's optional follow-up responses ("A confirmation that a device command request succeeded or failed, for example when locking a door" [GH-11]); Alexa's staleness stamps [AX-4]; SmartThings' dormant enums [ST-1/2]. The capability ships; no one sells it.
2. **An honestly documented *prediction* default.** openHAB — adjacent-FOSS, outside the seven — documents its false-confirm mechanism by name: "When left as default, openHAB's `autoupdate` function attempts to predict the outcome of a *command* on the Item *state*." with the opt-out "`autoupdate="false"` … keeps the current state of the Item, even if a *command* has been received." (openhab.org/docs/configuration/items.html, acc. 2026-08-18) [FD-4] SOURCE-GRADE [P-VERIFIED]. The one place the field says "prediction" out loud is documentation, not product.
3. **Unfulfilled user requests** (§4.6): the closed-loop check exists as feature-request text on the platforms' own forums, in the users' own words.
4. **The pro channel** (§4.5): failure-visibility IS marketed — to installers, about liveness, at a price.
