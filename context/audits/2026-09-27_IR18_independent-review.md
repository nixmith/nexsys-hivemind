## §0 Verdict

The instruction is correct at the bytes (every pin, range, count and worked value re-verified — §4 below) and fits the adapter's three seams (handler → classifier → reporting row). One design gap must be closed BEFORE it runs because the adoption one-way door makes it durable (A1); two cheap test adds close the handler-to-wire gap the siblings already cover (A2); one documented-contract lag (A3). ## §A Fold into IR-18 before dispatch
**A1 — Measurement clusters must ride EVERY arm, not only 0x0400.** As cut, `withIlluminance` attaches illuminance on every arm (the meters' R2/IR-24 shape) — but temperature (0x0402) and humidity (0x0405) still attach ONLY on the 0x0302 arm (`EndpointClassifier.java` :95–:134: `hasHumidity` feeds `temperatureSensor()` alone; `binarySensor()` :237 and `fallback()` :274 never look at 0x0402/0x0405). The device on the desk makes this concrete: the Hue motion SML003 is EP2 device type 0x0107 with input clusters 0001 0400 0402 0406 (DEVICE-SET :30). Under IR-18 as cut it adopts BINARY_SENSOR = occupancy + battery + illuminance (+identify) and its TEMPERATURE IS STRANDED — forever, by the one-way door (DEVICE-SET :77; `EndpointClassifier` :260). The same gap holds for any 0x0107/0x0051/light endpoint carrying 0x0402 or 0x0405.
Fix (smaller than the instruction's own Row 3): replace `withIlluminance` + the new fallback row with ONE post-processing method `withMeasurements(classified, descriptor)` in `withMeters`' exact shape (:180–:203), driven by a three-row table {0x0400 → illuminanceMeasurement(), 0x0402 → temperatureMeasurement(), 0x0405 → humidityMeasurement()}: append each capability whose cluster is present AND whose id is not already on the classification (append-if-absent — the 0x0302 arm's output stays byte-identical, so its `containsExactlyInAnyOrder` pins at `EndpointClassifierTest` :126/:140 stay green); when `classified` is EMPTY and any measurement cluster is present, return SENSOR with those capabilities (the measurement-only endpoint — `withMeters`' own rule). No fallback row is needed at all: for [0000 0001 0400] the DP-7 row already yields SENSOR + battery and the post-processing appends illuminance; for [0000 0400] alone the fallback is empty and the post-processing yields SENSOR + illuminance. The double-add hazard the instruction guards against disappears with it. Files table unchanged (still rows 3 and 7). Tests: re-cut T8 to the Hue descriptor — 0x0107 with [0x0000, 0x0001, 0x0003, 0x0400, 0x0402, 0x0406] → BINARY_SENSOR with exactly one each of occupancy, battery, illuminance_measurement, temperature_measurement (+identify) — and add T8b: fallback [0x0000, 0x0001, 0x0402] → SENSOR + temperature + battery (the temperature-only device that is not typed 0x0302). §1's purpose line and §8's MODULE_CONTEXT row say "the three measurement clusters ride their presence on every arm", not "illuminance".
Why now and not IR-18b: the cost is the same method IR-18 already writes, with a table instead of one constant; the Hue is unboxed on the desk (`HUE-MOTION: hold`); a second lane before its join is pure overhead, and a join before that lane strands the temperature.

**A2 — Two tests the siblings have and IR-18 lacks.** (i) T7b in `ClusterHandlersTest`'s nested-class shape (:281–:290, "TemperatureMeasurement 0x0402 → temperature_c"): a 0x0400 report dispatches THROUGH the table — 25,001 → 316.2. (ii) T11 in `ZclIngestionUnitTest`'s shape (:639–:651, `humidityReportPublishesCanonicalPercent`): a 0x0400 report on an adopted entity publishes `state_reported` with `attributeKey == "illuminance_lux"` AND `rawProtocolUnit == "log10x10000+1"` — the dialect string is the instruction's auditability claim (§4 Row 1) and nothing in T1–T10 proves it reaches the wire (`ZclIngestionUnit.java` :842 is the consumer). Both are additive; T11 adds `ZclIngestionUnitTest.java` as files-table row 10.

**A3 — The model's documented contract lags.** `EntityType.java` :92 (BINARY_SENSOR: "Optional capabilities: Battery, DeviceHealth") and :80 (SENSOR) do not name IlluminanceMeasurement/TemperatureMeasurement as optional on BINARY_SENSOR. Enforcement is on type×ROLE only (`allows(EntityRole)` :123; `Entity.java` :30), so nothing rejects at runtime — but the javadoc IS the model's stated contract. Either row 11: the two javadoc lines in `core/device-model/.../EntityType.java` (docs-only; ARCH-RULE-REACH untouched — no code, no dependency), or an explicit "documented contract lags; docs delta filed" line in the return plus Doc 02 §4.2's table in the docs repo. Recommend row 11.

## §B Forks — decide in the dispatch or accept the Coder's call
**B1 — the one-decimal rounding.** The siblings do not round (`raw / 100.0` is already two-decimal). The honest rationale for rounding lux is not "the rounding IS the contract" but the renderer: the dashboard prints NUMBER as `String(v)` (`web-ui/dashboard/src/lib/format.ts` :426–:433), so an unrounded `Math.pow` shows 316.22776601683796. Keep one decimal (raw retained; the bench re-derives), re-word §4's rationale, and note the shape: the encoding's own resolution is 0.023 % relative — coarser than 0.1 lx above ~4 lx, finer below it. Alternative if the hub prefers a policy that matches the encoding: four significant figures. Not blocking.
**B2 — the count pins.** Six `hasSize` pins (ClusterHandlersTest :205/:229/:251/:253/:261/:264) move by one on every handler added — brittle by design. Allow the Coder (§10) to replace them with `containsOnlyKeys(<the nine ids>)` / the ten and eleven variants: stronger (names the set) and ends the +1 churn. Recommend allowing it.
**B3 — the reportable change 1,000.** Fine: a factor of 1.26 per report plus the 3600-s heartbeat catches dusk in ~26 % steps. z2m's default is far chattier; ours is the quieter, defensible number. Leave.
**B4 — DP-1 (0 → 0.0 lux).** Agree, with the wording "below the measurable floor (< 1 lx)" in the javadoc — the device says "too low", not "zero"; raw "0" carries the distinction.

## §C v82 queue items this review surfaces (not IR-18's)
**C1 — IR-64 (new): the capability-evolution WU — the strategic lever.** AMD-59 (RATIFIED 2026-06-05; Doc 02 :10, Doc 05 :309/:561–:562) designs the post-adoption capability path: `capability.added`/`capability.removed`, entity-registry projection, no new table. In core at d22a8a4 it is typed and EMPTY: `EventTypes.CAPABILITY_ADDED` (:303), the `CapabilityAdded` record (integration-api), the persistence category mapping, the `CapabilityPublisher` interface (`publishAdded(EntityId, CapabilityInstance)`) — and ZERO implementations, ZERO projection consumers, ZERO adapter callers (`grep -rn 'implements CapabilityPublisher\|publishAdded(' --include=*.java . | grep -v test` → interface and javadoc hits only). Consequence: every handler and arm we add (IR-18 today; whatever the K-refresh's DEVICE-SET brings) reaches ONLY devices adopted after the deploy; the nine on the bench and every device in a pilot home are frozen at their adoption-day capability set until removed and re-paired — the operator load THE SIMPLER WAY exists to eliminate, and the pilot's upgrade story. Proposal: at boot after the cache load, re-run `EndpointClassifier.classify` on each cached endpoint (the cache persists `deviceTypeId` and `inputClusters` per endpoint — `ZigbeeDeviceCache.java` :631–:636), diff capability ids against the registry's entity, publish `capability.added` for each missing one through a `CapabilityPublisher` implementation, apply it in the registry projection (the AMD-99 single projection-apply path), and apply the reporting row for the newly-covered cluster (the rejoin re-apply path exists). Additive only; removal is a separate policy. One INFO token per addition (`zigbee.capability_extended`). Size: medium (integration-api impl, registry projection, adoption slice, tests). Recommend: sized Tuesday in the strategy pass; queued after IR-61 and before the pilot's freeze. Instrument: synthetic first (a cached descriptor adopted under the eight-handler table, booted under nine); in the field, the next handler after it lands.
**C2 — IR-61 design inputs (cut in v82).** (a) staleness is PER ATTRIBUTE, not per entity: a Hue entity has an event-driven occupancy and an hourly illuminance/temperature; (b) the cadence comes from the READ-BACK values in the recorded `ReportingPostureFact`, never the requested row (the ACK-lies rule, `ReportingConfigurator` :17–:26); (c) postures SLEEPY / READBACK_ONLY / NONE have no read-back → `staleAfter` null with freshness "unknown" (honest) or a learned cadence — the SNZB-06P24 is the live case (z2m `reporting:false` on its illuminance and occupancy, DEVICE-SET :29); (d) the metering rows (0x0B04 max 600 s, 0x0702 max 3600 s) and the new 0x0400 row (3600 s) give three different staleAfter values on one plug/sensor.
