## §0 Verdict

The mechanism is right and faithful to Doc 03 §3.8 (the seam, the chain, `staleAfter = eventTime + threshold` on `state_reported`, `stale` at read); the pre-verification is excellent — all fifteen rows re-verified at the bytes (§D). The one thing wrong is the 180-s figure, and it is wrong in a way that matters for the PRODUCT, not the bench: it sits below the maximum reporting interval the core itself configures on the very attribute it governs, so a well-behaved quiet meter would read stale most of the time (A1). ## §A Fix before dispatch
**A1 — The 180 s contradicts the core's own reporting contract.** `ReportingConfigurator.METERING_ROWS` configures `ActivePower` at min 5 / max 600 s with a 1-W reportable change, and `CurrentSummationDelivered` at 5 / 3600 s (`ReportingConfigurator.java` :77–:110; the javadoc calls the 600-s maximum "the heartbeat that proves a quiet load is a live meter"). Voltage and current are NOT configured by the core; the ≈ 5-s (Gen4) and ≈ 60-s (TR3) cadences the CHAR measured are firmware-default chatter — uncontracted, device-specific. A meter that honors exactly what the core asked for, under a steady load (no 1-W change), is legitimately silent for up to 600 s between ActivePower reports — and with `power_meter` = 180 s it reads `stale: true` for ~70 % of every heartbeat period. On the bench today this cannot happen (both Gen4s and the TR3 chatter; the S31 carries no meter), so the 72-hour run is safe either way; in a pilot home with an unmeasured plug it is a false alarm the operator learns to ignore — the trust cost THE SIMPLER WAY exists to avoid.
The rule that fixes the number and makes every future number derivable: **a capability's declared `expectedReportInterval` is a margin × the maximum interval the core configures for that capability's governing attribute — never an observed cadence.** So `power_meter` = 2 × 600 s = **1200 s**; `energy_meter` = 2 × 3600 s = **7200 s** (mains-powered; the row is contracted; under the MIN rule it never governs beside `power_meter` and governs an energy-only entity). Leave the three measurement sensors and `battery` EMPTY in this WU — their devices are sleepy end devices whose posture may be SLEEPY/READBACK_ONLY (no verified interval), the class where a constant false-flags; they belong to the AMD (C1). Honest consequence for §1's headline: G4-2's wedge (silent from 22:34:31Z) would have read stale at 22:54:31Z — twenty minutes in, not three — and it was power-cycled at 22:47; the true claim is "a wedge surfaces within 20 minutes; before IR-61 it never surfaced". Device-specific tightness (the Gen4 IS a 5-s reporter) is IR-61b's per-entity override or the AMD's read-back value — the layered answer: a conservative capability default, a device-true override. The pre-verification's one missing instrument is exactly this row (`METERING_ROWS` 600/3600) — add it as row 16.
**A2 — T6 cites the wrong sibling.** §2/§3 row 11 point the Coder at `LinkReadIT` (it reads LOG LINES — `zigbee.link_summary`, `zigbee.availability_link`). The sibling that does what T6 needs is `MeasureReadPathIT`: it seeds a `state_reported` carrying `power_w` on the rig's GEN4 (:72, :152, :435) and reads state through `core.stateQueryService().getSnapshot()` (:334) on the shared `TestClock`. Feasibility confirmed: the hardware-free rig already carries GEN4 with 0x0702/0x0B04 and its metering formatting (`ZigbeeHardwareFreeRig.java` :62–:68, :112–:114, :518), and `HomeSynapseCore.stateQueryService()` is public (:1154). ITs run under `check` (build-logic `homesynapse.java-conventions.gradle.kts` :57–:61 — only `bus-soak` is excluded), so §12's criterion holds as written.
**A3 — State the replay-order property and test it.** The registry projection (`HomeSynapseCore.java` :601–:608) and the state projection (:619–:636) are independent bus subscribers replaying concurrently; `awaitRegistryProjectionLive()` (:668) comes AFTER both subscribe. DP-3's fall-through ("a registry miss → the global default → empty") is therefore a live path at every boot: a `state_reported` the state projection replays before the registry has applied that entity's `entity_registered` resolves to null, and stays null until the entity's NEXT report (seconds for a Gen4; up to an hour for a sensor). Self-healing and harmless, but it must be written down in DP-3/DP-4 (the Coder will otherwise "fix" it) and pinned: T2b — registry miss → `staleAfter == null`; the entity registered, a second report → `staleAfter == T2 + threshold`. Also: `EntityState.java`'s staleness javadoc (:56–:61, "derived … from the wall clock") is in §2's read set but not §3's write set — add it as row 13 (javadoc only: "`staleAfter` = event-time + the resolved threshold (IR-61); `stale` at read") or the record's own doc contradicts the projection's.
