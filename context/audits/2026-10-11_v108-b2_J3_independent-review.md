## §2 FINDINGS (most severe first)

**F-1 [BLOCKING] — the per-handler guard turns a store-write failure into "a bad frame".**
The instruction (§4.1): "the dispatch of a resolved frame (the counter increment, the liveness feed, `handleAnnounce`/`handleZcl`, the listener's `onFrame`) runs inside ONE `try/catch (RuntimeException failure)` … and returns (the frame is dropped)".
Evidence: `handleZcl` → `publishStateReported` → `publisher.publishRoot(draft)` `ZclIngestionUnit.java:880` (only `SequenceConflictException` is caught, `:882`). `publishRoot` is `SqliteEventStore.appendOnWriteThread` `:409`–`:425`: the write coordinator "wraps checked exceptions in a RuntimeException whose cause is the checked exception" (`:416`–`:417`) and rethrows it (`:424`); `DatabaseExecutor.java:381,:384` throw `IllegalStateException` once shut down. `listener.onFrame` (`ZigbeeIntegrationAdapter.java:1848`–`:1854`) feeds `availabilityTracker.recordFrame` whose transition publishes through `availabilityPublisher` (`:526`) — the same path. Today a disk-full / `SQLITE_IOERR` / executor-down publish ends `run()` and the supervisor restarts (loud); after T-A as written it is ONE WARN per `(device, cluster)` then DEBUG — every `state_reported` and `availability_changed` silently dropped (the tracker's memory already flipped), the cycle "healthy", the three-strike arm never reached.
THE EDIT (add as §4.1's fifth bullet and §9's first bullet): "**The guards are for the FRAME, never the STORE.** A `RuntimeException` whose cause chain (`getCause()`, walked) carries a `java.sql.SQLException` or a `java.io.IOException` — the write coordinator's wrapping form (`SqliteEventStore.appendOnWriteThread` `:416`–`:424`) — is the store or the disk failing, not the frame: BOTH guards RETHROW it unchanged (no line, no count); it reaches the cycle guard (§4.2), which counts it; the third strike restarts the adapter — the fail-fast the design names." And add to §7 T-A: "**Z-7** the rig's `publisher` throws `new RuntimeException("write failed", new SQLException("disk I/O error"))` from `publishRoot` on a resolved HA report: `processCycle()` PROPAGATES it; `frameFailures() == 0`; no `zigbee.ingestion_handler_failed` line. ## §3 THE DESIGN READ (T-A)
The two-layer rule (frame survives, cycle three-strikes) is the right shape; the derivation from `KEEPALIVE_MISS_LIMIT` is sound as a liveness verdict: the counter resets on a clean cycle, the typed arms stay on the watchdog, the same object is rethrown so `run()`'s bare-`instanceof` classifier is unchanged. What I would change is the guard's BOUNDARY: it sits above `publishRoot` and catches the store under the handler (F-1) — the cause-chain rethrow fixes that with one predicate and no seam, and gives the cycle arm its only realistic production input (a failing store fails every cycle → three strikes → restart: today's outcome, 150 ms later, with two lines that name it). Memory: `(frameId, class)` is bounded by construction; `(device, cluster)` is gated on resolved senders (`:643`–`:656`), ceiling registry size × 65,536 — a spoofed resolved nwk can grow one device's set to ~2 MB of boxed ints, the exposure `unscaledNamed` (`:263`) already carries. Acceptable; a 64-entry per-device cap (the 65th falls to DEBUG) is the cheap bound if wanted. IR-119's close line is clean: one clock read, `elapsed=` beside `duration=`, no bench collision (F-10), and the shutdown and superseded paths both pass `closeWindow` (`:1326`) so "one line per row" holds.
