## §1 What this implements
Three rows, one seam, no new event type and no schema version:
1. **The per-device frame counter (IR-20 row (b); `FRAME: a`):** a per-IEEE `LongAdder` incremented in `ZclIngestionUnit.route()` after network-address resolution (`ZclIngestionUnit.java:576–:578`, the resolved branch only; unknown senders keep their existing `warn` and count nothing) and one INFO summary line per device on a ten-minute gate — never a line per frame.
2. **The link reading on every frame, carried on every silence:** `EzspIncomingMessage` already parses `lastHopLqi` (u8) and `lastHopRssi` (s8) (`EzspIncomingMessage.java:14, :36–:37`); `route()` hands the resolved device to `listener.onFrame(device)` (`:578`; the announce path `:589`) and the reading is dropped there (IR-16). LINK-READ threads it: `Listener.onFrame(IEEEAddress device, LinkReading link)` → `ZigbeeIntegrationAdapter.onFrame` (`:1234–:1245`) → `AvailabilityTracker.recordFrame(device, now, link)` (`AvailabilityTracker.java:36`; `StandardAvailabilityTracker.java:150`) → `DeviceState.lastLink` + `lastLinkAt` (`:90–:98`). The silence transition (`transition()` `:282–:317`, reason `SILENCE_TIMEOUT` from `evaluateTimeouts()` `:228–:261`) logs the last reading on its existing line: `zigbee.availability_changed: device={} available={} reason={} last_lqi={} last_rssi_dbm={} last_link_at={} frames_since_summary={}`.
3. **The sampling rule, as a constant with its reason:** the reading is kept in memory on every frame (two ints and an `Instant` per device; no allocation on the hot path beyond the record the ingestion unit already builds) and WRITTEN only at a transition and on the ten-minute summary line. The store never sees a per-frame write; `LINK_SUMMARY_PERIOD = Duration.ofMinutes(10)` lives beside the tracker's timeout constants (`StandardAvailabilityTracker.java:52–:54`) with a Javadoc that states the rule and its basis (R-5B's frame block counts per device are the number the rule is derived from; the run's fleet is ≤ ten devices; ten minutes gives ≤ 60 lines per device per ten hours).

Out of this unit (§11, and IR-45 opened by the hub): the reading on the read surface (`/api/v1/entities/{entityId}/state` `data.attributes.lqi.value` — the `link-quality.yaml` WIRE PIN stays PENDING; `constants.yaml` keeps `link-read: false`), and the reading inside `AvailabilityChangedEvent` (`core/event-model/.../AvailabilityChangedEvent.java:16–:18` is `(previousStatus, newStatus)`; Doc 01 §"payload evolution" makes an additive field a v2 with an upcaster — a unit of its own, LINK-READ-2, after Thursday).

**The ruling — the wire domain in the type, a total seam in `route()`, the plausibility as an instrument (option 4; it takes option 1's bounds and option 2's posture, and rejects option 2's `≤ 0`):**
1. **`LinkReading(int lqi, int rssiDbm)`** — the compact constructor asserts the WIRE domain, `0 ≤ lqi ≤ 255` and `−128 ≤ rssiDbm ≤ 127`, thrown, never clamped. A type carries the domain its producer can legally produce; a throw here is a programming error (a caller that did not decode s8/u8), which T6 pins at build time.
2. **The total factory:** `static Optional<LinkReading> fromWire(int lqi, int rssi)` — empty when the pair is outside the wire domain; never throws. `route()` builds the reading through it, never through the constructor.
3. **The seam is total and liveness never depends on the reading:** `Listener.onFrame(IEEEAddress device, Optional<LinkReading> link)` and `AvailabilityTracker.recordFrame(IEEEAddress device, Instant timestamp, Optional<LinkReading> link)`. On an empty reading the frame still counts (row 2's counter), `onFrame` still fires (M9.6-AVAIL DP-3: every device-originated RX is liveness), `lastSeen` still updates, and the tracker keeps its prior `lastLink`/`lastLinkAt`. The `Optional` on the two seam signatures is deliberate: the type states that the reading is optional at this seam and the liveness call is not. (If `java-patterns.md` forbids `Optional` parameters, the fallback is the overload pair `onFrame(device)` / `onFrame(device, link)` with the same semantics; the return names which was used and why.)
4. **The instrument, ONE WARN per device per process** (the once-per-device guard already in this file: `unscaledNamed.computeIfAbsent(...).add(...)` around `zigbee.metering_unscaled`, `ZclIngestionUnit.java:857–:862` — the same shape): `zigbee.link_reading_suspect: device={} lqi_raw={} rssi_raw={} reason={}` with `reason=out_of_wire_domain` (the reading DROPPED — it cannot be constructed) or `reason=positive_rssi` (an s8 in 1..127 — legal, physically implausible from an NCP, the reading KEPT and the line flags it).
