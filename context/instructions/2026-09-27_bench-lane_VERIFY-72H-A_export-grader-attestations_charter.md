## §1 The decisions (settled; the lane implements and raises a fork only with evidence)
1. **The export is a directory, not a tarball first:** `bench.sh export <label> <from-utc> <to-utc>` → `~/hs-bench/exports/<label>-<UTC stamp %Y%m%dT%H%M%SZ>/` with `events.jsonl` (one JSON object per row of `SELECT global_position, event_id, event_type, schema_version, ingest_time, event_time, subject_ref, subject_type, correlation_id, causation_id, event_category, payload, payload_iv, dek_ref FROM events WHERE ingest_time BETWEEN ? AND ? ORDER BY global_position` — `payload` emitted as UTF-8 JSON when `payload_iv IS NULL` and the bytes decode, else as `{"opaque": "<base64>"}`; nothing decrypted, ever), `app-log.jsonl` (every `bench-*.log` line whose wall-clock falls in the window, each given its DATE from the log file's own name `bench-%F-%H%M%S.log` and a rollover rule: a time-only stamp earlier than the previous line's by > 12 h advances the date by one), `window.json` (from/to, the store's min/max `global_position` and row count in the window, the db file's byte size, the `bench.sh` and engine shas), `MANIFEST.txt` (sha256 per file, GNU `sha256sum` form). `bench.sh bundle`-style `tar` of the directory is a second step, on request, never the default — the 7-day DIAGNOSTIC purge is the deadline that matters (`RetentionPolicy.SOURCE_DEFAULT = (7, 90, 365)`), so the export runs within 7 days of the window's end; the grader reads the directory.
2. **The grader is offline and pure:** `bench.sh verify <export-dir>` → `tools/verify72h/grader.py` reads `events.jsonl` (+ `app-log.jsonl` for (vii)'s counter tokens) and writes `verdict.json` + `report.md` into the export directory. Exit 0 on PASS, 2 on FAIL/FLAGGED, 3 on CANNOT-GRADE. Its output vocabulary is FROZEN to the runner's own (`constants.yaml` `runs-outcomes:` — read it and pin the line) plus `CANNOT-GRADE`; any other word is a defect the selftest catches (invariant (vi)).
3. **The seven invariants, pinned to source (Lane D's item 7):** the tokens are `EventTypes.java` at `e96dce8` — `command_issued` :56 · `command_dispatched` :59 · `command_result` :62 · `command_confirmation_timed_out` :65 · `state_reported` :70 · `state_confirmed` :79 · `automation_triggered` :132 · `automation_completed` :135 · `automation_run_skipped` :163 · `automation_run_cancelled` :166. **`superseded` is NOT an event type:** it is an OUTCOME string inside a `command_result` payload (`CommandResultEvent.java:35–:40`: `targetEntityRef`, `commandType`, `outcome`, `failureReason`; `StandardExplanationService.java:135` `OUTCOME_SUPERSEDED = "superseded"`, beside `acknowledged` and `unconfirmed` :146). ## §4 The three attestations — pre-registered as FALSIFIABLE gates (the review's C4 form: the observable · the instrument · the pre-registered value · the reading that FAILS it)
- **A1 — a key at boot → red.** Observable: `permit_join_opened` in the export (an event type; the lane pins its constant at `EventTypes.java` by grep) and in `app-log.jsonl`. Instrument: the grader's count over the window; the nightly's BH-2 already reds a boot on it. Pre-registered: **0** in a window with no card-ordered pairing. FAILS on: any count > 0 — and the finding is then the KEY's presence at boot (the `key-lines` read), never the grader.
- **A2 — a silent metered entity → `stale:true` + VOID (IR-61 / METER-3; C4).** Observable: every entity read the runner captured in the window (`api-captures.json` bodies: `stale`, `staleAfter`, `availability`, `lastReported`) against the export's last `state_reported` for that entity before the read. Instrument: the grader joins the two. Pre-registered, with THE DERIVATION RULE's thresholds (`power_meter` 1200 s; `energy_meter` 7200 s; an entity's threshold = the smallest of its capabilities): **ZERO reads with `stale:true` while the store shows a `state_reported` within 1200 s** (a false stale = FAIL); **ZERO reads with `stale:false` while the store shows silence ≥ 1200 s + 60 s** (a missed stale = FAIL; the 60 s is the read path's granularity, pinned by the lane from the projection's clock). `availability` is read BESIDE `stale` and never substituted for it (Doc 03 §3.8: independent signals). The bench's own `fresh_within_s` (30/180/30) stays the REP gate — a different question (DP-6). Until IR-61 is on the bench card the export carries `staleAfter: null` everywhere and A2 reads NOT-APPLICABLE (the grader says so; it never PASSes A2 on nulls).
- **A3 — a stale witness → VOID (METER-3).** Observable: every REP receipt in the window's bundles (`witness_age_s`, `fresh_within_s`, `verdict`). Instrument: the grader's consistency check. Pre-registered: **ZERO receipts with verdict `within`/`outside` whose `witness_age_s > fresh_within_s`**, and ZERO with a missing witness and a non-VOID verdict. FAILS on: any — a pass on a stale witness is the grader's own defect.
