## §4 Technical specification
**Row 1 — the handler.** `static final int CLUSTER_ID = 0x0400; ATTRIBUTE_MEASURED_VALUE = 0x0000; INVALID_MEASURED_VALUE = 0xFFFF (long); TOO_LOW_TO_MEASURE = 0 (long)`. `normalize(endpoint, clusterId, attributes)`: `Object v = attributes.get(0x0000)`; if `v instanceof Long raw && raw >= 0`: `raw == 0xFFFF` → `List.of()` (the invalid sentinel never observes — F-9); `raw == 0` → `illuminance_lux 0.0`, raw `"0"` (ZCL8 §4.2.2.2.1: "0x0000 indicates that the illuminance is too low to be measured" — the device's own statement of darkness; emitting nothing would leave the last daylight value standing after dusk, which is the lie F-9 forbids — DP-1, pushback welcome); else `lux = Math.pow(10.0, (raw - 1) / 10_000.0)` rounded to one decimal (`Math.round(lux * 10.0) / 10.0` — for the reader, not for parity: the siblings' `/100.0` is two-decimal by construction, while the dashboard prints a NUMBER as `String(v)` (`web-ui/dashboard/src/lib/format.ts` :426–:433), so an unrounded 316.22776601683796 would reach the screen; the raw is retained and the bench re-derives; B1), emitted as `new NormalizedAttribute("illuminance_lux", <double>, "lux", String.valueOf(raw), "log10x10000+1")` — the fifth field is `rawProtocolUnit` (`NormalizedAttribute.java` :28–:33; the meters write `"mult=1 div=1"` there — `ElectricalMeasurementHandler` :30; the humidity handler writes `null`) — write the dialect string so a reader of the bundle can re-derive lux from the raw. Anything else → `List.of()`. Worked values (ZCL8 §4.2.2.2.1, MeasuredValue = 10,000 × log10(lux) + 1): 1 → 1.0 · 10,001 → 10.0 · 20,001 → 100.0 · 25,001 → 316.2 · 30,001 → 1000.0 · 65,534 → 3,575,197.2 (the largest valid) — re-derive each independently before pinning (law #4). Thread-safe, stateless, javadoc in the humidity handler's form.
**Row 2 — the factory.** `handlers.put(IlluminanceMeasurementHandler.CLUSTER_ID, new IlluminanceMeasurementHandler(device, clock));` after the humidity line; the counts in the class javadoc and `forDevice`'s.
**Row 3 — the classifier.** After `classified = withMeters(classified, descriptor);` add `classified = withMeasurements(classified, descriptor);` — a private static method in `withMeters`' exact shape (:180–:203), driven by a three-row table `{0x0400 → StandardCapabilities.illuminanceMeasurement(), 0x0402 → StandardCapabilities.temperatureMeasurement(), 0x0405 → StandardCapabilities.humidityMeasurement()}` (three `if`s or a `List<Map.Entry<Integer, Capability>>` — the Coder's call): for each row whose cluster id is in `descriptor.inputClusters()` AND whose capability id is not already on the classification (`anyMatch` on the instances' capability id), append the capability; if no row applies, return `classified` unchanged; if `classified` is empty and at least one row applies, return `new Classification(EntityType.SENSOR, caps)` (`EntityType` :75 names temperature, humidity and illuminance among the sensor kinds). The device type stays a hint, never the key (the R2/IR-24 comment applies verbatim). What the tests pin: the 0x0302 arm's output is byte-identical (its capabilities are already present, so nothing is appended — `EndpointClassifierTest` :126 and :140 stay green); the 0x0107 arm gains illuminance AND temperature when their clusters are present (the Hue shape — T8); the fallback needs NO new row — `[0x0000, 0x0001, 0x0400]` → DP-7's SENSOR + battery, illuminance appended (T9); `[0x0000, 0x0001, 0x0402]` → SENSOR + battery + temperature (T8b); `[0x0000, 0x0400]` alone → SENSOR + illuminance; `[0x0000, 0x0001]` alone → SENSOR + battery only (DP-7 preserved); `[0x0000, 0x0003]` → still empty (:111). No `hasIlluminance` flag; the double-add hazard of the first cut does not arise.
**Row 4 — the reporting default.** `Map.entry(0x0400, new DefaultRow(0x0000, 0x21, 10, 3600, 1000))` — uint16 (0x21), min 10 s, max 3600 s (the row family's values), reportable change 1,000 log-units (= a factor of 10^0.1 ≈ 1.26 in lux; the smallest change a household automation would act on; the temperature row's 10 = 0.1 °C and humidity's 100 = 1 %RH are the siblings). The attempt is recorded as a device fact whatever the device answers (the class javadoc's rule) — so an SNZB-06P24 that refuses configure_reporting on 0x0400 records that fact and nothing breaks (DEVICE-SET :72's open question is answered by the record, not assumed here).

## §9 What to watch out for
- **Tests must inject `Clock`.** Do NOT use `Clock.systemUTC()`, `Instant.now()`, `System.nanoTime()`, or `System.currentTimeMillis()` in this module's test code. Use `Clock.fixed(Instant.parse("2026-01-01T00:00:00Z"), ZoneOffset.UTC)` injected via constructor/`@BeforeEach` (the module's tests use `TestClock.createDefault()` — follow them). **Enforcement reach:** `NO_DIRECT_TIME_ACCESS` runs from `com.homesynapse.app`'s test classpath, so it mechanically catches PRODUCTION code in every non-whitelisted module (plus app's own tests) — it does **not** scan this module's test source set. Clock-injection here is a self-enforced project convention that PM review, not `./gradlew check`, enforces.
- Uint16 arrives UNSIGNED as a `Long` (the humidity handler's comment): 0xFFFF is 65535L; never compare against a negative sentinel.
- The double: pin with `isEqualTo(316.2)` after the one-decimal rounding, never `isCloseTo` on an unrounded value — the rounding IS the contract.
- No fallback row: `withMeasurements` runs after every arm, including `fallback`'s DP-7 row and its `Optional.empty()`; a 0x0400 + 0x0406 endpoint still classifies BINARY_SENSOR on the occupancy row and gains illuminance after it (T8 pins BINARY_SENSOR).
