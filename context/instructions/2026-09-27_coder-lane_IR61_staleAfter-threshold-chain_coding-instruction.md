## §1 What this implements
Doc 03 §3.8 (AMD-11; `homesynapse-core-docs/design/03-state-store-and-state-projection.md` :399–:434) designs staleness as a per-entity threshold resolved from three sources in priority order — (1) a per-entity override (§9 config), (2) a capability-based default (`expected_report_interval` declared by the capability schema), (3) a global default — with `staleAfter = event.eventTime() + resolvedThreshold` recomputed on every `state_reported`, `stale` derived at read time, and `staleAfter` null (never stale) when no source applies. AMD-53 §2.2 records that "threshold resolution is not yet wired" (`AMD-53_Timestamp_Model_Unifier_Event_Time_Activity_Timestamps.md` :78) and excludes `staleAfter`/`stale` from the event-time rule (AMD-53-INV-02). At `e96dce8` the projection carries `prior.staleAfter()` on every branch and seeds null (`StateProjection.java` :810–:819, :1004–:1016 — `grep -n staleAfter` = 9 hits), the read path already derives `stale` (`MaterializedStateQueryService.java` :212–:231), the checkpoint serializer persists it (`git grep -n staleAfter -- core/persistence/src/main` = 8 hits) and the wire carries both fields (`contract.ts` :273–:274) — every metered entity has read `staleAfter: null`, `stale: false` forever (the CHAR bundle's nine bodies; G4-2's 12.5-min silence read fresh, the v81 b4/b6 audits). This WU: (a) `StalenessThresholdResolver` (state-store) — the seam the projection consults; (b) `Capability.expectedReportInterval()` (device-model) — source 2 declared where Doc 03 says it lives, with `PowerMeter` declaring 1200 s and `EnergyMeter` 7200 s by THE DERIVATION RULE (DP-6: 2 × the maximum interval the core configures for the capability's governing attribute — never an observed cadence); (c) `RegistryStalenessResolver` (state-store) — sources 1 → 2 → 3, indexing the capability catalog itself, with the entity's threshold the SMALLEST declared interval among its capabilities (fresh means the device said ANYTHING within the shortest interval any of its capabilities declared — the sentence the per-attribute AMD will later replace); (d) the projection's `state_reported` branch writes `staleAfter = stamp + threshold` (or null) and `stale = false`; (e) the composition root wires the resolver with the catalog, an empty override map and no global default (the §9 config keys are IR-61b — §11); (f) tests first, including one lifecycle IT that reads `stale: true` through the real read path after the clock passes the threshold. ## §4 Technical specification
**DP-1 — the seam.** `StalenessThresholdResolver` lives in `com.homesynapse.state` (exported; it names `EntityId` from `com.homesynapse.device`, which state-store already `requires transitive` — no `-Xlint:exports` trip) and `java.time.Duration`. `none()` is the default for every existing construction path so that every existing test and the IT harnesses stay byte-identical.
**DP-2 — source 2 lives on the capability.** Doc 03 §3.8 says the capability schema "may declare an `expected_report_interval`"; the Java home for a schema-level declaration is the sealed `Capability` interface — a `default` method so the 17 permitted records compile untouched (`grep -c 'implements Capability' core/device-model/src/main/java/com/homesynapse/device/*.java` = 17) — with `PowerMeter` (1200 s) and `EnergyMeter` (7200 s) overriding it. `power_measurement`, the three measurement sensors, the binary sensors, the actuators: EMPTY in this WU (the sensors report on change or at a 3600 s max interval, and sleepy postures make any constant a guess — the per-attribute AMD decides them with the read-back value; §10).
**DP-3 — the resolver.** `CapabilityInstance` carries the capability's ID, not the object (`CapabilityInstance.java` :33–:42), so the resolver indexes `capabilityId → expectedReportInterval()` from the catalog it is handed (`StandardCapabilities.all()`, :68–:86 — 16 entries; `CustomCapability` is not among them and contributes nothing); an entity's threshold is the MINIMUM of its capabilities' declared intervals (a plug with `power_meter` 1200 s and `energy_meter` 7200 s → 1200 s; an energy-only entity → 7200 s; the rationale: any `state_reported` on the entity resets `staleAfter`, so the most frequently reporting capability sets the honest expectation — "fresh means the device said anything within the shortest interval any of its capabilities declared", the sentence the per-attribute AMD will replace). Sources in order: `overrides.get(entityId)` → the capability minimum → `globalDefault` → `Optional.empty()`. **The replay-order property (state it in the javadoc; pin it as T2b; do not "fix" it):** the registry projection and the state projection are independent bus subscribers replaying concurrently (`HomeSynapseCore` :601–:608, :619–:636; `awaitRegistryProjectionLive()` :668 comes after both subscribe), so a `state_reported` replayed BEFORE its entity's registration resolves through the registry miss → the global default → null, and stays null until that entity's NEXT report (seconds for a plug; up to an hour for a sensor). Harmless and self-healing; a pure function of the log order; `InMemoryEntityRegistry` is copy-on-write under a `ReentrantLock` (:37, :44), so the projection thread's lookups during registry replay are safe.
**DP-4 — the projection.** Only the `state_reported` branch changes: `staleAfter` from the resolver on the EVENT-TIME stamp (`stamp` at :805 — AMD-53-INV-02: `staleAfter` is event-time-derived and deterministic; a target for real-time comparison), `stale = false` (the report clears staleness — Doc 03 §3.8 "resets `stale` to `false`, recomputes `staleAfter`"). REPLAY and LIVE alike (`staleAfter` must be current after replay — §3.8). Every other branch keeps `prior.staleAfter()`, `prior.stale()`. The scan and the two events are OUT (IR-61b); the read path's lazy derivation is the wire's truth for this WU.
**DP-5 — the composition root.** `HomeSynapseCore` :590 builds `entityRegistry` before :619 builds the projection; the resolver is built between them. `overrides = Map.of()` and `globalDefault = Optional.empty()` until IR-61b lands the §9 keys (`default_staleness_threshold`, `staleness_overrides` — Doc 03 :747, :754; `git grep -n 'staleness_overrides\|default_staleness_threshold' -- config/ app/ = 0 hits` at `e96dce8`).
**DP-6 — THE DERIVATION RULE and the numbers.** A capability's declared interval is a MARGIN × the maximum interval the core's own reporting contract configures for that capability's governing attribute — never an observed cadence. The core configures `ActivePower` at 5–600 s with a 1-W change threshold and `CurrentSummationDelivered` at 5–3600 s (`ReportingConfigurator.METERING_ROWS`, :100–:115; its javadoc: the 600-s maximum "is the heartbeat that proves a quiet load is a live meter"); voltage and current are NOT configured by the core — the ≈ 5-s Gen4 and ≈ 60-s TR3 cadences the CHAR measured are firmware chatter, uncontracted and device-specific. A plug that honors exactly what the core asked for is legitimately silent for up to 600 s under a steady load; a 180-s default would have read it `stale: true` for ≈ 70 % of every heartbeat period — a false alarm the bench cannot show (every bench plug chatters) and a pilot home's operator would learn to ignore. So: `power_meter` = 2 × 600 = **1200 s**; `energy_meter` = 2 × 3600 = **7200 s** (under the MIN rule it governs energy-only entities). The three measurement sensors and battery declare NOTHING in this WU. The honest headline: a wedge surfaces within 20 minutes (G4-2's 22:34:31Z silence → `stale: true` at 22:54:31Z; it was power-cycled at 12.5 min); before IR-61 it never surfaced. The METER-3 windows 30/180/30 s are the BENCH's per-plug freshness for a single REP — a different question. Device-true tightness (the Gen4 IS a 5-s reporter) is IR-61b's override or the AMD's read-back value: conservative capability default, device-true override. The margin 2 is the design number; pushback with a measurement is welcome.
