## §1 What this implements
1. **The §9 keys.** Doc 03 §9 (`homesynapse-core-docs/design/03-state-store-and-state-projection.md` :740–:757) places a `staleness:` block under the `state_store:` section of `homesynapse.yaml`: `default_staleness_threshold` (a duration or `null` = never stale), `staleness_overrides` (a map keyed by entity ULID string → duration), `scan_interval_seconds` (the passive scanner — NOT implemented: IR-61 evaluates `stale` lazily on the read path, Doc 03 §3.8's carve-out; the key is accepted and has no effect, said so in the javadoc). At `1f1d1e0` the composition root passes `Map.of(), Optional.empty()` to `RegistryStalenessResolver` with the comment "The §9 keys … are IR-61b" (`HomeSynapseCore.java` :621–:627). This WU reads the block from the loaded configuration model (`configurationService.getCurrentModel().rawMap()`, the way `automationSection` does at :703/:1503), parses it into a `StalenessConfig` record and hands its two values to the resolver. **Duration form: ISO-8601 (`PT20M`, `PT2H`), parsed with `Duration.parse` exactly as the automation section's durations are (`AutomationDefinitionLoader.parseIso8601` :390)** — one duration grammar in one file; Doc 03 §9's example strings (`"10m"`, `"1h"`) are corrected on the docs card (IR-81's sibling; D-v84-13). A malformed value or an unparseable ULID key throws `IllegalArgumentException` naming the full key path (`state_store.staleness.staleness_overrides[<key>]`) — Configuration is a FATAL subsystem (Doc 12 §4); a boot on a bad value stops with the key named, never runs with a silent default.
2. **The schema fragment.** `StandardSchemaRegistry` sets `additionalProperties: false` at the root (:168), so an unregistered `state_store:` section is an unknown property (WARNING) at every boot. The WU adds `StateStoreSchema` (`SCHEMA_SECTION = "state_store"`, `SCHEMA_JSON` — a static JSON string in the state-store module, the `AutomationSchema` form at `core/automation/.../AutomationSchema.java` :34–:37; no dependency on the config module) and registers it beside the automation schema (`HomeSynapseCore.java` :528). Inside `staleness` the three keys are typed (`default_staleness_threshold`: string|null; `staleness_overrides`: object of string values; `scan_interval_seconds`: integer 5–300) and `additionalProperties: false`; the `state_store` section itself keeps `additionalProperties: true` — Doc 03 §9 documents other `state_store` keys this codebase does not read yet, and this WU does not turn them into warnings.
3. **The ordering gate (IR-83).** At `1f1d1e0` the registry projection subscribes at :606–:610 and the state projection at :647; both replay from position 0 on their own bus threads; the root waits for both only at :677–:678. A `state_reported` the state projection replays before the registry projection has replayed that entity's registration resolves no threshold (the entity is unknown to the resolver) and carries `staleAfter = null` until the next live report — the PATTERN BC5 read (TR3 null 8 s before its first post-boot report; D-v83-25 ruled that reading confounded, the gate is ordered regardless). The fix: **`awaitRegistryProjectionLive()` is called BEFORE `eventBus.subscribeRuntime(projectionInfo, stateProjection)`** — the registry is at the log head before the state projection reads its first event; the existing pair at :677–:678 stays (the registry call returns on its first poll). The cost: the two replays run in series instead of concurrently — the registry replay is registrations and removals only (hundreds of events), so boot-to-LIVE grows by that replay's time, not the log's.
4. **The observable already exists — no new log line.** The registry projection announces its catch-up (`RegistryProjectionSubscriber.java` :107 `LOG.info("registry.projection_live: devices={} entities={} position={}", …)`, asserted by `ProcessRestartIdentityIT` :136) and so does the state projection (`StateProjection.java` :572–:591 `onCaughtUp()` → :588 `log.info("StateProjection {} caught up at position {}; projection.replay.duration_ms={} events_replayed={}", …)`, under `com.homesynapse.state`). D-v83-25's premise that the state projection logs no LIVE line was wrong at the bytes (the independent review, E1); this WU adds NO line — the gate's observable is the ORDER of the two existing lines in the app log (registry first), which PI-PROBE-2 and every future boot read. The bus fires `onCaughtUp()` AFTER it flips the subscriber to LIVE (`TransitionCoordinator.java` :142 `setMode(LIVE)` … :156 `onCaughtUp()`), so the registry's line is written on the registry's virtual thread moments after the gate on the main thread has already passed — T3's order assertion rests on the state projection's own subscribe-replay-catch-up taking longer than those fourteen lines; see §7 T3 and §9.9.

## §9 What to watch out for
1. The configuration model's `rawMap()` gives `Map<String, Object>` with YAML-typed values — a `null` YAML scalar arrives as a Java `null` and a bare `20m` would be a String; `PT20M` is a String; an unquoted `null` key value must not throw.
2. The schema registration must precede `configurationService.load()` (:531) — Doc 06 §3.2; the automation schema's line (:528) is the place.
3. `EntityId.parse(String)` (`EntityId.java` :56) is the direct form; it throws on a bad length, an invalid character (`Ulid.java` :144) or an overflowing first character (:86–:98); wrap it into the path-naming exception.
4. `awaitRegistryProjectionLive()` before :647 runs while the state projection is not yet subscribed — the registry projection's mode is read from the bus (`registryProjectionMode()`), not from the state projection; nothing in the method depends on the state subscriber.
5. The 30-s timeout of the awaits is unchanged; on a large log the state replay already took most of the budget concurrently — in series the registry replay adds its own time first. Report the boot time of the IT before and after (the fixture's log has the stamps) as an [INFO] deviation; do not tune the timeout.
6. `ListAppender` captures the `com.homesynapse` logger tree — `LOG` at :188 is `HomeSynapseCore`'s logger under that tree; assert on the formatted message, not the pattern layout.
7. `-Werror`: an `Optional` record component draws no lint; an unused import does.
8. LOCK-1's two test files sit uncommitted in the tree when you start: leave them; your porcelain lists them under LOCK-1's heading in the return, not IR-61b's.
9. The order assertion of T3 (registry's line before the state's) is deterministic only because the state projection's subscribe → replay → catch-up on the main-thread side takes far longer than the registry VT's fourteen lines between `setMode(LIVE)` (:142) and `onCaughtUp()` (:156). If T3 ever flakes in CI, the pin becomes T3b's shape and the flake is a register row — say so in §3 of the return if you see it once locally.
10. The plug's entity ULID is minted at adoption, after the first boot (`RealCoreFixture.java` :258–:274; `Ulid.java` :14 — 80 random bits), so an override for it cannot be in the FIRST `homesynapse.yaml`; T2 and T3b rewrite the file and `restart` (see §7).
