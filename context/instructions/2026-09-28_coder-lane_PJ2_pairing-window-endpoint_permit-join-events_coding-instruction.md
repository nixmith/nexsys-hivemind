## §1 What this implements
1. **The seam (DP-PJ2-1).** An OPTIONAL capability interface `PairingWindowControl` in `integration-api` — the adapter that can open a window implements it; `IntegrationAdapter` (AMD-55's surface) is untouched. `IntegrationSupervisor` gains `openPairingWindow(IntegrationId, PairingWindowRequest)`, which runs the open on THAT adapter's single-threaded command executor (`StandardIntegrationSupervisor.routeTarget(id)` :363–:377 — the same thread the M9.4a command write path uses; never the Javalin thread). `rest-api` owns a port `PairingWindowPort` written in JDK + platform types only, so rest-api takes NO new module edge (its module-info calls it "the public-facing HTTP interface"; the M7.5a Object-erased installer form stands); `lifecycle` bridges the port to the supervisor.
2. **The events (DP-PJ2-2).** `EventTypes.PERMIT_JOIN_OPENED = "permit_join_opened"` and `PERMIT_JOIN_CLOSED = "permit_join_closed"` (the log token BH-2 already forbids in boot-health — one word for the log line, the event type and the bench's grep); two records in `integration-api` under a new sealed `PairingWindowEvent extends DomainEvent`; both APPENDED to `IntegrationEvents.LIFECYCLE_EVENT_CLASSES` (:53–:64) — every aggregation site (`HomeSynapseCore.java` :549, `AllEventClasses.java` :43, the two replay tests, the IT harness) picks them up with no edit. Published by the ADAPTER through `context.eventPublisher().publishRoot(new EventDraft(type, 1, clock.instant(), SubjectRef.integration(id), EventPriority.NORMAL, EventOrigin.INTEGRATION, payload, null, null))` — the :1175–:1179 form; the REST endpoint publishes NOTHING (`REST_ENDPOINTS_NO_EVENT_PUBLISHING`, `HomeSynapseArchRules.java` :306–:312, its allowlist unchanged).
3. **The open (DP-PJ2-3).** `ZigbeeIntegrationAdapter implements PairingWindowControl`: `openPairingWindow(request)` validates nothing the record has not (the record validates 1–254; the API REJECTS out-of-range — the clamp at :908–:909 was the key's courtesy and goes with it), calls `protocol.enablePreconfiguredKeyJoins()` (:914 — §A.1: the policy, then the transient key; `ZigbeeTrustCenterJoinTest` :132–:138 pins the frame order SET_POLICY ×2 → IMPORT_TRANSIENT_KEY → PERMIT_JOINING, and :346–:356 pins that a NAK'd enablement THROWS with no permit frame) THEN `protocol.permitJoin(duration)` (:915) — the same two calls in the same order as today; only after both are accepted: `permitJoinDeadline = clock.instant().plusSeconds(duration)` (:916's form), the window stored by CAS (§4), `permitJoinEpoch` bumped, `PermitJoinOpened` published, `zigbee.permit_join_opened: duration={}s reason={} actor={}` logged (the token unchanged; two fields added), the `PairingWindow` returned. The two `HashSet`s cleared at :920–:921 today (`rejoinWindowClosedNoted`, `rejoinLookupAttempted`) are RUN-THREAD CONFINED (:246–:257) — the open, now on the command executor, does NOT touch them: it bumps the epoch, and `runCycleOnce()` (:572) clears both at its TOP when its run-thread `seenPermitJoinEpoch` differs from `permitJoinEpoch` (the F-R4-1 semantics preserved: a fresh admission epoch clears the notes before the cycle's ingestion; `ZigbeeInterviewOnRejoinTest` T7 :706–:765 stays green with that order). An open while a window is open: the prior window CLOSES first with ONE event — `superseded` if its `closesAt` is still ahead, `elapsed` (`closedAt = closesAt`) if the cycle had not yet observed its end — then the new one opens.
4. **The close (DP-PJ2-4).** `closeWindowIfElapsed()` runs at the END of `runCycleOnce()` (:572–:580 — the one cycle body both `productionLoop()` :938–:980 and the driven mode's `deliverAndCycle` :193 share; `productionLoop()` itself is a `while (stopSignal…)` loop with no single-cycle entry, :939): `w = currentWindow.get(); if (w != null && !clock.instant().isBefore(w.closesAt()))` → `currentWindow.compareAndSet(w, null)` wins → publish `PermitJoinClosed(elapsed, openedAt = w.opensAt(), closedAt = w.closesAt())` (the window's own end, not the cycle's clock — the cycle lags by up to 50 ms) and null the deadline; a lost CAS publishes nothing. The transport reopen at :1023 (DP-B5) → if `currentWindow.getAndSet(null)` returns a window, `PermitJoinClosed(transport_reopened, closedAt = now)` before the deadline's null. `close()` (:505) → the same with `shutdown`. Three closers on three threads (the executor's supersede, the run thread's cycle, the supervisor's close thread :804) — the `AtomicReference` CAS is MANDATORY, not a preference (§4).
5. **The key (DP-PJ2-5).** The start-path call at :500 becomes `warnIfPermitJoinKeyConfigured();` — a package-private method (so `ZigbeePermitJoinTest`, whose `bootProduction` :265–:283 drives the ladder to `awaitNetworkUp()` and never `run()`, can call it directly — :500 is unreachable from that fixture): `context.configAccess().getInt(PERMIT_JOIN_DURATION_KEY)` (`Optional<Integer>`, the :902–:906 form) present → ONE `log.warn("zigbee.permit_join_key_ignored: configured={}s — the window opens only by POST /api/v1/integrations/{id}/permit-join (PJ-2)")`, absent → nothing; NO frame either way. Boot never opens a window. The key stays in `zigbee-config-schema.json` (:26–:31) with its description re-cut (§4); its removal from the schema is Tuesday's `CONFIG-ERROR:` word, not this lane's.
6. **The endpoint (DP-PJ2-6).** `POST /api/v1/integrations/{integrationId}/permit-join`, body `{"durationSeconds": 1–254, "reason": "<1–120 chars>"}`; `200` with the sibling's envelope (`IssueCommandEndpoint.respondAccepted` :360–:384): `{"data": {integrationId, durationSeconds, reason, actor, opensAt, closesAt}, "meta": {"timestamp": <clock.instant()>}}` — ISO-8601 instants; camelCase keys as that wire writes them (`entityId`, `commandId`); no `viewPosition` (the installer takes no cursor supplier); IR-92's Javadoc-vs-wire question is NOT settled here. `actor` = `caller.keyId()` where `caller` is the `ApiKeyIdentity` the auth filter stores at :580 under `RestFilters.IDENTITY_ATTRIBUTE` (:491) — read in the `Handler` lambda and passed to a pure `apply(EndpointContext, ApiKeyIdentity)` exactly as `TokenAdminEndpoints` :140–:142 and :252 do; a null caller → 401 `AUTHENTICATION_REQUIRED` (the filter should make that unreachable; the check stays). Problems (RFC 9457, `EndpointResponses.problem`): a bad body → `INVALID_PARAMETERS` 400; an unknown or non-running integration → `INTEGRATION_UNHEALTHY` 503 with the detail; an adapter without `PairingWindowControl` → a NEW `ProblemType.PAIRING_WINDOW_UNSUPPORTED("pairing-window-unsupported", 409, "Pairing Window Unsupported")`; the port's future not done in 5 s → `INTEGRATION_UNHEALTHY` 503 `"the integration did not answer in 5 s"`; an exceptional completion from the adapter itself (an NCP NAK — `EzspCommandException` from :914/:915 — or any other throw) → 503 `INTEGRATION_UNHEALTHY` with the exception's class name and message, never a stack, never 500 (the integration is the unhealthy party, not the API). Auth and the rate limiter are inherited from `installAuth` (`before(*)`, :553); the readiness gate from `/api/*` (:99).

## §4 Technical specification
- **Threads.** `openPairingWindow` runs ONLY on the adapter's command executor (row 10 submits it there; row 4's Javadoc says so) and touches: the protocol (:914, :915 — the M9.4a command write path already writes to the protocol from this executor), `permitJoinDeadline` (volatile), `currentWindow` (`AtomicReference`), `permitJoinEpoch` (volatile) — and NOTHING run-thread-confined: `rejoinWindowClosedNoted` / `rejoinLookupAttempted` (:250, :257) are cleared by the run thread at the top of `runCycleOnce()` when `seenPermitJoinEpoch != permitJoinEpoch` (then `seenPermitJoinEpoch = permitJoinEpoch`). Three closers on three threads — the executor (supersede), the run thread (`closeWindowIfElapsed()` at the end of `runCycleOnce()`), the supervisor's close thread (:804 → `close()`) — so every close is `currentWindow.compareAndSet(w, null)` (or `getAndSet(null)` for the two unconditional closers), and only the winner publishes; the deadline is nulled after the CAS. The `AtomicReference` is MANDATORY.
- **`isPermitJoinActive()`** (:555) unchanged in shape; it now reads a deadline set only by the endpoint path. The two admission gates unchanged.
- **The superseding open**: if `currentWindow != null` at open: publish `PermitJoinClosed(superseded, openedAt = old.opensAt(), closedAt = now)` first, then the new open. `protocol.permitJoin(duration)` is called for the new duration (the NCP restarts its own timer).
- **The transport reopen** (:1015–:1025): before `permitJoinDeadline = null` at :1023, `if (currentWindow != null) publish PermitJoinClosed(transport_reopened)`; then null both; the DP-B5 comment re-cut: "Reopen ≠ boot: the window is NOT renewed; the operator re-opens by the endpoint (PJ-2)".
- **`close()`** (:505): before the transport closes, `if (currentWindow != null) publish PermitJoinClosed(shutdown)` — best-effort inside a try/catch that logs one WARN; the close proceeds regardless.
- **The key-ignored WARN** replaces :500: `Optional<Integer> configured = context.configAccess().getInt(PERMIT_JOIN_DURATION_KEY)` (the :902–:903 read; `isEmpty()` = no key, :904–:906) → `isPresent()` → the one WARN with `configured.get()`; the read and the WARN happen once, at the :500 site, production only (the driven mode never reached :500 — keep that).
