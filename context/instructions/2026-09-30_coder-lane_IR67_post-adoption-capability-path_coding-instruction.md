## §4 Technical specification
- **Threads and locks.** The reconcile runs on the thread that calls `initialize()` (the supervisor's launch path) BEFORE any cycle thread exists; the slice's lock guards only its map reads (copied out); `RegistryProjection`'s own lock guards the write-ahead apply; `SupervisorCapabilityPublisher` is stateless and thread-safe over the bus's publisher (the supervisor's own lifecycle publishes use the same publisher from other threads today).
- **The diff key is `capabilityId`** — never `CapabilityInstance.equals` (a profile override tunes `confirmation`/`featureMap` on the stored instance; the id is the identity — AMD-59-INV-03). An id present in both → nothing. The published instance is the classifier's (after `installOverrides`), so a device adopted before an override existed receives the tuned instance for the NEW id only; its existing ids are not re-tuned (not this unit; say so in §5 if the lane sees a case).
- **Idempotence across the two apply paths.** The write-ahead `applyCapabilityAdded` runs on the boot thread; the bus delivers the same event to `RegistryProjectionSubscriber` on the bus thread (live) and again at the next boot (replay). All three land on "id present → no-op". T10 pins it; T9 asserts the registry entity carries the id exactly ONCE after the pass (no duplicate instances).
- **The orphan arm** (`applyCapabilityAdded` for an entity the registry lacks): no-op, `false`, the subscriber's WARN — a replay ordering where the entity's `entity_registered` precedes its `capability.added` in the log is guaranteed by the adapter (it publishes only for entities `findEntity` returned); an orphan therefore means a wipe or a half-registration repair, both already handled downstream.
- **`publishRemoved` throws** `UnsupportedOperationException` — T2 pins it; no production caller exists (row 4) and this lane adds none.
- **The skip arm** (`context.discovery() == null`): ONE WARN, the pass does not run, `zigbee.initialized` still logs. Production never takes it (T4: the zigbee descriptor declares DISCOVERY and the supervisor provisions it). A fixture takes it (T8).
- **Ordering inside `initialize()`**: `rehydrateAdoptionMaps()` (:372 — the maps) → the ingestion unit (:420–:441 — the learned zone types seeded) → the configurator (:476) and the watchdog → **the reconcile** → `zigbee.initialized` (:498). A pass placed before :420 classifies IAS endpoints under the motion fallback — T9 includes one IAS-bearing endpoint whose learned contact zone type EQUALS its adoption-time classification and asserts ZERO shrink and ZERO adds for it; T7b pins the swap (adopted under the motion fallback, contact learned later → `relearned 1`, no add, no shrink).
- **Log tokens are grep targets** — exact, once per occurrence: `zigbee.capability_reconcile` (INFO, per launch) · `zigbee.capability_added` (INFO, per addition) · `zigbee.capability_reconcile_shrink` (WARN, per shrinking endpoint) · `zigbee.capability_reconcile_ias_relearned` (WARN, per re-learned IAS endpoint, every launch) · `zigbee.capability_reconcile_unbound` (DEBUG, per unbound device) · `zigbee.capability_reconcile_skipped` (WARN, fixture-only) · `integration.capability_event_conflict` (WARN) · `registry.capability_added_orphan` (WARN).
