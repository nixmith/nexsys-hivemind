## §4 The specification and the two forks
### §4.1 (viii) action-effect
Inputs: the `runs` dict of `build_runs` (:383–:407 — the raw terminals with their payloads; NOT `run_rows` :518–:525, which carry no payload) and the command partition. Let `SUCCESS` = the terminal enum's success constant's NAME (row 12 — expected `SUCCEEDED`; the plan quotes it; never "success"). For a run with terminal `automation_completed`: `ac = payload.action_count`, `cc = payload.command_count`, `issued` = the count of `command_issued` attributed to the run — the candidate key is the envelope `correlation_id` (grader :28–:29, README :49: "a correlation is the RUN's and spans every command the run issues"; `c.correlation == runs[rid]["triggered"]["correlation_id"]`); the plan cites the core line that sets a command's correlation to the run's, or declares NOT LINKABLE; `triggered is None` (a carried-in run, :405–:406) → `issued = None`. Verdict per run: `final_status == SUCCESS and ac >= 1 and cc == 0` → FLAGGED (`reason: "completed with actions and no command"`); `final_status == SUCCESS and issued is not None and issued != cc` → FAIL (`reason: "command_count disagrees with the partition"`); else PASS. The clause's verdict: FAIL if any FAIL, else FLAGGED if any FLAGGED, else PASS; CANNOT-GRADE never (a missing payload key is a FAIL naming the key — the pinned record has both). The semantics of `action_count` (row 2) decide the FLAG's wording: if it counts actions EXECUTED, the text stays (a notify-only automation FLAGS legitimately — the report says which actions); if it counts actions DECLARED, the text is "declared actions and no command" — the plan says which. **Pre-registered:** EXPORT-1's four runs (if its export is on the desk, row 11) re-grade FLAGGED under (viii), the layer FLAGGED, not PASS.
