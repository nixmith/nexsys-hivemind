## 2026-08-02 | Category: desk-harness instrumentation / shell portability | Source: B3.1+B3.2 (nightly hardening desk gates) — three ways a desk harness lies about the thing it tests, and the flag-order sibling of SPELL-THE-FLAG

**Discovery:** Three harness-instrument defects surfaced while proving A-3/A-4/A-6, each capable of a false verdict about CORRECT production code (or a false green about broken code): (1) **awk `-v` mangles backslash escapes in dynamic regexes** — `awk -v re='^\[20…'` turns `\[` into a bare `[`, silently rewriting the pattern into a character class; every stamped line then "fails" the stamp check. Dynamic-regex checks belong in a LITERAL `/…/` inside the awk program. (2) **A shell started with `&` by a non-interactive parent inherits SIGINT ignored and cannot trap it** (the POSIX async-ignore rule; an inner `trap - INT` is equally void because ignored-at-entry signals cannot be re-enabled) — so a backgrounded wrapper under test NEVER sees the harness's `kill -INT`, and the trap-INT path reads as broken while being correct. Deliver INT to a FOREGROUND child, with a background killer subshell reading the target pid from a pidfile. TERM is exempt (only INT/QUIT get the async-ignore). (3) **Windows `Path.write_text` newline translation shifts byte offsets** — `\n` becomes `\r\n` on disk, so a fixture whose marker carries `log_offset = len(content.encode())` points 2N bytes short and a genuinely-empty window grows a phantom tail. Offset-sensitive fixtures are written with `write_bytes` (no translation layer exists to lie).

**Detail:** The integrity rule when an instrument is corrected mid-session: the red-first baseline must be RE-RUN under the CORRECTED instrument (against git-extracted baseline sources — `git show <sha>:<path>`, preserving sibling-file layout so self-relative resolution works), and the quoted red/green table comes only from corrected-instrument runs. A baseline red that happened to hold under a broken check is not evidence. Bonus flag-order lesson: `git grep --untracked` must precede the PATTERN — `git grep -l $'\r' --untracked` parses `--untracked` as a REVISION and dies `fatal: unable to resolve revision` (the flag-order sibling of the 2026-07-28 SPELL-THE-FLAG lock-free-porcelain lesson); the planted-control leg of the CR-scan pair is what catches this class, which is exactly why the control is mandatory.

**Impact:** (1) Any harness check built on a dynamic awk/sed regex gets a deliberate-failure probe before its verdict is trusted (the planted-control discipline generalizes: prove the instrument CAN fail). (2) Signal-path desk proofs name the delivery topology (foreground vs background) as part of the design — INT and TERM are not interchangeable test vehicles. (3) On a Windows desk, every byte-offset-bearing fixture is written through the bytes API; the R6 CRLF class extends from consumed paths to fixture offsets.

## 2026-08-05 | Category: rationale-block amendment mechanics / history preservation | Source: B3.3 (the s31 suite-position amendment) — when a dated re-amendment must "prepend the amendment chain" of a block whose title sentence and chain are FUSED into one paragraph, insert the new dated paragraph AFTER the living example line instead of splitting the fused paragraph: zero history bytes move, and one explicit cross-claim kills the colon-attachment misattribution

**Discovery:** THE AUTO SUITE OF RECORD block carries its amendment chain ("AMENDED … 2026-07-30 …. RE-AMENDED 2026-07-31 …:") fused into the title paragraph, ending in a colon that introduces the living `bench.sh suite …` example line. B3.3's DP-3 ordered the 2026-07-30/31 text NEVER rewritten AND the new paragraph prepended newest-first. Literal chain-head insertion cannot satisfy both: the title and chain share physical lines, so inserting between them forces re-wrapping history bytes; moving the example line up leaves the F1 sentence's colon dangling; and keeping a second, stale example line is exactly the drift trap the quoted line exists to prevent. The realization that satisfies every pin: update the single example line IN PLACE (it is living reference, not history), insert the new dated paragraph directly after it (ahead of the older dated rationale paragraphs — newest-first for the dated chain), and open the new paragraph by claiming the line above ("the suite line above quotes THIS ruling's order") so the historical colon cannot misattribute the new order to the old ruling.

**Detail:** The precedent diff is the instrument for "established style": `git log -S "<chain marker>" -- <file>` found the prior re-amendment commit (`8bce651`), whose diff showed the prior mechanics (example line replaced in place; new rationale paragraphs at the head of the rationale region) — but ALSO showed that the prior amendment had truncated its predecessor's detail text, which is what the new DP forbade; match the mechanics while tightening the preservation. Distinguish three text classes before editing any rationale block: HISTORY (dated ruling text — byte-frozen when a preservation pin exists), LIVING REFERENCE (quoted command lines and examples "that must not drift" — updated in place, exactly one copy), and STANDING WATCH paragraphs (remain in force — the new paragraph states so explicitly rather than restating them).

**Impact:** (1) "Prepend the chain" in a fused-paragraph block means prepend the DATED-PARAGRAPH sequence, not split the fused sentence — verify against the prior amendment's actual diff, never the prose description of the style. (2) A living example line trailing a historical colon is a standing misattribution seam: whichever paragraph owns the current order must claim the line explicitly in its opening sentence. (3) Exactly one copy of any must-not-drift line — a preserved stale twin is worse than a moved line.


## 2026-08-05 | Category: atomic-write test mechanics / crash-window realization | Source: S-5c (the sidecar temp-then-move) — a temp-then-move invariant is pinnable in plain JUnit without fault injection: pre-create the FINAL path as a NON-EMPTY DIRECTORY, and the specified `DirectoryNotEmptyException` on `Files.move(..., REPLACE_EXISTING)` freezes the crash window deterministically on every platform — AFTER the temp bytes land, BEFORE the final path changes

**Discovery:** The S-5c red-first mandate required proving "the write goes through a temp sibling and the final path is only ever replaced by a completed move" without faking a power cut, in a class with no I/O seam (the production write path is called directly). Making the WRITE fail (the module's existing F-14 blocked-parent harness) fails too early — it proves nothing about the move. The realization: `Files.move` with `REPLACE_EXISTING` onto a non-empty directory is SPECIFIED to throw `DirectoryNotEmptyException` (javadoc-guaranteed, both Windows desk and POSIX Pi), so a directory-with-occupant at the final path is a deterministic move-blocker that stops the mechanism exactly between its two steps. The frozen state is then directly observable: the `.tmp` sibling must exist and hold the COMPLETE document, and the final path must be byte-untouched.

**Detail:** Two strengtheners rode the idiom. (1) Prove temp COMPLETENESS with the class's own loader — construct a second cache instance pointed AT the temp path; a partial temp would take the discard arm and the device assert fails, so the parse is the completeness oracle (no JSON hand-parsing in the test). (2) The same test carries the recovery tail: delete the blocker, flush again, assert the stale temp was truncated + consumed and the final path is complete with zero residue — pinning the fixed-name idiom's self-heal in the same scenario. At baseline the pre-fix in-place write fails against the directory too (`writeString` on a dir throws on every platform), so the test reaches the temp assert cleanly and goes RED for exactly the designed reason ("no temp ever exists"), giving a clean quotable red.

**Impact:** Any future atomic-replace WU (state files, config snapshots, checkpoint exports) can pin its mechanism with this shape: directory-blocker → assert temp-complete-by-its-own-parser + final-untouched → unblock → assert consumed-temp + complete-final. No fault injector, no I/O seam widening, no platform-conditional test. Pair it with a torn-file LOAD pin (truncate a real write to half) so the hazard the mechanism closes stays demonstrated beside the mechanism itself.

## 2026-08-07 | Category: await-primitives / projection ordering | Source: M9.5-DURd Phase A (the HeroLoop CI-red diagnosis) — an event-store await does not order a projection: polling the LOG for `state_reported` proves ingestion published, not that any subscriber processed it — and a LIVE-only derived publisher (StateProjection's `state_changed`) swallows an edge processed pre-LIVE permanently, by design

**Discovery:** HeroLoopHardwareFreeIT's occupancy awaits (:98/:102) poll `EventStore.readFrom` for `state_reported` — they pass the moment ingestion publishes, regardless of the state projection's mode or checkpoint. The projection's PUBLISH phase is LIVE-only (`StateProjection` :57; :399–:400 — in REPLAY/TRANSITION "derivation runs and state is applied but publishes are suppressed"; :475–:478 — replay re-derivations are NEVER published, INV-WRITER-01). So a motion edge whose `state_reported` is processed while the projection is still pre-LIVE produces NO `state_changed`, ever — no backfill exists, replay purity forbids it — and every `state_change`-triggered automation downstream stays silent. `awaitRuntimeSubscribersLive` gates four subscriber ids; `state_projection` is not among them, so nothing in the harness orders projection-LIVE before the edge pump.

**Impact:** A test assert that depends on a DERIVED event (or anything downstream of one) must either gate the deriving subscriber's mode/checkpoint first or await the derived event itself — awaiting the CAUSING event's presence in the log is a different, weaker fact. Third member of the instrument-semantics family: the type-filtered checkpoint (2026-07-10, not a log-head cursor), the projected-view lag (2026-08-06, a view read is not verdict-grade near the window), and now the log-await (log presence is not projection progress). Price all three before trusting any await.

## 2026-08-07 | Category: ci-forensics / per-test pass-vector | Source: M9.5-DURd Phase A — in a multi-test CI red, the sibling pass/fail vector is an instrument that runs before any desk repro: same-JVM passing siblings exonerate every leg they share with the failing test

**Discovery:** Each red run reported 60 completed / 1 failed, 3/3 — only `heroLoop_motionToHonestConfirmed`. Its four sibling tests (identical boot, identical `label()` calls) plus both other label ITs drove `fireManual` actions targeting the same labels through the same LabelSelector → engine → dispatch → real zigbee handler → scripted-NCP path in the SAME JVM, minutes apart, and passed every time. That vector exonerates label resolution, the engine subscriber, dispatch, and the adapter path outright, and localizes the red to the one leg only the failing test exercises: the motion edge (`state_reported` → state projection → `state_changed` → trigger). Reading this out of the intake line ("60 tests completed, 1 failed") costs nothing and re-ranks hypotheses before any instrument is built — the leading candidate carried from precedent (the DURc label-race) was disfavored by the record all along.

**Detail:** The desk half: when a repro instrument is a JVM flag, prove it governed the test JVM before trusting a green — the `-i` executor command line plus an in-JVM `availableProcessors` print made 11/11 green non-vacuous — and state the instrument's reach honestly: `-XX:ActiveProcessorCount` shapes JVM pool sizing, not OS scheduling latency, so it cannot reproduce runner-class starvation on a fast many-core desk (the same reason the DURc red had "no honest red leg at desk").

**Impact:** First act on any multi-test CI red: write down which tests passed in the same JVM and diff the failing test's event-flow legs against theirs — legs shared with passers are exonerated; the residual legs rank the hypotheses. Then build instruments for the residual only.

## 2026-08-08 | Category: liveness-gates / mode-regression census | Source: M9.5-DURd-B′ (the window-closure) — before filing a "nothing orders X LIVE" gap against a test harness, walk the composition root's OWN await inventory and the mode FSM's regression arcs: start() may already hard-gate the id, and SubscriberMode leaves LIVE only to SUSPENDED

**Discovery:** The B′ pre-edit read found `HomeSynapseCore.start()` :589 calls `awaitProjectionLive()` (:1238–:1254) — a HARD gate (1,500 × 20 ms, THROWS `IllegalStateException` on exhaustion) ordering `state_projection` LIVE before the runtime subscribers even register and before `start()` returns — while the thread of record (this lane's own §7 filing, carried into the B′ instruction) said "nothing orders the projection LIVE before the first report pump." The IT-helper half of the claim was true (the four-id gate omits the projection; nothing RE-confirms it after `start()`); the absolute half was not — and the in-tree evidence was already sitting in `RunPipelineReplaySafetyTest`'s helper javadoc ("The projection is already LIVE (gated inside start())"). The regression census then bounds what a strengthened gate can catch: `ReplayDriver`'s overflow-recovery (:127–:133) is boot-`run()`-internal, `resume()` (:387) is the only SUSPENDED exit and is manual, and the LIVE delivery path (`pendingPositions.offer`) has no overflow arm — so LIVE regresses ONLY via a SUSPENDED trip, and a "projection lagged the whole boot" mechanism cannot coexist with a cleanly-returned `start()` (that failure reds the BOOT with a different signature).

**Impact:** (1) A liveness-gap filing carries TWO source walks or it is not filed: the await inventory of EVERY layer between subscribe and the assert (composition root included — the harness is never the only candidate orderer), and the mode FSM's regression arcs (which states can the id lawfully occupy at the gate?). (2) A helper javadoc documenting an ordering guarantee is evidence — read it as a claim to verify, not decoration; it was in the WU's own minimum read set and named the fact verbatim. (3) When a filed mechanism requires a state the FSM cannot reach at the assert point, say "mechanism source-closed" even while the red it explained stays unexplained — both facts coexist, and the unconfirmed-caveat travels sharpened rather than resolved.

## 2026-08-20 | Category: gate-probes / log-signature scans | Source: WU R-1/R-2 (the packaged write-path assert) — a log-scan probe greps the signature the real incident actually printed, pinned from the journal of record, with the regex written to net every spelling the JVM emits — and a scan that finds zero sources must fail, not pass

**Discovery:** The F-23 throw prints THREE spellings across one incident: `NoClassDefFoundError: jdk/jfr/Event` (slashes — the NCDFE message form), `ClassNotFoundException: jdk.jfr.Event` (dots — the cause line), and bare class-name stack frames (`BusMetricsJfr…`). A probe pinned from an ASSUMED signature (say, the dotted module name only) would miss the primary NCDFE line entirely. The shipped pattern `NoClassDefFoundError|jdk.jfr|BusMetrics` nets all three — the DELIBERATELY unescaped dot is load-bearing (it matches both `jdk.jfr` and `jdk/jfr`), and the bare `NoClassDefFoundError` arm is the generic second net for future missing-module classes. The pattern is also byte-identical to the operator block's grep, so the CI check and the hardware ⏺ read the same instrument. Second half: the scan sums hits over N sources (journal, stdout log), and a mode where N=0 would sum to zero and pass vacuously — the exact silence-as-success class the WU exists to kill — so the check counts scanned sources and `bad`s at zero ("the probe cannot run"), with the PASS line printing both the zero and the source count.

**Impact:** (1) Pin log-scan signatures from the incident journal of record, never from the exception class name you expect — then re-derive the spellings the JVM actually emits (slash-form class descriptors in NCDFE messages, dot-form in causes) and write ONE pattern netting all of them, shared verbatim with any operator-side grep so desk and hardware read one instrument. (2) Every multi-source scan carries a scanned-source count; zero sources is a FAIL arm, and the success line prints the count — an absence assert is only as strong as the presence of what it scanned (sibling of the anti-vacuous-success INFO and the OR-group observation-anchor rules). (3) When a tool the probe needs can be absent (sqlite3), tool-absence is an honest `bad` with the install hint, never a skip — a gate that silently skips its probe when the tool is missing re-manufactures the false confidence it was built to end.

## 2026-08-22 | Category: HTTP framework write-order / content-type overrides | Source: WU R-6/R-8 rider R-C (F-V2, the `application/problem+json` discriminator) — Javalin's `Context.json(...)` SETS `application/json` itself, so a content-type written BEFORE `json(...)` is silently overwritten in production while a recording test fake happily records it: set the media type AFTER the body write, and pin the order from the framework's bytecode, not from its method name

**Discovery:** The instruction's rider read "`problem()` sets `application/problem+json` before the `json(...)` write". `javap -p -c` on the pinned Javalin 6.7.0 jar shows `Context.json(Object, Type)` = `contentType(APPLICATION_JSON)` → `jsonMapper().toJsonString(...)` → `result(...)` — `json()` owns the content type. A header set before it would be overwritten at the very next call, and `RecordingEndpointContext` (a map of headers) would have recorded the pre-json value and gone GREEN on a production lie — the comment/code-divergence class in test-fake form. The in-tree exception path already knew: `RestFilters.writeProblem` (:549–:551) calls `ctx.json(...)` THEN `ctx.contentType("application/problem+json")` with a comment saying exactly why. The endpoint seam has no `contentType()` method, only `header(name, value)`; Jetty 11's `Response.setHeader` special-cases `Content-Type` → `setContentType` (verified at the jetty-server 11.0.25 bytecode), so `ctx.header("Content-Type", …)` AFTER `ctx.json(...)` is the correct and sufficient form through the existing seam — no seam widening.

**Detail:** The red-first capture was the cheapest in the WU: add the one assertion to an existing 404 test (`GetEntityEndpointTest:73`), run it against HEAD code → `AssertionError` (4 run / 1 failed), then land the two-line fix. The rider's census also shrank by one: the instruction listed `RecordingEndpointContext` as M ("records it"), but the fake's `headers` map already records every response header (:378–:380) — a file that needs no change is not touched to hit a count. Two sibling problem writers stay outside the fix and were filed as the next pointer: `IssueCommandEndpoint.problemWithFields` (builds its own 400 + `errors[]` body, bypasses `problem()`) and `ReadinessFilter`'s 503 responder — both still `application/json`.

**Impact:** (1) Any "set header X then write body" instruction against a web framework gets a bytecode (or source) read of the body-writing call BEFORE the test is written — frameworks routinely own `Content-Type`, `Content-Length`, and charset at the body write, and a recording fake cannot see the override. (2) When a test double records calls rather than effects, a passing test proves call ORDER, not wire truth; pair it with the framework-level idiom already proven live (here the exception path the FE lane had observed as `problem+json` on the wire). (3) A census row that turns out to need no bytes is reported as such, never padded.

## 2026-08-22 | Category: operator-path design / single-writer stores | Source: WU R-6/R-8 (the token-rotation operator path, closing F-S5) — a file with ONE lawful writer (the running service) gets an operator path by REQUEST FILE, not by a second writer: consumed at startup under the store's own lock, deleted BEFORE execution so a crash never replays it, with two DIFFERENT failure arms (unreadable → leave it; undeletable → execute nothing)

**Discovery:** `config/api_tokens` is rewritten whole by the service under a `ReentrantLock`; a `homesynapse-token rotate` that edited it offline would be a lost-update race by construction (and needs the hash/format knowledge to live in two places). The design that keeps the single writer: the helper appends a verb line to `config/token_ops.request` (owner = the service user, 0600) and restarts; `processOperatorRequests()` runs immediately after `ensureInitialToken()` — before the auth middleware is built and before any socket binds — reads the lines, DELETES the file, then executes. Order is the invariant: an unremovable request executes nothing (it would replay on every start — a `rotate` loop that logs every client out each boot), while an unreadable request is left in place so the operator can fix ownership and restart (the store's existing never-brick-startup posture). Both arms are WARN + zero report; neither throws. The helper's `install -o homesynapse -g homesynapse -m 0600 /dev/null` + append makes the file service-readable and append-safe by construction.

**Detail:** Three things the bytes taught while authoring. (a) The atomic-rewrite promise in the class javadoc was FALSE at HEAD (`Files.writeString` truncate-and-write): a crash mid-rewrite leaves an EMPTY store, and an empty store MINTS A NEW PAIRING TOKEN on the next boot — F-23's false-confidence class on credentials; fixed to the comment with the temp+`ATOMIC_MOVE` idiom, owner-only on POSIX (`asFileAttribute` at `CREATE_NEW` AND re-asserted after the write — a strict umask can strip owner bits too). (b) `rotate` mints BEFORE revoking the rest so a concurrent `validate()` never observes zero active tokens; ONE `persist()` for the whole batch. (c) The packaged readiness probe (`health-probe.sh`) authenticates with the artifact `initial_api_token`: a bare `revoke` of that key takes the unit down at the next restart (403 → exit 3 → ExecStartPost failed), and deleting the artifact — the install banner's own advice — makes the next restart wait out the 90 s probe timeout. Neither was in the instruction; both went into the doc, the helper's usage text, and a store-level WARN whose predicate (`artifactCarriesDeadToken()`) is unit-pinned.

**Impact:** (1) "Add an operator verb for X" against a single-writer store is a request-file problem, not a CLI-writes-the-file problem; the consumption point is wherever the store is already opened under its lock at boot. (2) Delete-before-execute is the crash law for any one-shot request file; the two failure arms are not interchangeable and each gets its own test (POSIX + non-root gated via `Assumptions` — root ignores directory write bits, container CI may run as root). (3) Before shipping a `revoke`-class verb, walk every consumer of the credential it can kill — the readiness probe was one the instruction did not account for, and the doc's "delete the artifact after pairing" advice needed a packaged-path caveat with source citations, not a bare repeat.
