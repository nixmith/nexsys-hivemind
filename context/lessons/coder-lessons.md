## 2026-08-22 | Category: readiness probes / credential timing | Source: WU R-6/R-8 review fleet (the shell-distribution lens, confirmed 2/2) — a `Type=exec` unit's `ExecStartPost` probe starts the instant the service is exec'd and may CACHE the credential it reads; a boot that rotates that credential before binding then fails its own readiness gate although the rotation persisted. Walk a credential consumer's TIMING, not only its existence

**Discovery:** `homesynapse.service` is `Type=exec` with `ExecStartPost=health-probe.sh --wait --timeout 90`; the probe's `load_token` (`health-probe.sh:85–:93`) reads `config/initial_api_token` on its first iteration and returns early on every later one once `TOKEN` is non-empty (`:87`). A `rotate` request is applied by the service during `bringUpHttpSurface()` — seconds after exec, BEFORE the socket binds — and revokes every prior token, so the probe's cached pre-rotation token gets 403 at its first connect → exit 3 → the start job fails → `systemctl restart` returns non-zero → the helper dies under `set -e` without its success line; systemd's `Restart=on-failure` brings the service back ~10 s later with the NEW artifact. The §OP-A bench block (no systemd, no probe) cannot surface it; install-smoke never runs `rotate`. The author's own "walk every consumer of the credential" pass (the lesson above) found the probe but priced only its EXISTENCE (revoke-of-the-artifact-key, deleted artifact), not its read timing.

**Detail:** The in-census close: the helper removes the artifact before a `rotate` restart (only in the systemd branch, only after the request is queued), so the probe's file-absent arm (`:96–:98`) polls until the service writes the new artifact (rotate rewrites it before binding), then authenticates with the new token. Root cause — a file-sourced token cached for the probe's lifetime — is a `health-probe.sh` change outside the census (re-read the file each iteration when the value came from a file), filed as the next distribution pointer beside E3.

**Impact:** (1) For every credential a boot can rotate, list each consumer AND when it reads: a probe, a sidecar, a cron, a watcher that snapshots the secret at T0 is stale the moment the service rotates at T1, and a restart-time rotation is exactly the T0→T1 window. (2) A start-gating probe that authenticates is itself a credential consumer with a cache semantic — read its loop, not its usage line. (3) A review lens that DIFFERS from the author's (here: distribution/systemd rather than the store) is what found it; the author's pass had already walked the same file.

## 2026-08-22 | Category: version schemes / packaging grammar / fixture rigs | Source: WU R-7 rider F-V1 (the `hs_version` bare-id arm) — "starts with a digit" is the WRONG discriminator for "is this a tag": a bare hex id is digit-leading 10/16 of the time, and a digit-leading bare id sorts as a NUMBER above every `0.x.y`, turning every later build into an apt downgrade. The dot is the discriminator; assert the grammar at the capture site AND at the consumer; drive the function's real arm in the test by disabling its own bypasses — and let the instrument correct your expected mutation count

**Discovery:** `hs_version` wrapped a `git describe --always` id as `0.1.0+g<id>` only when it began a–f (`[0-9]*)` passed digit-leading ids through). The H3 artifact was `0.1.0+gd26777c`; the 2026-08-22 Block-0 build printed `version=7c9e4fa` bare, and dpkg orders `7c9e4fa` above every `0.x.y` — the next wrapped build is a "downgrade" apt refuses. The fix is a different discriminator, not a wider arm: a tag-shaped describe (`1.2.3`, `1.2.3-5-gabc1234`, `1.2.3-dirty`) ALWAYS carries a dot and a bare id (`7c9e4fa`, `7c9e4fa-dirty`) NEVER does, so `*.*)` passes through and everything else wraps — and a grammar assert `^[0-9]+\.[0-9]+\.[0-9]+` at the capture site (`build-image.sh`, outside any `$( )` because a `die` inside a substitution cannot abort the script) plus the same regex echoed at the consumer (the workflow, after the `.deb` exists) makes the rule mechanical; a `v1.2.3` tag is rejected by design (tags must be digit-leading).

**Detail:** The fixture test had to defeat the function's own bypasses to exercise the arm: `HS_VERSION` returns verbatim, and a `VERSION` file beside the caller returns verbatim — and "beside the caller" under the `bash -c '. common.sh; hs_version'` idiom means `dirname "$0"` = `dirname bash` = the CWD, so the tracked `distribution/VERSION` (`0.1.0-skeleton`) silently wins from `distribution/` or `distribution/image/` as cwd (a cwd-dependent version of record — filed as a [REVIEW], not fixed: fenced). The rig: a stub `git` on PATH answering `rev-parse` → 0 and `describe` → the fixture, `hs_version` run from a hermetic `mktemp` cwd with `HS_VERSION=` empty through the exact production invocation. Mutation-verified twice: HEAD's arm fails TWO rows, not the three I wrote in the header — `d26777c` is a–f-leading and wrapped even before the fix; the instrument corrected the comment. A `sed`-based carrier mutation silently did not apply (the literal still present) — caught only because the mutant run was read against the expectation; redone in Python and re-proven (exactly 1 FAIL).

**Impact:** (1) Never classify a version string by its first character; classify by a property the two populations cannot share (here: a dot). (2) A version scheme ships with its ORDERING consequence stated: `+g<sha>` suffixes do not order between untagged builds either (`g7c9e4fa` < `gd26777c` by dpkg's segment compare) — the honest doc says "the clean fix is a tag", and the monotone alternative (`+git<rev-list --count>.g<sha>`) is the hub's call. (3) A fixture test for a shell function with early-return overrides must prove the overrides are OFF in the rig (env empty, no file at every path the function checks, the real invocation shape), or it tests the override. (4) A mutation run whose failure count differs from your prediction is a finding about your model, not noise — re-derive the expected set from the old code before "fixing" the test; and a mutation applied by `sed` is unproven until the mutant bytes are read back.

## 2026-08-22 | Category: HTTP framework method fallbacks / conditional-status routes | Source: WU R-9 / E3-HEALTH (the unauthenticated loopback `/health`) — Javalin 6's automatic HEAD-for-GET answers a BARE 200 without running the GET handler, so a route whose status is conditional must register `app.head(...)` itself; a "does the framework handle HEAD automatically?" question has THREE answers (no / yes / yes-but-wrong), and only the bytecode tells you which

**Discovery:** The instruction's fallback read "if Javalin 6 does not answer HEAD for a GET route automatically, register `app.head`". `javap -c` on the pinned 6.7.0 jar (`io.javalin.http.servlet.DefaultTasks`): the HTTP task dispatches a handler only when `findHttpHandlerEntries(ctx.method(), uri)` has an entry for the request's OWN method; the fallback task then runs `method()==HEAD && router.hasHttpHandlerEntry(GET, uri)` → `return` — Javalin's default status is 200 and the GET handler is never invoked. For the dashboard shell (a 200-always static route) that is fine and the DASH-SERVE `HEAD /dashboard/` pin rides the resource handler instead; for `/health` — 200 only when the projection is LIVE — it is a passes-but-false "ready" during REPLAY for any HEAD-based prober. Registering the same handler under `app.head` makes the real predicate run; Jetty drops the body for HEAD at the generator, so status + headers survive and the wire body is empty (e2e-pinned: HEAD 200 + empty body on loopback; HEAD 401 off loopback).

**Impact:** (1) Any route whose GET status is conditional (readiness, existence, authorization-dependent) needs an explicit HEAD registration if HEAD semantics matter — treat "the framework handles HEAD" as a claim to verify per route, not a property of the framework. (2) A yes/no question about framework behavior gets a bytecode read of the dispatch path BEFORE the design decision (the R-C `json()`-owns-Content-Type lesson's sibling): the third answer — "yes, unconditionally" — is the one that passes every green-path test and fails in production. (3) Pin the honest arm e2e at the level where the framework's shortcut would have answered: here a HEAD through real Jetty, not the recording fake (which never sees the fallback).

## 2026-08-22 | Category: refusal guards on mutators / test-fixture fan-out / address-literal classification | Source: WU R-9 rider R-H2 (the last-full-access-token guard) + the R-H1 loopback classifier — a refusal guard turns every minimal fixture that exercised the mutator into a refused call, so walk `git grep` callers (not the instruction's list) and make each fixture ASSERT the non-refused outcome; and never hand a request-derived string to `InetAddress.getByName` unless it is syntactically a literal — the JDK resolves colon-free non-literals via DNS

**Discovery:** R-H2 makes `OpaqueTokenStore.revoke()` refuse the only active full-access token. Every "mint one token, revoke it, assert it is dead" fixture in the module — five in `OpaqueTokenStoreTest`, the self-revocation test in `TokenAdminEndpointsTest`, AND `StandardAuthMiddlewareTest.revokedTokenIs403` (a file the instruction's consumer survey did not list; `git grep -n "\.revoke("` found it and `TokenCliTest:71`, which revokes a SCOPED token and is unaffected) — would silently become a refused revoke: the token stays valid and the assertion that follows fails. The fix is not to loosen the guard but to re-fixture each test with a second full-access token AND assert `revoke(...) == REVOKED`, so a future guard change can never make the fixture vacuous. On the classifier: the instruction's charset rule (`[0-9A-Fa-f:.]` else false, then `InetAddress.getByName`) still admits hex-only hostnames (`cafe.babe`, `deadbeef`, `1e3`) and colon-free non-quads (`1.2.3.4.5`, `127.000.000.001`, `2130706433`); JDK 21 `InetAddress.getAllByName` (`src.zip`, `:1635–:1663`) enters the literal branch only for a leading hex digit or `:`, THROWS `UnknownHostException` when a colon-bearing parse fails, but falls through to the resolver for any colon-free string that is not a valid dotted quad — and maps an EMPTY host to loopback (`:1615–:1617`). The shipped classifier parses the IPv4 arm locally (strict dotted quad, `InetAddress` untouched), charset-guards the IPv6 arm plus the JDK's first-char precondition, strips Jetty's IPv6 brackets (`Request.getRemoteAddr()` → `formatAddrOrHost`) and a `%zone`, and rejects the empty remainder.

**Impact:** (1) "Add a guard to X" = re-read every caller of X by grep, including tests in OTHER classes and modules; the instruction's survey is a floor, not the census; a test that a guard would refute gets the +1-and-disclose treatment, never a silent widening of the guard. (2) Every re-fixtured test asserts the guard's non-refused outcome explicitly — a fixture that merely "still passes" after a guard lands may be passing for the wrong reason. (3) A request-time address classifier must be literal-only by CONSTRUCTION, derived from the JDK's own branch conditions (not from an assumed charset), with the IPv4 arm never touching the resolver API at all; pin the non-literal set (hostnames, hex words, `host:port`, 5-part, leading zeros, bare integers, half-brackets, zone-only, empty) as false-without-throwing.

## 2026-08-23 | Category: CI step assertions / shell -e semantics / action-major verification | Source: WU R-7b (the version-scheme micro-WU) — a `! grep` gate in a `set -e` step is vacuous, and an action major's EXISTENCE is not its RUNTIME

**Discovery:** (1) Rider (k) specified `! grep -q 'Unknown key name' /tmp/unit-verify.log` followed by a green echo inside a `set -e` workflow step. Bash (and POSIX) exempt a `!`-inverted command from `-e`, and the step's verdict is its LAST command's status — so with the echo last, the step exits 0 even when the grep MATCHES: the gate can never fail. Proven at the desk: `bash -e` with the string present → exit 0. Shipped `if grep -q …; then echo ::error…; exit 1; fi` instead, plus a `command -v systemd-analyze` hard guard (an absent verb would otherwise read as success), and mutation-flipped it both ways (HEAD's unit with `LogDirectory=` → step RED at `:31`; the fixed unit → green). (2) The ruled `upload-artifact@v5` bump was chartered to clear the Node-20 deprecation annotation, and the v5 tag EXISTS — but its `action.yml` declares `runs.using: 'node20'` (v6.0.0's release note: "v5 had preliminary support for Node.js 24, however this action was by default still running on Node.js 20"). The R-7 verification ritual (`git ls-remote --tags`) proves a major exists; it says nothing about what the major DOES. Implemented `@v5` as ruled; filed the evidence + the one-token `@v6` flip as [REVIEW].

**Impact:** (1) Never ship `! cmd` as a step's failure gate under `set -e` — use `if cmd; then …; exit 1; fi` (or make the inverted command the step's LAST line, fragile) — and mutation-flip every new CI assert like any fixture (arc-7 applies to workflow steps). (2) When a bump's PURPOSE is a runtime/behavior change, verify the property itself at the tag (`curl raw …/action.yml | grep using:`, a release note), not just tag existence — existence-verification passed here while the purpose silently failed. (3) Desk rig note (msys/Git Bash): a Windows-style `C:/…` path in `PATH` splits at the drive colon, so a stub-binary dir prepended that way silently loses to the real binary — build stub PATHs from POSIX paths (`cygpath -u`, or mktemp's native /tmp); the version-grammar rig is immune only because mktemp already answers a /tmp path.
