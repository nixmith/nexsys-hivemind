# The R-10 sitting — a plain-language walk-through

## Part 1 — The five strategy words (these shape the company; take your time here)

### R-1 · What do we build the community around?
**What it's really about.** When outsiders first touch this product, what do they touch? Three candidates: (A) a plugin SDK — "write code against our APIs"; (B) the explainability demo — "watch it explain why it fired"; (C) the measured corpus — "bring your device, we measure it on the bench, we publish confirmed/unconfirmed at a named commit." Your 08-30 instinct was "pivot toward plugins." RS-5 tested that instinct hard and found: a public code SDK this fall would let third-party code run inside our process, where it could forge the very attribute reports our confirmation verdict is built on — we would be selling a verdict that a plugin could counterfeit. It would also freeze APIs we are still changing (three to five milestone-sized builds, then six release cycles of deprecation duty for every surface we froze). So "SDK now" dies on its own evidence — but "plugins" survives in its data-first meaning: device profiles and converters as declarative files, no code inside the boundary, measured on the bench. And that is the same act as your Founder Operating Plan's "single highest-leverage action" — the presence-quality benchmark — at a different grain: bring your home, we measure the four metrics, we publish.
**My recommendation: (b)** — the corpus is the front door; the explain surface is its demo face; your benchmark is folded in as the second thing the corpus measures; the code SDK becomes a rung we price later, when there are users to serve.
**If you choose otherwise.** (a) = the same, minus your benchmark — the strategy would keep not mentioning it. (c) = we spend a design round pricing an SDK we will not ship this year. (d) = we drop the plugin story entirely and lose the community wedge that survives the evidence.
**Where I'm unsure.** Whether the presence benchmark belongs in the strategy NOW (as a P3 row — "begin instrumenting your home + 3–5 others", your own FOP Phase-2 timing) or later. I put it in now because a strategy that omits the founder's highest-leverage action is not the strategy the founder is running.

### R-2 · When does the code go Apache-2.0, and on what chain?

Going open needs two legal papers and a nod: an IP assignment from you to NexSys LLC (cheap insurance the entity ruling already recommended), a one-page consent under your operating agreement (§VIII(4) — you are the sole member today), and counsel's word. Then the LICENSE files change. RS-5 added the sharp point: until that flip, NOTHING can be contributed — not even data — so no community date can be spoken before the flip date is scheduled.
**My recommendation: (b)** — do it in the same window the rename lands in the tree, so the first public Apache snapshot carries the final name: one launch moment, not two. ## Part 2 — The four rows that charter code (this is where hours and hardware go)

### Row 10 · F-R4-1 — the device that rejoins and is never noticed
**Plain.** When a mains-powered device (the Hue) rejoins the Zigbee network after a power cycle, our software never notices it is un-adopted — it logs "unknown sender, frame skipped" forever. That is why R-4 could not reach its fourth criterion. **The fix:** during an open join window, an unknown device that speaks gets looked up, interviewed, and proposed exactly like a brand-new device. **My recommendation: (a).** **What changes otherwise:** (b) auto-adopting would violate the doctrine that adoption is an explicit, evidenced act; (c) leaving it means R-4b is impossible and the fleet sentence never mints. **Where I'm unsure:** the lookup of a device's permanent address from its network address is a radio-protocol call we have never run on real hardware — the instruction names it as the first thing R-4b verifies. **Your dispatch tonight IS the (a) word** — recorded as such.

### Row 13 · PKG-SEC-2 — the warning on every boot
**Plain.** The service warns at every start that `integrations.zigbee` "is not defined in the schema." Reading the source tonight: the schema fragment EXISTS and IS registered — but after the config has already been validated (an ordering choice from an earlier milestone). So it is not a missing piece; it is a sequence bug, and today a badly-formed zigbee block is invisible behind "unknown". **My recommendation: (a′)** — register the fragment before validation (it is static text; no adapter needed). **What changes otherwise:** (b′) validates late — weaker; (c) the carve-out silences the warning and validates nothing — never. **Where I'm unsure:** whether the lifecycle design doc's text forbids the earlier registration (the Coder checks and STOPS if it does).

### Row 6 · OR-FAILCHAN — "failed" after a clean stop
**Plain.** After a normal `systemctl stop`, the service shows as FAILED. Tonight's source read explains it: the JVM's default behaviour on SIGTERM is to exit with code 143, and our unit file never told systemd that 143 is a clean exit (`SuccessExitStatus=` is absent). Same class: an orderly close logs `transport_failed`; healthy outcomes are being reported through failure channels, which trains an operator to ignore red. **My recommendation:** one sweep WU; the §6-B fix is most likely the ONE-LINE unit change (declare 143 as success) rather than fighting the JVM in code — the sitting rules which. **Measured?** Yes, at R-3a (exit-143 observed); the O-2 confirmation on the held card is now a step in R-4b's packet, not a gate.

### Row 14 · CG-1/2/3 — three missing fields in the dashboard's read API
**Plain.** The explain surface cannot show that an automation's trigger points at a device that no longer exists, cannot correlate an entity row to its adoption event, and cannot show a real "last reported" time in the list — because the frozen read API does not carry those fields. Three OPTIONAL fields, one version bump, Core first then the FE fast-follow. **My recommendation: (a) all three.** **What changes otherwise:** (b) CG-1 only unblocks the loud surface but leaves the list dishonest; (c) defers the demo face of the corpus.
