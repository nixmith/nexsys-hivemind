## §2 The forks the instruction cannot settle alone (H10; the recs stand by silence past Wed 2026-09-30 13:00 CT; `IR67:` is the word)
**(a) The publish seam — `seam=runtime` (REC) | `seam=adapter`.** REC: honour AMD-59's letter with the smallest code — the runtime implements `CapabilityPublisher` as one class over the supervisor's `publisher` (an `EventDraft` per call: `capability.added`, subject = the entity, origin INTEGRATION, the `SequenceConflictException` caught as one WARN in PJ-2's form), provisions `new DiscoveryServices(impl)` into the context ONLY when the descriptor declares `RequiredService.DISCOVERY` (row 6's sentence becomes true; the other four families stay null), and the zigbee descriptor declares `DISCOVERY`; the adapter calls `context.discovery().capabilityPublisher().publishAdded(entityId, instance)`. `seam=adapter` (the adapter publishes `CapabilityAdded` itself through `eventPublisher()` as PJ-2 did) is fewer files but leaves AMD-59's seam a dead letter and duplicates the envelope code in every future adapter. Refutable-by: the lane finding the supervisor's context construction unable to see the descriptor's required services at :1089 (then the provisioning moves to the factory registration path — the lane says where).
**(b) The reporting row — `reporting=relink` (REC) | `reporting=boot`.** REC: the boot pass publishes and logs only; the newly covered cluster's reporting is configured by the EXISTING relink path at the device's next rejoin/announce (row 15), which already runs `ReportingConfigurator` — if that path derives its cluster set from the handlers (not from the entity's stored capabilities) nothing more is needed, and the instruction's test pins that; if it derives from the entity, the projection's appended capability is what makes the next relink cover the cluster. `reporting=boot` (configure at boot, device by device) would put radio I/O on the boot path against a fleet that may be asleep — against IR-83's boot-ordering gate and the bench's boot-health window. Refutable-by: row 15 showing relink configures reporting only for a subset that a boot-time list could not join.
**(c) Removal — `removal=none` (REC).** The register row says additive only. A re-classification that yields FEWER capabilities than the entity holds (a handler retired, a zone type re-learned) publishes nothing and logs one WARN `zigbee.capability_reconcile_shrink: device= endpoint= entity= missing=[…]` — a record for the hub, never a `capability.removed` (that door — an entity losing a capability the automations bind — is its own unit with its own review).
**(d) Not bundled — CONFIG-ERROR-1 (IR-90; `CONFIG-ERROR: fatal`).** The validator's seam is in the configuration module, a different path-domain from this unit's four; D-v88-12 routes it to Nick's desk (Mon 10-05). The pre-verification found nothing that couples them.
**The observables the instruction pre-registers:** one INFO per addition `zigbee.capability_added: device=<ieee> endpoint=<n> entity=<ulid> capability=<id>`; one summary per boot `zigbee.capability_reconcile: endpoints=<n> entities=<n> added=<n> shrink=<n>` (0/0 on a fleet whose handlers have not moved — the nightly's silent case); the store gains `capability.added` rows with the entity as subject; `/api/v1/entities` renders the new ids on the Hue's entity; boot-health's positive tokens unchanged (the pass runs after `adoption_maps_rehydrated` and before `registry.projection_live`? — NO: the projection must be LIVE before the boot pass reads the registry — the instruction pins the ordering against IR-83's gate at `$Z/ZigbeeIntegrationAdapter.java` :372–:445 and names it in the test clock's paste-block).
