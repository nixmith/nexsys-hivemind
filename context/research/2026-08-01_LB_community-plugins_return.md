### 1.2 What the field converged on

**FACT — HIGH.** Every comparable ecosystem examined runs a **two-tier structure today: a zero-review side-load for day 1, beside a reviewed permanent channel.**

| Ecosystem | Day-1 side-load (no review) | Permanent reviewed channel |
|---|---|---|
| Zigbee2MQTT | external converter `.mjs` dropped beside config, or pushed live over MQTT | PR to `zigbee-herdsman-converters` (+ a 512×512 image PR) |
| Home Assistant | HACS **custom repository** — paste a URL | `hacs/default` PR (one line in a JSON array) / HA-core integration PR |
| ESPHome | `external_components:` in YAML — including **`github://pr#NNNN`**, an unmerged PR | core component PR |
| Tasmota | paste a template JSON in the web UI | `tasmota/autoconf` PR / `.tapp` extension repo |

Sources: [zigbee2mqtt.io external converters](https://www.zigbee2mqtt.io/advanced/more/external_converters.html) · [hacs.xyz custom repositories](https://www.hacs.xyz/docs/faq/custom_repositories/) · [esphome.io external_components](https://esphome.io/components/external_components/) · [tasmota.github.io Templates](https://tasmota.github.io/docs/Templates/).

**INFERENCE — MED (see §0.3 gap 6): the two-tier shape is an *arrived-at equilibrium*, not an initial design.** The web sources above are current-state pages and cannot evidence origins. The trajectory evidence is internal and dated: the wars dossier records openHAB's **five-era arc** (1.x monolith → Eclipse IoT Marketplace 2017–2019, launched because *"the queue for binding PRs is still too long"* → abandonment → a two-year gap → forum-as-registry at 3.2, 2021-12-19), ESPHome's removal of runtime "custom components" at 2025.2.0, and **L-17**: *"An unofficial installer arises wherever official distribution has friction; the healthy response is embrace-and-partner."* Treat "all arrived there" as a well-supported pattern, not a proven universal.

**INFERENCE — HIGH. The decisive design property is not the two tiers; it is whether the day-1 artifact is *identical* to the merged artifact.** Z2M gets this right — the frontend's *"Generate external definition"* button (shipped in **1.35.0, 2025-01-01**, [release tag](https://github.com/Koenkk/zigbee2mqtt/releases/tag/1.35.0)) emits the same object that later goes into the vendor file. ESPHome gets it perfectly right: a core component and an external component are byte-identical in layout, so `github://pr#NNNN` makes an unmerged PR directly installable and **decouples "usable" from "merged" at zero cost — reviewer queue depth becomes irrelevant to adoption.** Where the two artifacts diverge, contributors strand between tiers.

**FACT — HIGH — backlog is universal and openly admitted (all counts as-rendered 2026-08-01).** HACS ships the sentence *"new additions still take **months** to be reviewed and included"* in its own submission instructions ([hacs.xyz/docs/publish/include](https://www.hacs.xyz/docs/publish/include/)); [`hacs/default`](https://github.com/hacs/default/pulls) shows **691 open PRs** against ~**2,637** accepted integration entries ([the `integration` file](https://github.com/hacs/default/blob/master/integration), 2,639 lines). [HA core](https://github.com/home-assistant/core/pulls): **807 open / 99,232 closed**; its review doc tells contributors *"it might take a while… have a bit of patience,"* caps them at five simultaneous PRs, and deprioritises features below bugfixes ([review process](https://developers.home-assistant.io/docs/review-process/)). [ESPHome](https://github.com/esphome/esphome/pulls): **458 open / 14,296 closed**. [`zigbee-herdsman-converters`](https://github.com/Koenkk/zigbee-herdsman-converters): **56 open / 10,457 closed** against **5,521 supported devices from 583 vendors** ([supported-devices](https://www.zigbee2mqtt.io/supported-devices/)).

**INFERENCE — MED.** Submission-unit *size* predicts standing backlog worse than *what kind of decision the review is*. HACS's unit is **one line of JSON** and still queues for months, because the review is a **trust/curation** decision. Z2M's device channel carries the smallest standing backlog in the set relative to throughput, and its review is **pattern-matching against 5,521 existing entries**. *(No latency claim is made — see §0.3 gap 5; "backlog" here means the open/closed ratio only.)* Curation queues do not shrink by shrinking the artifact — only by delegating trust or by removing the coupling that makes the queue urgent (§1.4).

### 1.3 The category moved *away* from in-process third-party code, this quarter, in our exact protocol

**FACT — HIGH.** Zigbee2MQTT PR **#31826** (opened 2026-05-01, **merged 2026-05-08**) added a setting to *"disable execution of custom user-provided JS code (external extensions and converters)"* **"In order to provide better security by default."** It shipped in **2.11.0**: *"External extensions and external converters are now disabled by default for new installations… enable them using the configuration `enable_external_js`."* Existing installations keep them enabled **until 3.0**. Sources: [PR #31826](https://github.com/Koenkk/zigbee2mqtt/pull/31826), [2.11.0 release](https://github.com/Koenkk/zigbee2mqtt/releases/tag/2.11.0), release-discussion thread dated **2026-06-01** ([#32158](https://github.com/Koenkk/zigbee2mqtt/discussions/32158)). Z2M's own securing guide states the reason plainly: *"By design, external extensions and converters execute arbitrary user-provided JavaScript code within the Zigbee2MQTT process"* ([securing guide](https://www.zigbee2mqtt.io/guide/installation/14_securing.html)). **Elapsed: ~12 weeks since merge, ~9 weeks since the release discussion.**

**INFERENCE — HIGH. This is the single most decision-relevant external fact in the lane.** The ecosystem with the best day-1 generator UX in the category concluded, this quarter, that in-process arbitrary JS was too dangerous to leave on by default. **Doc 18 principle 4 ("data-first extensibility before code extensibility") is therefore not the conservative choice — it is the direction the category's leader just moved.** It also corroborates wars-dossier **L-1** and **L-4** from a 2026 datapoint the dossier (2026-07-02) records only in passing.

**INFERENCE — HIGH.** A data channel has no equivalent exposure. A Tasmota template cannot compromise a host; a `.mjs` converter can. For a project whose entire brand is *truth about what the system did*, **the first community surface being a code-execution surface is a category error** — one compromised converter is one falsified log.

### 1.4 The most transferable single rule found anywhere in the survey

**FACT — HIGH.** Z-Wave JS documents, verbatim: **"A missing config file *does not* mean that the device is unsupported."** Standardised Command Classes give baseline function regardless; the community-contributed file adds labels, parameter names and device-specific workarounds ([zwave-js config-files overview](https://github.com/zwave-js/zwave-js/blob/master/docs/config-files/overview.md)).

**INFERENCE — HIGH.** Every backlog complaint in this survey ultimately traces to users whose hardware is inert until a maintainer merges something. **Make the community submission additive quality, never gating function, and the review queue stops being an emergency.** For us this is not a new posture — it is the *same* posture as honest-UNKNOWN: a device with no profile is a device we describe accurately and serve generically, not a brick. **This belongs as a written design rule on the M9.3 profile registry**, and it is the cheapest sustainability decision in the whole return (§3).

### 1.5 Where a data channel was the FIRST community surface — and what happened

**FACT — HIGH.** **openHAB's Z-Wave device database** is the cleanest case, and it was a *web form*. Its README states the motivation verbatim: *"producing the XML files takes some knowledge. Therefore, maintaining the database is often left to a small group of people"* — the answer was *"a GUI to make it easy enough for anyone to enter and update records"* ([cdjackson/zwave-database](https://github.com/cdjackson/zwave-database)). The live database carries **"First Approval" / "Last Approval"** timestamps and a **"Modified Awaiting Review"** flag ([opensmarthouse.org/zwavedatabase](https://opensmarthouse.org/zwavedatabase/)). Maintainer Chris Jackson, **2021-12-01**: *"it does take a little bit of time… Normally it's about a day for everything to filter through to the snapshot build"* ([forum thread](https://community.openhab.org/t/question-about-status-of-z-wave-database-updates/129129)). ~1,250 devices at the 2020-07-29 rewrite ([announcement](https://community.openhab.org/t/z-wave-database-site-updates/102984)).

**INFERENCE — HIGH.** The data channel solved the **format** problem completely and then hit a **governance/bus-factor** wall instead: in that same 2021 thread the maintainer's fix for latency was *to hand out write access personally.* One named individual owned the schema, the hosting, the deploy pipeline and the account-granting.

**FACT — HIGH.** **Tasmota** is the same shape at larger scale: **2,861 device templates** at [templates.blakadder.com](https://templates.blakadder.com/), submitted through **an embedded Google Form** into one person's Jekyll site ([blakadder/templates](https://github.com/blakadder/templates)) — a catalog the Tasmota project *points at* but does not own. Its newer *official*, CI-validated channels (`tasmota/autoconf`: **578 commits, 16 stars**; `.tapp` extensions) are orders of magnitude smaller.

**INFERENCE — HIGH.** Governance and volume moved in **opposite** directions in both cases. And every high-volume community data surface examined — blakadder, cd-jackson/OpenSmartHouse, ludeeus/HACS — is **a single-maintainer dependency of a much larger project**. That is wars-dossier **L-26** confirmed from four fresh angles, and it is the mirror pm-handoff **X-3** already turns on us.

**FACT — HIGH.** The converter-DB pipeline design (2026-06-26) **already specifies the inbound path**, and specifies it correctly: *"The IR + DeviceProfile schema (Doc 08 §3.6) is the contribution unit… This is the *same artifact the embed pipeline emits*, so contributions and machine-ingest converge on one format"*; the `CustomCapability` namespace is *"the contribution sandbox"*; and *"The human-review gate (§1.2) is the contribution merge gate — community submissions enter at the same Stage-4→5 gate as machine output, so quality control is uniform."* §6 marks the mechanism **DEFERRABLE**: *"design now (done, §3.2), stand up during/after M9."*

**INFERENCE — HIGH — the answer to Q-1.** Yes: **the profile/converter data channel is the correct first community surface**, and our design already satisfies the two properties the survey says decide the outcome — *same artifact both directions* (§3.2 makes the IR/DeviceProfile the contribution unit **and** the emit target) and *a merge gate already designed* (Stage 4→5). What is missing is small and named:

1. **Wire `loadUserProfiles` to a config key** and document the path — the zero-review day-1 side-load, turning a cut seam into a connected one. *(Post-gate WU; **this lane sizes it, the hub authors it**.)*

It joins the on-ramp, not the licensing backlog.

**OPINION — MED-HIGH.** Do **not** build a code-plugin on-ramp at launch, and do not promise one. The field's leader just turned its own off by default (§1.3); Doc 18's ladder rungs 1–4 are unbuilt and the **honesty rule (DP-18-B)** forbids any sandbox language until they enforce. The honest launch posture is the Obsidian shape the wars dossier isolated as **L-4** — *third-party code off by default, the access stated plainly, the user as explicit trust authority* — except we do not even need the toggle, because we ship no code-plugin loader at all. **Say that plainly; it is a stronger sentence than a sandbox promise.**

## §2 — Q-2: THE GOVERNANCE MINIMUM SET

### 2.1 The frame: GitHub's own checklist *is* the minimum set, as a contributor sees it

**FACT — HIGH.** GitHub's community profile checklist checks for exactly six things: **README, CODE_OF_CONDUCT, LICENSE, CONTRIBUTING, issue templates (`.github/ISSUE_TEMPLATE`), and a security policy** ([about community profiles](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/about-community-profiles-for-public-repositories)). CONTRIBUTING surfaces as a repo tab, a sidebar link, a `/contribute` page, and a banner when someone opens an issue or PR ([setting guidelines](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors)).

**INFERENCE — HIGH.** That six-item list is the cheapest, highest-visibility legitimacy signal available to a pre-launch project. We currently score **2/6, 1/6, 1/6, 1/6** (§1.1) — and in the two repos where LICENSE is present it is a proprietary licence, which for a project presenting as open source reads worse than absence. **Recommend: land the missing five per repo as one commit per repo, in the same push as the flip**, rather than dribbling them out; landing them piecemeal advertises exactly the improvisation X-3 is worried about.

### 2.2 DCO vs CLA — RECOMMEND the **DCO** as the mechanism; the licence-effect question goes to counsel

**FACT — HIGH.** Apache-2.0 **§5**, verbatim: *"Unless You explicitly state otherwise, any Contribution intentionally submitted for inclusion in the Work by You to the Licensor shall be under the terms and conditions of this License, without any additional terms or conditions."* ([LICENSE-2.0.txt](https://www.apache.org/licenses/LICENSE-2.0.txt)) The ASF nevertheless requires an ICLA, stating the purpose is *"to clearly define the terms under which intellectual property has been contributed… and thereby allow us to defend the project should there be a legal dispute"* ([contributor-agreements](https://www.apache.org/licenses/contributor-agreements.html)).

**This lane does not interpret §5.** What each instrument *does legally* — and in particular whether a CLA's residual value for this project reduces to a relicensing option — is **§2.6(ii), for counsel**. What follows is the mechanism-and-cost case, which is what Q-2 asks for.

**FACT — HIGH — the measured friction.** **Dolt dropped its CLA on 2021-04-05** reporting that **"9 out of 10 potential contributors did not sign it,"** having concluded the CLA and Apache-2.0 overlapped; framing: *"Asking for a CLA on a small PR is like asking for a prenuptial agreement on a first date."* ([dolthub.com/blog/2021-04-05-no-cla](https://www.dolthub.com/blog/2021-04-05-no-cla/)). **Helm moved CLA→DCO on 2018-08-27**: *"It is often easier to get started contributing under a DCO than a CLA"*, and the corporate signing path *"can take weeks or longer"* ([helm.sh/blog/helm-dco](https://helm.sh/blog/helm-dco/index.html)).

**FACT — HIGH — peer postures, each read at source.**

| Project | Contributor agreement | Source |
|---|---|---|
| **Home Assistant** | **A file named "CLA" that is functionally the DCO** — clauses (a)–(d) are DCO 1.1 text with the licence swapped to Apache-2.0. Self-describes: *"It is based on the Linux Developer Certificate Of Origin, but is modified to explicitly use the Apache 2.0 license and not mention sign-off."* **No copyright assignment, no separate patent grant, no sign-off.** Adopted 2017-01-28. | [core/CLA.md](https://raw.githubusercontent.com/home-assistant/core/dev/CLA.md) |
| **openHAB** | **DCO sign-off required.** Two exemptions (spelling/grammar; single-line docs). No CLA. | [openhab-core CONTRIBUTING](https://github.com/openhab/openhab-core/blob/main/CONTRIBUTING.md) |
| **Node-RED** | OpenJS Foundation CLA — a consequence of foundation membership. | [node-red CONTRIBUTING](https://github.com/node-red/node-red/blob/master/CONTRIBUTING.md) |
| **ESPHome / Zigbee2MQTT / Homebridge** | **None.** | [esphome](https://github.com/esphome/esphome/blob/dev/CONTRIBUTING.md) · [z2m](https://github.com/Koenkk/zigbee2mqtt/blob/master/CONTRIBUTING.md) · [homebridge](https://raw.githubusercontent.com/homebridge/.github/latest/CONTRIBUTING.md) |

**INFERENCE — HIGH.** Home Assistant is the closest structural analogue we have — company/foundation presence, Apache-2.0 posture, a foundation-held mark — and it took **neither assignment nor relicensing rights** while keeping the ceremony. Three of six peers take nothing at all. Whatever counsel concludes on §2.6(ii), **the peer set does not support a CLA on precedent.**

**RECOMMENDATION (mechanism — pending §2.6(i)(ii)): adopt the DCO, enforced by the DCO GitHub App.** **FACT — HIGH:** the app (`dcoapp/app`, Probot, ISC) *"enforces the presence of valid DCO signoffs on all commits (excluding bots and merges)"*, fails the PR status otherwise, and is configured via `.github/dco.yml` with `allowRemediationCommits` ([dcoapp/app](https://github.com/dcoapp/app)). Contributor cost is `git commit -s`. **DCO 1.1** is at [developercertificate.org](https://developercertificate.org/); CNCF's guidance calls it *"in use by thousands of projects to avoid more burdensome requirements to contribute (such as a CLA)"* and clarifies *"a real name does not require a legal name"* ([cncf dco-guidelines](https://github.com/cncf/foundation/blob/main/policies-guidance/dco-guidelines.md)).

### 2.3 Code of conduct — RECOMMEND **Contributor Covenant 3.0**, with the reporting section honestly filled

**FACT — HIGH.** **Contributor Covenant 3.0** is current, announced **2025-07-28** by the Organization for Ethical Source; CC BY-SA 4.0; four-tier enforcement ladder (Warning → Temporarily Limited Activities → Temporary Suspension → Permanent Ban) with the qualifier that it *"is intended as a guideline"* ([announcement](https://ethicalsource.dev/blog/contributor-covenant-3/) · [text](https://www.contributor-covenant.org/version/3/0/code_of_conduct/)). **The Reporting section is a literal placeholder:** *"To report a possible violation, **[NOTE: describe your means of reporting here.]**"*

**FACT — HIGH — the burden, in GitHub's own guide.** *"A code of conduct that isn't (or can't be) enforced is worse than no code of conduct at all."* It requires a private reporting channel with a named recipient, recommends **an alternative path for when the primary recipient is the subject of the complaint**, and states *"When somebody reports a code of conduct violation, it is your, not their, job to handle it."* ([opensource.guide/code-of-conduct](https://opensource.guide/code-of-conduct/))

**FACT — HIGH — the actual caseload.** The **Linux Kernel Code of Conduct Committee report for 2025-04-01 → 2025-09-30 records THREE total reports** in six months, two of which were scope/education questions ([LKML report](https://lkml.iu.edu/hypermail/linux/kernel/2510.3/09858.html)).

**INFERENCE — MED.** If the Linux kernel generates ~3 reports per six months, the steady-state caseload for a new single-founder project is **near zero**. The burden is not adjudication volume. It is (a) monitoring a private channel, and (b) **tail risk: one high-conflict incident with no second human to escalate to.**

**FACT — MED, carried WITHOUT an opened URL — stated so explicitly.** The failure mode of having no body above the enforcement body is reported as the **November 2021 mass resignation of the Rust moderation team**. **RECOMMENDATION (OPINION — MED-HIGH).** Adopt **Contributor Covenant 3.0** unmodified except for Reporting, and fill that section **honestly**: a single monitored address under {COMPANY}, and — if there is only one recipient — **say so in the document**. Naming a second recipient is the cheapest hardening available and needs no co-founder (an advisor, a faculty contact, or the fusion record's bounded-trial collaborator would each discharge it) — **but it requires that person's consent first, which is an outreach act and therefore post-gate.** Counsel item: §2.6(v).

**Recorded for balance (OPINION — MED, cited).** Shuji Sado, **2025-09-30**, argues complex CoCs impose administrative cost on volunteer projects and that *"the rhetoric of strengthening governance… can be used not to protect the community, but to strip it of its authority"* ([shujisado.org](https://shujisado.org/2025/09/30/why-heavy-codes-of-conduct-are-unnecessary-for-most-open-source-projects/)). ### 2.5 SECURITY.md + the disclosure channel (X-2 operationalized)

**FACT — HIGH — GitHub Private Vulnerability Reporting (PVR).** *"Anyone can privately report a security vulnerability to repository maintainers."* It is **opt-in, off by default, public repos only**, enabled at Settings → Security → Advanced Security. **Critically: *"Private vulnerability reporting is separate from a repository's SECURITY.md file."*** GitHub auto-adds the reporter as a credited collaborator on the draft advisory. ([privately reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability) · [configuring PVR](https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/configuring-private-vulnerability-reporting-for-a-repository))

**FACT — HIGH.** GitHub is an authorised **CNA**: a maintainer may request a CVE from within a draft advisory and GitHub *"usually reviews the request within 72 hours"*; *"Requesting a CVE identification number doesn't make your security advisory public."* On publication the advisory enters the GitHub Advisory Database and can raise Dependabot alerts. ([about repository security advisories](https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/about-repository-security-advisories))

**INFERENCE — HIGH.** PVR + draft advisory + optional CVE is **a complete coordinated-disclosure pipeline with zero external infrastructure** — no HackerOne, no PGP mailbox, no third-party account. For a solo maintainer that is the correct default, and it costs one settings toggle. **It must be toggled explicitly**; a SECURITY.md alone does not enable it.

**FACT — HIGH — what peers promise, and refuse.**

| Project | Promises | Explicitly does NOT promise |
|---|---|---|
| **Syncthing** | One sentence: email `security@…`, PGP key offered. | Nothing. No response time, no timeline, no embargo, no credit, no bounty. ([SECURITY.md](https://raw.githubusercontent.com/syncthing/syncthing/main/.github/SECURITY.md)) |
| **curl** | Human acknowledgement; distros notified ≤7 days pre-release; master merge ≤48h pre-release; credit all reporters. | **No response-time SLA.** *"There is no bug bounty and the curl project never offers rewards."* Refuses email intake: *"We lose track of the reports."* ([secprocess](https://curl.se/dev/secprocess.html)) |

**RECOMMENDATION (OPINION — MED), with its own tension named.** SECURITY.md that routes to **PVR as the only intake** (curl's reason: email loses reports); states supported versions; credits reporters by default; and states **explicitly that there is no bug bounty and will not be one** — see §3.1 for why that sentence is load-bearing rather than decorative.

### 2.7 Trademark policy — the seventh governance file nobody lists

**FACT — HIGH — the converged shape**, from four policies read this lane: [Rust Foundation](https://rustfoundation.org/policy/rust-trademark-policy/) · [PSF](https://www.python.org/psf/trademarks/) · [Linux Foundation](https://www.linuxfoundation.org/legal/trademark-usage) · [Mozilla](https://www.mozilla.org/en-US/foundation/trademarks/policy/). **FACT — MED — the backlash case, and what it was about.** The Rust Foundation's **April 2023 draft** clause 4.3.1 read: *"Using the Marks in the name of a tool for use in the Rust toolchain, a software program written in the Rust language, or a software program compatible with Rust software, will most likely require a license"* — which would have made long-standing package names (`intellij-rust`, `rust-postgres`, `rust-libp2p`…) infringing ([devclass, 2023-04-11](https://devclass.com/2023/04/11/dont-call-it-rust-community-complains-about-draft-trademark-policy-restricting-use-of-word-marks/)). The Foundation's **2024-11-06** post enumerates the concerns received; the **2025-01-23** post records what shipped, including the direct repeal: *"Use 'Rust' in the name of crates or code repositories… when referring to use with or compatibility with the Rust programming language"* ([updates](https://rustfoundation.org/media/rust-trademark-policy-updates/) · [explained](https://rustfoundation.org/media/rust-language-trademark-policy-updates-explained/)). **INFERENCE — HIGH: the failure mode was retroactivity against established naming convention, not the existence of a policy.**

## §3 — Q-3: SOLO-MAINTAINER SUSTAINABILITY

### 3.1 The base rates, and the one controlled experiment

**FACT — HIGH.** Tidelift **2024 State of the Open Source Maintainer Report** (n=437, fielded mid-2024, published Sept 2024): **60% unpaid hobbyists**; **60% have quit or considered quitting** (22% quit, 38% considered); **61% of unpaid maintainers work solo vs 26% of paid**; 48% feel underappreciated, **32% describe it as lonely**; post-xz, **66% report decreased trust in non-maintainer pull requests**; **64% would be less willing to review AI-generated contributions**. Paid maintainers outperform unpaid on every governance practice by ~22–26 points. ([report PDF](https://assets-eu-01.kc-usercontent.com/ef593040-b591-0198-9506-ed88b30bc023/d325a56f-05be-4379-bfd1-ee4776fcad41/2024-tidelift-state-of-the-open-source-maintainer-report-.pdf))

**INFERENCE — HIGH.** Funding does not reduce **demand**; it buys **hours** and, decisively, **co-maintainers** — the 61%→26% solo-rate gap is the mechanism. GitHub's own framing at the Sponsors $100M mark (post ~2026-07-21): *"the open source funding gap is still enormous… maintainer burnout continues to be one of the biggest risks to the software supply chain"* ([github.blog](https://github.blog/open-source/maintainers/100-million-for-open-source-a-milestone-built-by-the-community/)).

**FACT — HIGH — the arc to internalise, because it is close to a controlled experiment.** curl:
- **2025-07-14** — quantifies the load: ~20% of 2025 submissions AI slop; **"Every report thus engages 3-4 persons. Perhaps for 30 minutes, sometimes up to an hour or three. Each."** Team members have as little as three hours a week. ([Death by a thousand slops](https://daniel.haxx.se/blog/2025/07/14/death-by-a-thousand-slops/))
- **2026-01-26** — **kills the bug bounty**, effective 2026-01-31. Confirmation rate fell from >15% to <5% in 2025; 87 confirmed vulnerabilities and >$100,000 paid since 2019. *"The never-ending slop submissions take a serious mental toll… Time and energy that is completely wasted."* ([The end of the curl bug-bounty](https://daniel.haxx.se/blog/2026/01/26/the-end-of-the-curl-bug-bounty/))
- **2026-05-26** — **still overloaded.** *"having that list of potential security problems in a list that you don't have control over takes a mental toll"*; *"For the first time in my life, my wife voiced concerns about my work hours"*; *"I might soon have to reduce my work hours."* ([The pressure](https://daniel.haxx.se/blog/2026/05/26/the-pressure/))

**INFERENCE — HIGH — the transferable lesson.** **Removing an inflow mechanism after the fact reduced one channel and did not restore sustainability.** You cannot solve load by subtraction once the expectation exists. The only cheap move is **not creating the inflow** — which is why §2.5's "no bounty, and there will not be one" sentence is load-bearing, and why §3.4's C-3 shaping matters more than any triage discipline we could later adopt.

**FACT — MED-HIGH — the cleanest written no-SLA declaration found.** libxml2, June 2025: **"The basic idea is to treat security issues like any other bug. They will be made public immediately and fixed whenever maintainers have the time."** Triaging reports *"of questionable severity"* took *"several hours each week"*, unpaid. *(MED-HIGH: the primary GitLab issue returned HTTP 406; quotes are via [Socket.dev, 2025-06-17](https://socket.dev/blog/libxml2-maintainer-ends-embargoed-vulnerability-reports), which names the primary.)*

### 3.4 C-3 — who owns the nightly-numbers publishing obligation

**INFERENCE — MED (a universal negative from one internal survey; R-1 §6.4 via the adjudication).** The differentiator is real: no competitor is known to publish reliability data. This is the premise of everything below and it deserves a re-check before it goes on a public surface.

**FACT — HIGH — the only decade-scale exemplar of continuously published performance numbers was sunset ~March 2026.** **TechEmpower Framework Benchmarks.** The announcement is terse — *"Today, with a full heart, we're announcing that we're sunsetting the project"* — and **gives no reasons**; the rendered page exposed neither author nor date to the fetch ([issue #10932](https://github.com/TechEmpower/FrameworkBenchmarks/issues/10932)).

**FACT — MED (secondary; two accounts, both dated 2026-03-24) — the reported mechanics.**
- Cost: **"Running a full round takes weeks of compute time and significant human oversight. TechEmpower's team, by all accounts, is small."**
- Structural fragility: *"a project this influential shouldn't depend on the bandwidth of a single company's employees."*
- Gaming: **"Framework authors would optimize specifically for TechEmpower tests, sometimes creating dedicated benchmark configurations that bore little resemblance to production deployments."**
- Obligation transferred to others: *"Some framework authors reported that their pull requests sat unreviewed for months."*
- The trap: **"Performance numbers carry an implicit promise of objectivity"** and **"When the process behind those numbers becomes opaque or inconsistent, the numbers themselves lose credibility."**
([webpronews](https://www.webpronews.com/the-benchmark-that-broke-how-a-single-github-issue-exposed-the-fragile-politics-of-web-framework-performance-testing/) · [dev.to](https://dev.to/kaliumhexacyanoferrat/techempower-framework-benchmarks-are-now-archived-whats-next-3l0a))

**FACT — HIGH — the counter-exemplar, and its cost.** Rust's compiler-performance triage is performed **weekly by a named roster of four**, timed *"Monday evening to Tuesday afternoon in North America"* to feed This Week in Rust on Wednesday. The duty includes checking prior follow-ups, generating reports, analysing instruction counts / max RSS / binary size, **pinging PR authors about regressions**, and — for substantial regressions — **requesting reversion**. ([rustc-perf triage README](https://github.com/rust-lang/rustc-perf/blob/master/triage/README.md); triage logs continue into 2026.)

**INFERENCE — MED-HIGH.** Publishing numbers continuously converts into **(1) a standing weekly human triage duty that never ends, and (2) a social-enforcement obligation on every contributor whose change appears in the numbers.** Rust sustains this with a foundation and a four-person rotation; the one project that tried it at scale without that structure ended after a decade. *(MED-HIGH rather than HIGH because TechEmpower's own announcement states no cause — see the label split above.)*

**Reported as absence — do NOT assert this in the charter.** No maintainer statement was found of the form "publishing our own regression damaged us," and no case of a project suppressing or delaying a regression because it was public. **The evidenced trap is process-maintenance and credibility-of-process, not reputational damage from an honest bad number.** C-1 messaging should not claim otherwise.

**RECOMMENDATION (OPINION — MED-HIGH) — reshape the obligation so it needs no owner.** The honest answer to X-3's *"WHO OWNS the nightly-numbers publishing obligation during fall semester"* is: **nobody can own a standing weekly human duty on an unquantified attended-hours budget (§3.2). So the obligation must be shaped to require no human on a schedule.** Concretely:

1. **Publish a machine-authored artifact, not a curated report.** The digest publishes automatically; no human is in the publication path.
2. **Ship the C-3 pre-reqs as fields of that artifact, not as prose**: pinned governor · N repetitions · published variance bands · an explicit rig-scope statement. They are already ruled; making them *fields* is what makes them survive inattention.
3. **State the no-triage posture on the page itself**: regressions publish unreviewed and are triaged when attended. That converts an implied SLO into a disclosed property.
4. **Never accept externally-submitted benchmark configurations.** One rule forecloses the exact mechanism reported at TechEmpower (optimizing-for-the-metric plus an inherited review queue from every party whose number appears). Our rig is our rig; other people's numbers are not our obligation.
5. If (1)–(4) cannot be met by the charter, **defer C-3 by name** rather than shipping a number that implies attention we cannot pay. A deferred differentiator is recoverable; a lapsed public commitment is the TechEmpower ending.

**OPINION — MED-HIGH.** Rule 4 is also a positioning asset: "we publish our own rig's numbers, including regressions, and we do not accept tuned submissions" is a *narrower and more credible* claim than an open benchmark, and it is the version one person can hold for years.

## §6 — Q-6: THE COMPOUNDING FRAME

*(Substrate Thesis §11 precedence observed: where the thesis conflicts with source, governance artifacts, or direct system knowledge, those win. Claims below are grounded in Doc 18, the register, the north star and the repo; the thesis supplies the paradigm layer only.)*

### 6.1 Why community + plugins compound the substrate thesis rather than merely accompanying it

The thesis's corollary is that anything built *underneath* the model — enforcing, attributing, bounding what it proposes — is made **more valuable by every model improvement**. The plugin argument is that corollary with the actor generalised:

**INFERENCE — HIGH. Every extension is another proposer.** The kernel makes no assumption about what produced a proposal — *"Frontier model, local 3B, or a hand-written rule — same adjudication path, same guarantees"* (north star). A third-party extension is one more entry in that set. The value of the enforcement-and-attribution layer therefore grows with the **number of distinct proposers**, and a plugin ecosystem is the cheapest available way to grow that number.

**INFERENCE — MED-HIGH — the superlinear part.** The log's value grows faster than the proposer count because it becomes **the only place where cross-vendor, cross-author causality is reconstructable**. One vendor's device misbehaving inside another author's automation, adjudicated by the same kernel and recorded in one hash-chained order, is a fact no per-vendor system can produce. That is the community→substrate compounding loop, and it is the honest sense in which plugins are strategic rather than merely popular.

### 6.2 The plugin TRUST story — stated under the language law (D5)

**The claim, in the only form it may be stated:**

> The field's extension-security posture is **L2/L3-shaped**: review the code, judge the artifact, scan every version, revoke on discovery. Those are the right instruments and we need every one of them — **L1 without L2 is insufficient.** A deterministic floor cannot evaluate whether an extension is contextually harmful, deceptive, or badly intentioned; that is exactly what review, the two-tier split, the quality ladder and revocation are for.
>
> What is **missing** beneath those instruments, across every ecosystem surveyed, is a **categorical floor** — an adjudication point that bounds what any extension can *cause*. **L2/L3 without L1 are unsound:** a probabilistic filter with no categorical floor beneath it provides no guarantee, only a lowered error rate. **The floor is missing from the field, not superior to what the field has.**
>
> The correct posture is layered defence with a deterministic floor beneath the reviewed tiers.

**INFERENCE — HIGH.** This is the one claim we can make truthfully **today**, because it is a property of the single-writer total order that already exists — not of a rung we have not built. It stays inside DP-18-B's honesty rule by construction, because it makes no isolation claim at all. And it composes with C-1: *nothing watches the watcher* is the same argument one layer down.

**INFERENCE — HIGH — the mechanism that carries it is already minted.** **EXT-INV-2 (capability declared, not discovered)** is the manifest-as-trust-contract pattern the wars dossier isolated as the most-repeated trust win in the field (**L-5, L-7**) — and it is the **same** pattern the 2026 registry material converged on independently (§4.2: declared single purpose, namespace proof, pre-publication machine checks). **Declared capability is machine-checkable; machine-checkable is what survives an AI-authorship volume era** (L-31, L-32; Chrome's safe declarative rule updates publish in minutes). The invariant was minted 2026-07-03 and the independently-dated field material — Feb–Aug 2026 — runs the same way. **That convergence is worth one sentence in the charter and zero further work.**

### 6.3 Where community input feeds the bets table

**INFERENCE — MED-HIGH.** The device-profile corpus is not just a breadth asset; it is the **input three named bets already need**:

1. **C-2 (the sleepy/battery position paper)** requires per-device-class reporting contracts. A community profile channel is the only mechanism that produces those at scale — the contract *is* profile data.
