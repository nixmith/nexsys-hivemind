## §1 — D-1: THE PLUGIN-SYSTEM TIMING MEMO

*Not a date — CONDITIONS.*

### 1.1 The finding that reorders the question

**INFERENCE — HIGH. "When does plugin-system development start" is not one decision. It is three, with three different forcing events, three different cost curves, and — this is the part that matters — the cheapest one to defer is the one everybody means when they say "plugin system."**

Doc 18 reserves **seven** seams. The field evidence sorts them into three groups that have almost nothing to do with each other in timing terms:

| Layer | Doc 18 seams | State today | What forces the decision | Cost of being late |
|---|---|---|---|---|
| **(A) The extension CONTRACT** | §3.1 (the frozen SPI, restated not owned) + seam 5 (namespace & identity) | **EXISTS, FROZEN, V1-REAL** (L-B §4.1) | Nothing — it is done | n/a |
| **(B) The DISTRIBUTION / INDEX** | seams 6–7 (packaging & distribution; marketplace trust floor) | Nothing built, nothing scheduled | **The first unofficial installer or index someone else publishes** | **HIGH and permanent** — see §1.6 (HACS) |
| **(C) The LOADER and its machinery** | seams 1–4 (dynamic loading; operation registry; event-manifest layering; trust-boundary ladder) | Nothing built; enum slot + empty permit reserved | A third party who cannot do what they need with data alone | **LOW** — see §2.3 |

**INFERENCE — HIGH, and it is counter-intuitive.** The loader is the **cheapest** of the three to defer, because LTD-17 pre-authorizes the swap and the SPI's narrow two-type contract is process-agnostic — the Homebridge precedent (**L-3**) proves per-plugin subprocess isolation retrofits as *pure configuration, zero plugin code changes*, when the contract stayed process-agnostic. The **distribution layer** is the expensive one to defer, and it is the one Doc 18 correctly builds nothing of and — equally correctly — does not put a clock on. **This memo's main contribution is to put a clock on (B) and to say plainly that (C) does not need one.**

**Restating the boundary so it is not lost:** none of this reopens Doc 18. Doc 18 §4 row 1's proposed LTD-17 amendment shape stays *proposed, not assumed*; OQ-2 stays non-blocking; OQ-3 stays open with L-B's three added rows (**A-11**). This memo supplies **conditions for when each layer's question becomes live**, which is the one thing a Locked reservation doc deliberately does not carry.

#### **T-1 — Extension-surface API stability across N public releases**

**VERDICT: KEEP, but it is currently UNMEASURABLE, and that is the finding.**

- **How measured.** Count of consecutive *public* releases in which the two-type SPI, the `IntegrationDescriptor` surface, and the event-class manifest contract ship unchanged in any way that would break a third party. Breaking = anything a third-party adapter compiled against release *n* would fail on at release *n+1*.
- **Current reading — FACT, HIGH.** **ZERO.** There is no public release. The contract is **frozen in development** (AMD-54..64) with shipped test fixtures, which is a strictly weaker property than *stable across shipped releases* — a freeze is a discipline we hold on ourselves; stability is a promise third parties can rely on. L-B §4.1 verifies the contract as V1-REAL; it does not and cannot verify release-stability, because there are no releases.
- **The hidden prerequisite — INFERENCE, HIGH.** N cannot even be *expressed in wall-clock* until the release cadence is decided. Doc 18 §7 item 2 (OQ-1, ruled at co-sign 2026-07-03) pins the deprecation floor at **six release cycles + a Repairs-class automated-migration surface, SEMANTIC PINNED**, with the explicit note that *"'release cycle' is re-expressed in wall-clock terms when the release cadence is decided — monthly → 6 months, quarterly → 18 — the semantic pin exists precisely because the cadence is undecided."* **The release-cadence decision is a prerequisite to measuring this trigger at all**, and it is a prerequisite to two further things (§5.1 finding 3).
- **Earliest plausible date — INFERENCE, MED.** First public release is downstream of X-1 → the LICENSE flip → MVP, which the north star targets for **late 2026**. Taking N=6 as the floor the project already ruled for deprecation: **mid-2027 at monthly cadence; late 2028 at quarterly.** The range is wide *because the cadence is undecided*, not because the estimate is soft.
- **Field calibration — FACT, HIGH.** The strongest counter-exemplar says the *stability promise* is a separate, later, revocable-once product from the *API*. Visual Studio Code shipped the extensibility model at Connect();2015, let the community build **"over 1000 extensions"** against an unpromised API, and only at **1.0 on 2016-04-14** said: *"With this great ecosystem in place, we're now confident in declaring our API as stable, and guaranteeing compatibility going forward."* ([code.visualstudio.com/blogs/2016/04/14/vscode-1.0](https://code.visualstudio.com/blogs/2016/04/14/vscode-1.0), primary). Obsidian did the same with a label: the plugin API opened **2020-10-26** carrying *"Keep in mind that the plugin API is in `alpha` status. Any part of the API could introduce breaking changes in a future release"* ([obsidian.md/changelog/2020-10-26-desktop-v0.9.7](https://obsidian.md/changelog/2020-10-26-desktop-v0.9.7/), primary), and only called the app 1.0 on **2022-10-13** — two years later. Kubernetes ran CRDs in explicit **beta from 1.7 (2017) to GA at 1.16 on 2019-09-18** ([kubernetes.io/blog/2019/09/18/kubernetes-1-16-release-announcement/](https://kubernetes.io/blog/2019/09/18/kubernetes-1-16-release-announcement/), primary) — ~2 years, 9 minor releases, with a published mechanical deprecation policy.
- **What this changes about the trigger — INFERENCE, MED-HIGH.** T-1 as literally stated ("stability across N releases") describes the moment we may **promise** stability. It does **not** describe the moment we may **open** an extension surface, because three of the field's healthiest ecosystems opened theirs while explicitly disclaiming stability. **The trigger should be split**: an *opening* condition (the contract exists and is documented — already true) and a *promising* condition (N releases unchanged — currently zero). Conflating them is what makes the plugin question feel further away than it is on the data side and nearer than it is on the promise side.

#### **T-2 — ≥K external converter/profile contributions signalling real demand**

**VERDICT: KEEP, and it is the best of the four — but K is not the interesting number.**

- **How measured.** Count of merged, externally-authored device-profile/converter contributions after the user-override channel is wired and the submission format is published. Distinct external authors is the better co-metric than raw count.
- **Current reading — FACT, HIGH (host-verified in the record).** **ZERO, and structurally so.** `loadUserProfiles` exists with **zero callers**; `ProfileSource.USER(0)` already outranks BUNDLED; there is no config key; the bundled corpus is **6 profiles at `schemaVersion 1.0`** (L-B §4.1, §1.6; host-confirmed at the beat-4 adjudication, **A-5**). There is no channel, therefore no contributions, therefore no signal.
- **Earliest plausible date — INFERENCE, MED-HIGH.** L-B §7.2 act **1.1** ("wire the profile user-override channel") is **Small** and **⚙ gate-independent** — the loader and precedence rank already exist. But *contributions* need an audience, and the audience needs the launch, which needs X-1 → the LICENSE flip. So: **channel wireable now; signal not readable until post-launch.**
- **The datum that reframes K — FACT, HIGH.** In the closest comparable ecosystem, **the seam was used the day it existed.** `zigbee-herdsman-converters` — the library that made device definitions a contribution unit — has its **first commit on 2018-05-23**, and its **first external contribution (Kirov Ilya, "Added device model to parser parameters", merged as PR #1) merged the same day, 2018-05-23**. (Dated from the merge commits; the GitHub API was unavailable to this lane, disclosed in §0.4(9).) Today that ecosystem states **"Currently 5521 devices are supported from 583 different vendors"** ([zigbee2mqtt.io/supported-devices](https://www.zigbee2mqtt.io/supported-devices/), primary, accessed 2026-08-01).
- **And the shape of the first contributions — FACT, HIGH.** Of the first thirteen external contributions to that project, **nine are device/vendor adapters** — "my device isn't supported." Not features, not refactors, not docs. This **independently corroborates L-B Q-1's answer** (the converter/profile channel is the day-1 on-ramp) from a direction L-B did not use, and it is the reason K is the wrong knob.
- **What this changes about the trigger — INFERENCE, HIGH.** **K is not a demand signal we wait for; it is an output we switch on.** The evidence says the arrival rate is set by the seam's existence and the audience's size, not by latent enthusiasm accumulating somewhere. So T-2's honest form is: *K measures whether the data channel is working, and it is the input to the CODE-channel question — not to the distribution question and not to the contract question.* A high K with a healthy review load is the evidence that **more data-first surface** is the right next move (Doc 18 principle 4); a high K with a drowning review load is the evidence for the **distribution** layer, not the loader.

- **Current reading — FACT, HIGH.** **ZERO, necessarily** — there is no public repo, so there is nothing to build an installer for.
- **Earliest plausible date — INFERENCE, MED.** Not before launch. After launch, it is a function of contribution volume and of how visible the discovery gap is. In the closest comparable ecosystem the gap was filled within roughly **five months** of the predecessor tool being publicly deprecated (§1.6).
- **Why it is a trigger and not a risk — INFERENCE, HIGH.** Because the response window closes. §1.6 documents what happens on each side of it.

#### **T-6 — ADDED: a third party needs the CODE channel and says so**

**VERDICT: ADD. It is the only honest trigger for seams 1–4, and it costs nothing to wait for.**

- **How measured.** A concrete, named use case from outside {COMPANY} that the data channel provably cannot serve — i.e. someone who needs to *execute*, not to *describe*.
- **Current reading — FACT, HIGH.** **ZERO** (no public surface). And note the asymmetry the record already carries: adjudication **A-6** rules that *the category moved AWAY from in-process third-party code this quarter*, making Doc 18's data-first principle *"the direction of travel, not the cautious option."*
- **Why this is the right trigger — INFERENCE, HIGH.** Doc 18 principle 4 already ranks data-first above code-first as the *widest, safest on-ramp that ships value before any code-plugin machinery exists*. The wars dossier's **L-22** (staging-area model as the strongest anti-rot pattern: 5,473 devices on bus-factor ~1.5) is the same finding from the field. **Waiting for T-6 costs nothing, because the loader's retrofit cost does not rise while we wait** (§2.3) — which is precisely what makes it different from T-5.

### 1.5 FAILURE MODE ONE — TOO EARLY, with dated ecosystem exemplars

*Two distinct sub-modes: the API churns and breaks third parties; and the registry is thin, which reads as dead.*

#### (a) API churn breaks third parties

**FACT — HIGH. Notice length is not the variable that predicts survival. A mechanical, drop-in migration path is.** Four dated cases, in descending order of notice given:

|---|---|---|

**FACT — HIGH. The replacement API is what gets shipped too early, not the original.** Chrome opened Manifest V3 on **2020-12-09** while naming its own gaps in the same post (*"expect more functionality and iteration as we continue to incorporate feedback and add new features"*), then spent three years filling them — **Offscreen Documents 2023-01-25 (Chrome 109)**, **userScripts 2023-11-02 (Chrome 120)** — while the MV2 deprecation slipped from an announced **January 2023** (stated 2021-09-23) to **2025-07-24** (Chrome 138, the last version supporting MV2). **FACT — HIGH, and this is the datum that reframes the whole failure mode. Most of any mature registry is already dead before you break anything.** Peer-reviewed measurement of the Chrome Web Store (**124,094 extensions as of Feb 2023**; Hsu, Tran & Fass, ACM AsiaCCS 2024, [arXiv:2406.12710](https://arxiv.org/abs/2406.12710)):

- ***"60% of the extensions in the CWS have never been updated"*** — precisely **73,865 (59.5%)** never updated since being added.
- ***"the median number of updates an extension receives after a year in the CWS is 0, and the average is 0.16."***
- ***"only 51.86–62.98% of extensions are still available after one year"*** (median 60.39%).
- ***"on average, 3,775 extensions are removed from the CWS every month and another 2,687 are added"*** — the store is net-shrinking by unit count.

Corroborating shape on npm: **8.2% of the top 50,000 most-downloaded packages officially deprecated, rising to ~21% under extended definitions** (archived repos, unavailable repos, no linked repo), representing **2.1 billion weekly downloads** ([Aqua Security, 2024-01-18](https://www.aquasec.com/blog/deceptive-deprecation-the-truth-about-npm-deprecated-packages/), vendor research).

**INFERENCE — HIGH.** Two consequences follow, and both are directly load-bearing for us. **First**, a breaking change does not break "some" extensions — it instantly reclassifies the *majority* of a mature catalog as broken, because the majority was already unmaintained. **Second**, the metric everyone reports is constructed to hide this: Chrome's *"Over 85% of actively maintained extensions in the Chrome Web Store are running Manifest V3"* ([blog.google/chromium, May 2024](https://blog.google/chromium/manifest-v2-phase-out-begins), primary) is true and excludes exactly the population that breaks. **Any future {PRODUCT} extension-health metric must report the denominator, or it will lie to us the same way.**

**INFERENCE — HIGH. Three and a half years stuck between 9 and 18, then 2.5× growth in under five months once the gate opened.** The bottleneck was never developer supply; it was the curated allowlist. **The lesson that transfers: a registry that is thin *because you are gatekeeping* looks identical, to a user, to a registry that is thin *because nobody came* — and users punish both the same way.** Doc 18 §4 row 7's *default-off unreviewed tier* and *two-tier labelled split* are exactly the mechanism that lets a registry be both curated and non-empty; this evidence is why that row's shape matters more than its timing.

**FACT — HIGH. And a thin registry is not merely unimpressive — its named gaps are an attack surface.** Open VSX went from **"more than 900 extensions"** (Eclipse newsletter, January 2021) to roughly **16,000** (measured by this lane against the public search API's `totalSize` field on 2026-08-01; two calls minutes apart returned 16,005 and 16,229 — method disclosed, treat as ~16k), against an incumbent that went from *"more than 20,000"* (2021-03-30) to **93,862** (2026-03-03). **INFERENCE — HIGH, and it converges with something already in the record.** Opening a registry means opening a **namespace you must defend from day one**. Terraform did this correctly at registry launch on **2020-07-16**, where the new `source` attribute (`[hostname]/[namespace]/type`) *"solves the issue of namespace collisions which can arise from forks and generic provider names"* ([hashicorp.com](https://www.hashicorp.com/en/blog/automatic-installation-of-third-party-providers-with-terraform-0-13), primary). **Doc 18 §3.5 already governs this for us** — publisher-scoped `publisher.extension`, immutable once published, transfer-on-abandonment pre-planned, an explicit collision ruling, fingerprint-priority disambiguation. **This is the single place where the project is already ahead of a 2026 registry, and it cost one section of a reservation doc.** It is also the strongest available vindication of the Lock-before-M9.3 sequencing decision (Doc 18 §3.5's own stated reason for existing).

### 1.7 D-1 conclusion

**INFERENCE — HIGH.** The plugin-system timing memo returns four things, and none of them is a date:

1. **The decision decomposes into three layers** with different forcing events. The contract is done. The loader has no clock. **Distribution has a clock someone else controls.**
2. **The trigger set is six, not four** — T-1 (split into open-vs-promise), T-2 (an output, not a demand signal), **T-3′ replacing T-3** (a first-party exhibit cannot prove third-party demand), T-4 (proposed as a **veto**), and two additions, **T-5 (the first unofficial installer — the only hostile clock)** and **T-6 (a use case data cannot serve)**.
3. **Every trigger reads ZERO today, and two are unmeasurable** until the release cadence is decided and Nick's number lands. **The cheapest act is to make them measurable.**
4. **Both failure modes are real and asymmetric.** Too-early costs a catalog that was mostly dead already, plus a namespace you must defend from day one. Too-late costs the distribution layer permanently, to a volunteer, and the fork argument is much weaker than it is usually stated.

## §2 — D-2: CHEAP-NOW vs EXPENSIVE-LATER

*Which Doc-18 pre-decisions keep the plugin door open at near-zero present cost, and which retrofits get expensive with every shipped release. Output is a named list of candidate post-gate WUs at most. **Zero pre-freeze scope. Zero code.***

### 2.1 The frame: three different cost curves, and only one of them is running

**INFERENCE — HIGH.** "Expensive later" is usually said as if one curve governs everything. It does not. Every reserved seam in Doc 18 sits on exactly one of three curves, and knowing which is the whole of this section:

| Curve | Shape | What drives it | Seams on it |
|---|---|---|---|
| **FLAT** | cost of retrofit does not rise with time | the reservation is structural and pre-authorized | dynamic loading (seam 1); operation registry (seam 2); event-manifest layering (seam 3); trust rung 4 |
| **RISING, ours** | cost rises with **our own** shipped surface | every first-party artifact written against the un-narrowed shape is one more thing to change | trust rungs 1–2 (scoped context wrappers; publish permissions) |
| **RISING, theirs** | cost rises with **third-party** adoption, and is ~zero until the first outside adopter | you cannot change a contract people have built against | descriptor compat-range (seam 6); artifact/manifest format (seam 6); namespace (seam 5) |

### 3.2 The cloud admissibility test — four questions before any cost question

*Derived entirely from governing artifacts, not invented here. Per Substrate Thesis §11, where the thesis conflicts with source or governance artifacts, those win — so each test below cites the **governing instrument** first and the thesis second.*

**A cloud service that fails any of these is not an option at any price.** The brief's instruction is explicit: *"a cloud that contradicts the thesis is not an option at any price."* Stated as a test so it can be applied rather than admired:

| # | Test | Governing instrument | Thesis layer | Failure mode it forecloses |
|---|---|---|---|---|
| **CA-1 — NON-DEPENDENCY** | Does local function degrade if this service is down? | **INV-LF-01 / INV-LF-02**; Doc 17 principle 2 (*"Local-first is inviolate; cloud is strictly additive"*); **AIOT-INV-2** (kept as principle, Doc 17 §6) | §3.3 the arms-dealer position | The system stops working when our service does — the exact structural failure the north star names in the cloud platforms |
| **CA-2 — NON-CUSTODY** | Does the service hold keys, or data the operator can read? | **INV-LF-02** (*"no cloud service holds the keys"*); Doc 17 §3.4; north star (*"no user data is exfiltrated or monetized"*) | §8 anti-pattern: *"Letting an accountability product become a data-collection product"* | We become a party who could read the record we sell the integrity of |
| **CA-3 — NON-EXTRACTION** | Does any revenue from this service derive from *access* to community content, or from data? | **DP-18-C** (Doc 18 §2 standing constraint); revenue principles **4** (*"No advertising, ever. | **CA-4 — NON-WATCHING** | Can the service observe user behaviour at per-user granularity? | **X-4's pending telemetry ruling** (parked for the charter, and it must state that characterisation ≠ telemetry); C-1's *nothing watches the watcher* | §7 item 4: *"Requires opt-in, anonymized data collection or it violates the founding premise"* | The trust brand's single unrecoverable failure |

**CA-4 is a conditional, not a binary.** The thesis's own formulation is *"the corpus must be opt-in and anonymized or it must not exist"* — so a service that *can* observe passes only with **opt-in, aggregate-only, a published retention ceiling, and no per-user granularity**. That is the strictest of the four and it is the one the fleet/telemetry class lives or dies on (§3.4).

**INFERENCE — HIGH.** The value of writing the test down is that it is **cheap to apply and it disqualifies before it costs anything**. Three of the five classes pass all four cleanly with a known architecture; one passes only conditionally; one has a structural answer that must be designed in rather than assumed. §3.8 carries the verdicts.

### 3.3 CLASS 1 — REMOTE-ACCESS RELAY

**What it is.** Letting a user reach their hub from outside the LAN without port-forwarding. Named in Connect. The most-wanted cloud feature in this category, by the incumbent's own feature ordering.

#### Build / buy / partner, with dated cost curves

**FACT — HIGH, and it is the single biggest cost fork in this entire radar: relay architecture vs NAT traversal.**

The incumbent's remote access is **100% relayed, not peer-to-peer**, and it says so: *"Your local Home Assistant instance connects to one of our custom-built UI proxy servers. These servers operate at the TCP level, forwarding all encrypted data between your browser/client and the local instance"*, with *"Routing … handled on the proxy server … by the Server Name Indication (SNI) extension during the TLS handshake"* ([support.nabucasa.com](https://support.nabucasa.com/hc/en-us/articles/25619268678557/), primary; the implementation is open-sourced as `snitun`).

Tailscale, by contrast, reports *"success rates for direct NAT traversal well north of 90% in typical conditions"* and that *"the vast majority of Tailscale traffic flows directly between peers, with the cloud relay servers … used to initiate connections and as a fallback relay"* ([tailscale.com/blog/nat-traversal-improvements-pt-1](https://tailscale.com/blog/nat-traversal-improvements-pt-1), 2025-10-15, primary).

**INFERENCE — HIGH. A relay pays egress on ~100% of user traffic; NAT traversal pays on <10%.** The former scales cost with *usage*; the latter with *connection setup*. The incumbent chose the expensive one — because it works behind CGNAT with zero client software — and then, on the evidence of the price point, must be running it on flat-rate bandwidth rather than hyperscaler egress. *(That last clause is this lane's inference from the arithmetic below, not a published fact.)*

**INFERENCE — HIGH. Per-user SaaS VPN pricing is structurally incompatible with a consumer hub subscription, and the reason is a units mismatch, not a price level.** Every customer is *one user with one or two devices*. Tailscale/Cloudflare/Twingate charge per **user**; our revenue is per **household**. At $8/user/month the relay alone costs 1.5× the entire subscription. **Screen on the billing unit before screening on the price** — a rule that recurs in three of the five classes.

**FACT — HIGH, and it is a live risk to the only shape that closes.** Effective **2026-06-15**, Hetzner raised cloud prices sharply with roughly six weeks' notice — CCX13 dedicated €15.99 → **€42.99 (2.69×)**, CPX52 €36.49 → **€100.49 (2.75×)**, CX23 shared €3.99 → €5.49 (1.38×) ([Northflank, 2026-06-17](https://northflank.com/blog/hetzner-cloud-server-price-increases) — **secondary**; Hetzner's own pricing page is JS-rendered and did not fetch, disclosed). **Dedicated-CPU instances — exactly what a relay fleet needs — took the worst of it.** Any relay cost model resting on flat-rate European bandwidth now carries an explicit supplier-risk term.

#### What the thesis demands of it

**INFERENCE — HIGH. This is the class with the highest exposure on CA-2 (non-custody), because it is the only service that carries *user traffic*.** But a structural answer exists and is demonstrated in production by the incumbent: **a TCP/SNI-level forwarder of already-encrypted bytes.** The operator routes on the SNI field and cannot read the payload. That satisfies CA-2 by construction rather than by policy, and it composes with INV-LF-02's *no cloud service holds the keys*.

- **CA-1 (non-dependency):** passes by construction — every automation runs locally; the relay carries a *view*, not a decision. This is Doc 17 §3.4's cut-line restated: *"WAN outage ⇒ every automation still runs locally."*
- **CA-2 (non-custody):** passes **only if** the relay is architected as an opaque forwarder. **This is a design commitment that must be made before the service exists, not after** — it is the cheapest CA-2 answer available and the most expensive to retrofit.
- **CA-3 (non-extraction):** passes — remote access is convenience, not access to community content.
- **CA-4 (non-watching):** **conditional.** A relay necessarily observes connection metadata (which hub, when, how much). Passing requires an explicit, published position on what relay logs are retained and for how long — and note that the highest-bandwidth workload (camera streams) is the one the incumbent moved to **WebRTC**, which is plausibly a deliberate move to keep it off the relay entirely. *(That reading is this lane's inference from the feature list, not a published rationale.)* Either way it is both the cheaper and the less-watching architecture, and **honest and cheap coincide again.**

#### Last responsible moment — the event that forces it

**INFERENCE — MED-HIGH. The forcing event is the first public pricing page that names remote access** — not the first user request, and not launch. Two reasons, both structural: **(a)** DP-18-C and the revenue non-negotiables bind the *wording* of that page, so the architecture must already satisfy CA-1..CA-4 before it is described; **(b)** CRA scope attaches at *placing on the market*, and §3.7's Recital 12 is explicit that remote-control cloud functionality for smart-home devices is in scope. **Before that page exists, the decision is free. After it exists, it is a promise and a regulated product simultaneously.**

**A weaker, earlier signal worth naming:** the first support conversation in a channel we staff where a user cannot use {PRODUCT} without remote access. That is not a forcing event — it is the evidence that one is approaching.

#### What the thesis demands of it

**INFERENCE — HIGH, and this is the class where the thesis can veto outright.** The anti-pattern is named in the thesis's own §8: ***"Letting an accountability product become a data-collection product. Fatal to the founding premise; the corpus must be opt-in and anonymized or it must not exist."*** And revenue principle 4 is absolute: *"No advertising, ever. No data monetization, ever."*

- **CA-1:** passes trivially — telemetry is never load-bearing.
- **CA-2:** passes **only if** the payload carries no readable per-user data. Aggregate-only satisfies this.
- **CA-3:** passes — this class earns nothing.
- **CA-4 (non-watching):** **this is the test, and the conditions are the thesis's own.** Opt-in. Anonymized. Aggregate. Published retention ceiling. No per-user granularity. **Anything else and it must not exist.**

**INFERENCE — HIGH, and it is the most useful sentence in §3.4: the cheapest architecture and the thesis-compliant architecture are the same architecture.** A Worker + KV + 60-day retention + aggregate rollups is simultaneously the near-zero-cost shape *and* the shape that passes CA-4. We are not paying a premium for the founding premise here; we are being paid by it.

**And the boundary the record already parked.** X-4's telemetry ruling — parked for the charter — *"must state characterisation != telemetry; the profile channel tests the distinction first."* **This class is where that ruling gets its second and harder test**, and L-B §6.3 already made the argument: community-submitted *characterisation* (a human describing a device) is categorically different from *telemetry* (a device reporting on a user). §3.4's whole admissibility hangs on holding that line in a place where nobody is describing anything.

**One honest tension, recorded rather than resolved.** The north star's own open research question — *"Real-world longitudinal benchmarking of physical agents, from opt-in, anonymized deployment data rather than simulation"* — needs a corpus, and the thesis's §7 item 4 already carries the constraint: *"Requires opt-in, anonymized data collection or it violates the founding premise."* **The research agenda wants the corpus; the founding premise prices it. Both are in the record and neither is being re-litigated here.** The relevant D-3 observation is narrow: **if this corpus is ever pursued, its infrastructure is this class, and CA-4 is the design spec, not a later review.**

#### Last responsible moment — the event that forces it

**INFERENCE — MED.** Two candidate forcing events, and they point at different scopes:

- **The narrow one:** the first field failure we cannot diagnose from a user's description. That forces *diagnostic* telemetry — small, opt-in, per-session, arguably not a fleet service at all.
- **The wide one:** any external claim that requires field evidence to stand up. C-3's nightly-numbers artifact is bench-derived and does **not** need it (A-7, and L-B §7.2 act 1.5 reshapes it precisely so it needs no owner). The availability/confirmation claims are architectural and do not need it either. **So the wide forcing event does not currently exist**, which is a good finding: this class can be deferred by name with no clock at all.

- **CA-4:** passes if download telemetry is aggregate. Same discipline as §3.4.

**And Doc 18 §4 row 7's floor still governs the shape whenever this is built**, with L-B's three added rows riding **OQ-3** (**A-11**): pre-publication scanning with quarantine, transitive-dependency awareness, and an explicit published statement of what the registry does **not** guarantee. **No Doc-18 amendment is proposed by this lane either.**

#### Last responsible moment — the event that forces it

**INFERENCE — HIGH, and it is the sharpest forcing event in the whole radar: the first unofficial installer or index (trigger T-5).** §1.6 is the evidence in full. **Note carefully what the cheap response is.** It is **not** building a registry. #### What the thesis demands of it

**INFERENCE — HIGH. This is the class that most directly threatens the founding premise, and it is the one where "buy" imports a third party into the trust story.**

- **CA-1 (non-dependency):** passes **only if the account is optional.** A hub that cannot be set up or operated without an account has made a cloud service load-bearing, which is the exact structural failure the north star names in the incumbent cloud platforms. **This must be an architectural commitment, not a default.**
- **CA-2 (non-custody):** **the hard one.** An identity plus synced configuration is the seed of a user graph, and INV-LF-02's *"no cloud service holds the keys"* is a governing invariant, not a preference. A structural answer exists — **sync end-to-end-encrypted config blobs the operator cannot read** — and it is cheap if designed in and expensive if retrofitted. It also happens to be the shape that makes the buy-vs-build question *less* fraught, because an opaque blob store is a commodity and an identity provider that never sees plaintext config is a much smaller trust surface.
- **CA-3:** passes — sync is convenience, not access to community content.
- **CA-4 (non-watching):** **conditional, and it is the sharpest conditional in the radar.** An account service knows who exists, when they connect, and how many homes they have. Passing requires that this is opt-in (falls out of CA-1's account-optional commitment), that no behavioural data rides along, and that a retention position is published.

**OPINION — MED-HIGH.** Of the five classes this is the one where a cost-optimal decision and a thesis-optimal decision most plausibly diverge — WorkOS at $0 to a million users is extremely hard to argue with on economics, and the argument against it is entirely CA-2. **That is a decision to take deliberately, with the trade named, rather than to arrive at by default because the free tier was generous.**

#### Last responsible moment — the event that forces it

**INFERENCE — MED-HIGH. The first product surface that cannot function without an identity.** Concretely, that is whichever comes first of: a mobile application, a multi-home/multi-site customer (Cloud Pro's promised *"multi-home management"*), or a hosted channel that must know who is entitled to it (Connect's promised verified channel — which links this class to §3.5). **Before any of those exists, the decision is free; the moment one is scoped, CA-1's account-optional commitment has to be made first or it cannot be made at all.**

### 3.8 THE CRA RIDER — across all five classes

**This subsection covers the CRA rider for classes 1–5 in one place**, because the caveat below applies identically to every citation and repeating it five times would obscure it. **Per the not-legal-advice law, nothing here is answered. Everything is a sourced question or a sourced text.**

> **⚠️ SOURCING CAVEAT, LOAD-BEARING. The final guidance C(2026) 5252 of 2026-07-27 could not be read** (§0.4(1)). Every paragraph citation below is to the **DRAFT of 2026-03-22** (Ares(2026)2319816; 70 pp, 55 examples), obtained from a third-party mirror and marked **[DRAFT ¶n]**. The final reportedly carries **67** examples and at least one paragraph is reported to have shifted by roughly **+11**. **Every ¶ number below will be wrong against the final.** The substance is offered as evidence of Commission thinking, and the counsel packet must re-verify paragraph by paragraph. **The beat-4 adjudication's follow-up D(1) remains open and this lane did not discharge it.**

#### (a) The statutory hook — why a cloud service is not merely adjacent to the product

**FACT — HIGH, verbatim from EUR-Lex** (recitals fetched directly, 2026-08-01; the operative Articles were truncated — §0.4(2)):

> **Recital (11):** *"The purpose of this Regulation is to ensure a high level of cybersecurity of products with digital elements and their integrated remote data processing solutions. Such remote data processing solutions should be defined as data processing at a distance for which the software is designed and developed by or on behalf of the manufacturer of the product with digital elements concerned, the absence of which would prevent the product with digital elements from performing one of its functions."*

> **Recital (12) — and the smart-home example is directly on point:** *"Cloud solutions constitute remote data processing solutions within the meaning of this Regulation only if they meet the definition laid down in this Regulation. For example, **cloud enabled functionalities provided by a manufacturer of smart home devices that enable users to control the device at a distance fall within the scope of this Regulation.** On the other hand, websites that do not support the functionality of a product with digital elements, or cloud services designed and developed outside the responsibility of a manufacturer of a product with digital elements do not fall within the scope of this Regulation."*

**FACT — MED (Article text via mirror, cross-checked against the Commission's own verbatim quotation inside the draft guidance).** **Article 3(1)** defines 'product with digital elements' as *"a software or hardware product **and its remote data processing solutions**"* — i.e. the cloud component is **part of the product**, not a separate thing beside it.

#### (b) Which of our five classes the draft guidance's own list catches

**FACT — HIGH [DRAFT ¶174], verbatim.** Functions whose remote processing brings a service into scope expressly include:

> *"(i) sending commands to a device; (ii) synchronising files; (iii) onboarding the user; (iv) configuration (personalisation of the product); (v) receiving updates, including feature update and security patching; (vi) identity and access management."*

Mapped against §3.3–§3.7, with the caveat above applying to every row:

| Class | Draft-guidance signal | Reading |
|---|---|---|
| **1 — Remote-access relay** | ¶174(i) *sending commands to a device*; **Recital 12's own smart-home example** | **Most clearly caught of the five.** And **[DRAFT ¶175]** forecloses the obvious defence, verbatim: *"In some cases, the user can use a function both remotely and manually (e.g. switching a light bulb with an app or manually). **Having this option does not exclude qualification as RDPS.**"* — i.e. **local-first does not exempt the relay** |
| **2 — Fleet/telemetry** | **[DRAFT ¶176]**, verbatim: *"where the absence of a certain data processing does not prevent the product from performing one of its functions, such processing is not considered as a RDPS … This includes, for example, **remote analysis of telemetry data collected purely for statistical purposes or future product development**"* | **Least entangled of the five** — the intuition inverts. But **[DRAFT ¶177]** still requires those communications be risk-assessed |
| **3 — Registry/distribution** | ¶174(v) *receiving updates* **vs** **[DRAFT ¶166]**, which excludes internal IT including *"the distribution of security updates to edge locations"* | **Genuinely ambiguous in the draft — the two paragraphs are in tension.** Counsel question |
| **4 — Account/profile sync** | ¶174(ii) *synchronising files*, (iii) *onboarding the user*, (iv) *configuration*, (vi) *identity and access management*; plus **[DRAFT ¶178]**: *"an authentication portal that issues credentials/tokens required for the product to operate would be considered RDPS"* | **Caught on four separate limbs** |
| **5 — OTA** | ¶174(v) vs ¶166, same tension as class 3 | **Ambiguous.** Note the industry ask to exclude OTA outright ([DIGITALEUROPE, 2025-07-25](https://cdn.digitaleurope.org/uploads/2025/07/Towards-clear-guidance-for-remote-data-processing-under-the-CRA_DIGITALEUROPE.pdf), **secondary/industry**) **was not cleanly adopted in the draft** — a useful negotiating fact |

**FACT — HIGH [DRAFT ¶180], verbatim, and it is the single most important sentence in this subsection:**

> *"In understanding RDPS, the notion of **'who operates the solution' is not a decisive factor**, as the CRA definition only refers to the design and development of the RDPS. … If manufacturers design and develop solutions, which are then operated by a third party, **they remain responsible for compliance** with the CRA's essential requirements for the product that they place on the market."*

**INFERENCE — MED-HIGH.** Outsourcing operation does not shed responsibility. That collapses a whole category of "just use a partner" answers into "use a partner *and* still own the obligation," which is a materially different cost picture than the buy-column of §3.3–§3.7 alone suggests.

**FACT — HIGH [DRAFT ¶162], and it extends the reporting cascade to the cloud component:**

> *"the manufacturer must consider **the product as a whole, including its remote data processing solutions (RDPS)** … **The same is valid when considering lifecycle obligations, such as reporting of actively exploited vulnerabilities and severe incidents (Article 14).**"*

**FACT — HIGH [DRAFT ¶78], and it reaches the steward posture too:** a steward that *provides the underlying IT infrastructure* **must** notify ENISA and CSIRTs under **Art 14(3)** of severe incidents impacting product security. **INFERENCE — MED-HIGH: hosting infrastructure carries a reporting obligation even in a steward posture** — which is directly relevant to §3.5, because a registry is infrastructure.

#### (c) The steward-vs-manufacturer boundary — the text, not the answer

**FACT — HIGH, verbatim from EUR-Lex Recital (15) — the commercial-activity test, with the clause that matters emphasised:**

> *"Supply in the course of a commercial activity might be characterised not only by charging a price for a product with digital elements, but also by charging a price for technical support services where this does not serve only the recuperation of actual costs, **by an intention to monetise, for instance by providing a software platform through which the manufacturer monetises other services**, by requiring as a condition for use the processing of personal data for reasons other than exclusively for improving the security, compatibility or interoperability of the software, or by accepting donations exceeding the costs associated with the design, development and provision of a product with digital elements."*

**FACT — HIGH [DRAFT ¶49–50, ¶51, ¶54, ¶73], the Commission's own elaboration, verbatim in the load-bearing places:**

- **¶49:** *"the paid version is monetised in some way … and therefore considered to be placed on the market, triggering the manufacturers' obligations. The version provided for free (or community version) is not monetised and therefore is not considered to be placed on the market."*
- **¶50:** *"**If the person supplying the community version is a legal person, that legal person is also subject to the obligations on stewards for the version it supplies for free.**"*
- **¶51:** *"A natural or legal person publishing a FOSS may also be placing it on the market … where **it provides the software through which it monetises other products or services**."*
- **¶54:** *"**This includes cases where a paid edition or enterprise version is made available under a commercial agreement, irrespective of whether functionally equivalent software is also available free of charge under a free and open-source licence.**"*
- **¶73:** *"a legal entity that publishes a free (or community) version and a monetised version of the same FOSS, is deemed a steward to the free (or community) version (and a manufacturer to the monetised version)."*
- **Example 9** — the closest published analogue to our shape: *"A natural or legal person publishes a free and open-source VPN. The application is available free of charge, but it enables users to pay to access additional servers or dedicated IP addresses. That application allows that person to monetise other services offered through it, therefore it is considered placed on the market in the course of a commercial activity."*

**INFERENCE — MED-HIGH, and it is the finding, not a conclusion.** The draft guidance clearly contemplates one legal entity being **steward for the free edition and manufacturer for the paid one, simultaneously**. What it does **not** squarely address is our exact shape: *identical code, one self-hosted and free, one operated by us for money* — because a **hosted service is not a differently-licensed edition**. That gap is precisely where the beat-4 adjudication's **A-12** ("the live classification risk is MANUFACTURER vs steward") bites, and it is why the questions below ask only the **cloud-specific delta** and deliberately do not re-ask L-B §2.6(iii).

#### (d) COUNSEL QUESTION BLOCK **H** — proposed to JOIN the D-4 packet per ruling R-5

*Answers deliberately withheld. D-4 is the carrier document; L-B §2.6 joined as section G; this proposes **section H**. Each question names the document that would settle it.*

- **H-1.** Does **operating** any of the five service classes (relay, telemetry, registry/distribution, account/sync, OTA) constitute *making available on the market in the course of a commercial activity* such that {COMPANY} is a **manufacturer** rather than an Art-24 steward — **and if so, for which product(s)**: the operated service, the self-hostable build, or both? *(Distinct from §2.6(iii), which asks the general classification question; H-1 asks the cloud-operation delta.)* → **Settled by:** final C(2026) 5252 §3.2/§3.3 and the expanded example set.
- **H-2.** Is a **free, unpriced** relay/sync/registry service, offered alongside a free open-source product **with no paid tier at all**, a monetisation trigger under Recital 15's *"intention to monetise … by providing a software platform through which the manufacturer monetises other services"*? **[DRAFT ¶51] and Example 9 both involve *paid* upgrades; nothing found addresses a wholly free service.** → **UNSETTLED.** Settled by: final §3.2.2 and its examples.
- **H-3.** Where the same legal entity publishes the open-source build **and** sells a hosted tier of the same code, is the **self-hostable build itself** thereby "monetised"? **[DRAFT ¶49/¶54/¶73]** treat community and paid as different products with split roles — but a hosted **service** is not a differently-licensed **edition**. → **UNSETTLED.** Settled by: final §3.2.1–§3.2.3.
- **H-4.** Does the **Art 13(8) support period** (≥5 years, subject to expected-use) bind the **RDPS** as well as the shipped software? Art 3(1) makes RDPS part of the product, but **[DRAFT §5, ¶114–120] never mentions RDPS** — verified by search across the draft. → **UNSETTLED as to express confirmation.** Settled by: final §5 (reported to renumber near Point 126) read with final §8.2.
- **H-5.** Can changes to **our own** RDPS constitute a **substantial modification** under Art 3(30) / Art 69(2)? **[DRAFT ¶192]** answers only for *third-party* providers (*"A major change in the solutions provided by the third-party cloud services providers should not qualify as a substantial modification"*) and is silent on the manufacturer's own. **This is the highest-stakes gap in the file**: a continuously-deployed backend could otherwise be argued to substantially modify a pre-2027 product on an ongoing basis, pulling it into full scope. → **UNSETTLED.** Settled by: final §4 read with §8.2 (a four-factor test is reported at final Point 110).
- **H-6.** Is **OTA update infrastructure** an RDPS under **[DRAFT ¶174(v)]** or excluded internal distribution under **[DRAFT ¶166]**? The draft is internally in tension. → **UNSETTLED.** Settled by: final §8.1.2 and the security-update examples (reported at final Examples 46–50).
- **H-7.** Does **providing the underlying IT infrastructure** for the project — e.g. hosting a profile/extension registry — trigger **Art 14(3)** severe-incident reporting even in an otherwise steward posture, per **[DRAFT ¶78]**? → **Settled by:** final §3.3.1; confirm the ¶78 text survives.
- **H-8.** For any class that **is** an RDPS, what is the **scope of the conformity assessment** for the cloud part? **[DRAFT ¶189]**: *"CRA requirements should only apply to those parts of the system where data intended for the provision of product functions is stored or processed … the intent of the CRA is not to cover the entire entity's environment … the underlying hardware infrastructure should be considered outside the scope of the product."* → **Settled by:** final §8.2.
- **H-9.** Does **Art 69(3)** (reporting applies to products placed on the market before 2027-12-11 regardless of substantial modification) reach **severe incidents occurring in the RDPS** of such a product? **[DRAFT ¶162]** puts RDPS inside "the product as a whole" for Art 14 purposes but does not say so expressly for Art 69(3). → **UNSETTLED.**
- **H-10.** **A sequencing question, not a scope question:** is there any classification advantage to deciding **before** first placing on the market which of the five classes {COMPANY} will operate — as opposed to adding them later — given that Art 69(2)'s transitional relief turns on substantial modification and H-5 is open? → **Settled by:** counsel's reading of final §4 + §9.3.

**Two things this block deliberately does not do.** It does not re-ask **A-12 / §2.6(iii)** (the general manufacturer-vs-steward classification), and it does not touch the **Annex III Class I vs Default** hub-classification question, which the R-3 return already flagged as *"the single highest-leverage classification decision on the runway"* and routed to IR (EU) 2025/2392 + C(2026) 5252. **Both are already in the packet's pipeline. Block H is additive and cloud-specific.**

## §4 — D-4: THE PREMATURE-INVESTMENT RISK REGISTER

*Explicit, because the founder's word this beat is "not rushing." Each row is a failure mode of early platform/cloud spend **for a solo founder pre-revenue** — burn, maintenance surface, security/on-call obligations the CRA prices, and distraction from the substrate. Closes with the minimum-viable radar.*

### 4.1 The register

---

#### **PIR-1 — THE PAGER NOBODY CAN STAFF**
**Severity: the binding constraint. Not money — the pager.**

**FACT — HIGH.** Google's SRE practice gives hard numbers: *"the maximum number of incidents per day is 2 per 12-hour on-call shift"* because handling one properly *"takes 6 hours"*; *"at least 50% of SRE time into engineering"* with *"no more than 25% … on-call"*; and — the number that governs — ***"the minimum number of engineers needed for on-call duty from a single-site team is eight"*** for a 24/7 primary-plus-secondary rotation ([sre.google/sre-book/being-on-call](https://sre.google/sre-book/being-on-call/), primary, accessed 2026-08-01).

**FACT — HIGH.** The CRA's Article 14 reporting cascade commences **2026-09-11**: **24-hour** early warning from becoming aware, **72-hour** fuller notification, **14 days** after a corrective measure (one month for severe incidents) — re-verified at the Commission and already adopted at **A-12**.

**INFERENCE — HIGH. A solo founder is one-eighth of a minimally sustainable rotation, against a statutory 24-hour clock.** There is no configuration of tooling that closes an 8× staffing gap. The only levers are: **(a)** do not run the service, **(b)** do not promise the availability, **(c)** buy it from someone who already has the rotation.

**And the part that is easy to mis-file: this risk does not disappear by staying local-first.** Art 14 attaches to the **product**, not to the cloud. **[DRAFT ¶162]** then *extends* it to the RDPS. So local-first does not escape the pager; **operating cloud services multiplies it** — five always-on services, each an independent incident source, each inside the same 24-hour window.

**Mitigation available today, at zero cost:** publish no SLA. See PIR-2.

---

#### **PIR-2 — THE UPTIME PROMISE YOU CANNOT RETRACT**
**Severity: high, and it is an irreversible-commitment risk rather than a cost risk.**

**FACT — HIGH.** Every vendor surveyed puts SLAs behind a paywall, which prices what an SLA costs to *offer*: Ory Enterprise and Auth0 Enterprise at **99.99%** (custom pricing); Grafana Advanced/Enterprise at a **$25,000/year minimum commit**; Supabase Team **$599/mo**; PowerSync Team **$599/mo**; Balena Production **$1,439/mo** for a 60-minute response. **99.99% is 52 minutes of downtime per year. 99.9% is 8.8 hours.**

**INFERENCE — HIGH, and the record already contains the governing precedent.** Adjudication **A-9** adopted the curl arc for the bug-bounty question — ***you cannot solve load by subtraction once the expectation exists*** — and ordered *"no bug bounty, permanently"* stated up front. **An uptime promise has exactly the same shape.** Publishing no SLA is retractable in the sense that it can later be improved; publishing one and withdrawing it is the thing that cannot be undone.

**And L-B's holdable-posture test already gives the rule, adopted at A-14 as the SUPPORT.md frame:** *hold only obligations that survive zero attention; disclose the rest as unpromised.* **Applied to cloud: any service whose value proposition is "it is up" fails that test at a solo staffing level, so it must ship with the availability explicitly unpromised or not ship.**

---

#### **PIR-3 — BURN AGAINST A PRICE THAT IS ALREADY FIXED**
**Severity: high, and it is arithmetic rather than judgement.**

**FACT — HIGH.** Connect is specified at **$7.99/mo = $95.88/yr**; the category incumbent charges **$65/yr** and has held it flat since 2022-02-01 (§3.1). Net of VAT and processing, ~**$55–63/subscriber/year** (this lane's arithmetic).

**INFERENCE — HIGH. Two stacks, from the same list prices:**

| Stack | Composition | Per device/yr | % of net |
|---|---|---|---|
| **The naive stack** | Balena Production ($24–25) + Grafana Cloud Pro ($7.80) + Tailscale Standard ($96) | **~$128** | **>200% — the product loses money on every subscriber** |
| **The disciplined stack** | GitHub Releases ($0) + Mender OSS self-hosted (~$0) + WorkOS free tier ($0) + Honeycomb event-billed (~$0.18) + AWS IoT Core (~$0.56) + **self-hosted relay (the open term)** | **~$0.74 + relay** | **~1% + relay** |

**INFERENCE — HIGH, and it is §3's synthesis stated as a risk: four of five classes are effectively free at our scale; the relay is the only class whose cost scales with user *traffic* rather than user *count*, and it is therefore the entire question.** The premature-investment risk here is not that cloud is expensive — it is that **the naive stack is available, plausible, and 200% of revenue**, and each of its components looks reasonable in isolation.

---

#### **PIR-4 — INFRASTRUCTURE PRICE IS NOT A CONSTANT**
**Severity: medium, and it is a supplier-risk term most cost models omit entirely.**

**FACT — HIGH.** Three separate list-price-≠-effective-price hazards surfaced in a single sweep:

1. **Hetzner raised cloud prices 1.33×–2.75× effective 2026-06-15** with roughly six weeks' notice, worst on the dedicated-CPU instances a relay fleet needs (§3.3). The "build it cheap on flat-rate bandwidth" plan became 1.3–2.7× more expensive in one step.
2. **GHCR is free with a word attached**: *"Container image storage and bandwidth for the Container registry is **currently** free."*
3. **Tailscale states on its own pricing page: *"We are currently not enforcing the hard limits or overages"*** on ACL groups, tagged resources, and ephemeral resources.

**INFERENCE — MED-HIGH.** A cost model resting on any of these carries an unpriced option written **against** us. **The disciplined stack in PIR-3 leans on GitHub Releases and R2 for the two zero-cost classes; both are commercial decisions someone else can revise.** The mitigation is not to avoid them — they are correct choices today — but to keep the **artifact format portable** so a hosting change is a DNS-and-mirror exercise rather than a re-architecture. **That is a Doc 18 §4 row 6 property already** (*"distribution may ride existing infrastructure initially … with the supply-chain inheritance named honestly"*, **L-16**), and this is the cost reading of that row.

---

#### **PIR-5 — THE MAINTENANCE SURFACE COMPOUNDS AGAINST THE SUBSTRATE**
**Severity: high. The thesis names this as the most likely proximate cause of failure, in its own words.**

**FACT — HIGH, verbatim from the Substrate Thesis §8 anti-patterns:**

- ***"Boiling the ocean across segments and deployment models simultaneously. The most likely proximate cause of failure."***
- ***"Building an agent instead of the substrate. The default move; produces a commodity wrapper over a model you don't control."***
- ***"Confusing a research agenda with a roadmap. Everything in §4 and §7 is a multi-year horizon. Cheap optionality now; depth later; exactly one at a time."***

And from §5's unproven ledger, item 8: ***"That one person can hold a research frontier. Structurally, no."* — [PROVEN false in the general case]**.

**INFERENCE — HIGH, and it is measurable in our own record rather than merely asserted.** All five cloud classes are **greenfield — zero code today**. So is the inbound-MCP server (L-B §4.1's zero-hit grep). **The MCP server is already ordered as a Tier-1 compounding act (L-B §7.2 act 1.4, Medium effort) precisely because it grows the substrate's value.** Cloud services do not: they are convenience and distribution, not additional *proposers* into the adjudication path. **Per L-B §6.1's frame — every extension is another proposer, and the enforcement layer's value grows with the number of distinct proposers — cloud work competes directly with Tier-1 for the same scarce hours while contributing nothing to that count.**

**OPINION — MED-HIGH.** That is the most precise available statement of the distraction risk, and it is stronger than "cloud is a distraction" because it says *from what, and by what mechanism*.

---

#### **PIR-6 — THE REGISTRY'S REAL COST ARRIVES WITHOUT WARNING, AND NOBODY PUBLISHES IT**
**Severity: high, and it is the risk most likely to be under-modelled because the number does not exist.**

**FACT — HIGH, reported as an absence (§0.4(3)).** No moderation or security-scanning cost figure is published for **any** registry — PyPI, npm, crates.io, Open VSX, Homebrew. Searched and not found. **The reason appears structural: it is a headcount, not a line item.**

**FACT — HIGH, the incident load that stands in for it** (carried from L-B §4.2, cited not re-derived): the Eclipse Foundation mandated pre-publication scanning with quarantine in **February 2026**, enforcing from **March 2026**, with its director stating the prior reactive-removal approach *"does not scale as publication volume increases and threat models evolve"*; **72 additional malicious Open VSX extensions since 2026-01-31** built transitive delivery chains from benign-looking parents; and UpGuard's verdict on discovery: ***"The malicious package was not discovered through monitoring or alerting. It was found through independent security research."***

**INFERENCE — HIGH.** The last sentence is the risk in one line: **the cost arrives as an incident you did not detect, reported to you by a stranger, inside a 24-hour statutory window (PIR-1).** That is the compound failure — PIR-6 triggering PIR-1 — and it is the specific reason a registry is not merely "more work."

---

#### **PIR-7 — THE EMPTY-REGISTRY TRAP RUNS IN BOTH DIRECTIONS**
**Severity: medium-high, and it is the trap that makes "just open it early to be safe" wrong.**

**FACT — HIGH.** Opening early is not merely premature — **it creates a namespace that must be defended from day one.** Firefox for Android sat at 9–18 extensions for **three and a half years** and collected one-star reviews for it; Open VSX's *named gaps* — extensions recommended by inherited config but absent from the registry — were being actively exploited on **2026-01-06**, with a proof-of-concept placeholder attracting **500 installs** (§1.5(b)).

**INFERENCE — HIGH.** So the two failure modes do not bracket a comfortable middle — they bracket a **shape requirement**: a registry must launch with (a) governed namespace ownership, (b) a default-off unreviewed tier so thinness is a policy rather than an embarrassment, and (c) pre-publication checks. **All three are already in Doc 18 §3.5 and §4 row 7 plus L-B's OQ-3 additions (A-11).** The risk is not that we lack the design; it is that **the design is only cheap while nothing is published**.

---

#### **PIR-8 — A CLOUD SERVICE CAN PULL THE WHOLE PRODUCT INTO A HEAVIER REGULATORY CLASS**
**Severity: high. Not a legal conclusion — a risk to price. Every leg is a question in §3.8(d).**

**FACT — HIGH [DRAFT ¶180].** *"the notion of 'who operates the solution' is not a decisive factor"* — outsourcing operation does not shed responsibility. **FACT — HIGH [DRAFT ¶162].** Art 14 lifecycle obligations extend to the RDPS. **FACT — HIGH [DRAFT ¶78].** Providing the underlying IT infrastructure triggers Art 14(3) reporting **even in a steward posture**.

**INFERENCE — MED-HIGH, stated as exposure and not as an answer.** The beat-4 adjudication already established that *"the live classification risk is MANUFACTURER vs steward, not steward-vs-nothing"* (**A-12**). **This lane's contribution is narrow and specific: operating a cloud service is a plausible mechanism by which that risk is realised, and at least three of the five classes are caught on the draft guidance's own list (§3.8(b)).** Whether it *is* realised is **H-1**, **H-2** and **H-3** — and **H-2 and H-3 are genuinely unsettled in the draft**, which means the exposure cannot currently be priced even by counsel until the final guidance is read.

**The premature-investment reading:** every cloud class we launch is a bet placed **before** the question that prices it can be answered. **The cheapest risk reduction available is temporal — decide after the final guidance is read, which costs nothing because no forcing event has fired (§3.9).**

---

#### **PIR-9 — THE SECOND-ORDER OBLIGATIONS NOBODY BUDGETS**
**Severity: medium, cumulative.**

**FACT — MED-HIGH.** Beyond uptime and incident response, operating any of the five imports: GDPR Art 33's **72-hour** breach-notification duty (quoted from Recital 85; the operative Article text could not be fetched — disclosed, and **Art 83 fine tiers are deliberately not quoted** because they could not be verified); the CRA's Annex I Part I requirement for **encryption at rest and in transit**, **data minimisation**, **security-relevant logging and monitoring**, and **secure permanent deletion of all data and settings**; and — for any enterprise conversation — SOC 2 or ISO 27001, for which the only cost figure found was *"$100,000 or more"* (⚠️ **vendor-published, upward bias, order-of-magnitude only**).

**FACT — MED (sponsored source, direction only).** Current empirical on-call load, n=1,039, fielded February 2026, ⚠️ **sponsored by a vendor selling incident-response AI**: **77%** of on-call teams receive ≥10 alerts/day; **57%** say fewer than 30% are actionable; **44%** had an outage in the past year linked to a suppressed or ignored alert; **78%** had an incident where **no alert fired at all**. Used only alongside the unsponsored Google SRE numbers in PIR-1.

**INFERENCE — MED-HIGH.** Each obligation is individually small and collectively is a role. **This is the row that turns "we could run a relay" into "we would be a company that runs a relay."**

## §5 — D-5: WHAT CHANGES OUR PLANS

### 5.1 The findings

1. **INFERENCE — HIGH. "When does plugin-system development start" is three questions, not one — and the layer everyone means is the cheapest to defer.** The extension **contract** exists and is frozen (V1-real). The **loader** and its machinery sit on a **FLAT** cost curve — LTD-17 pre-authorizes the swap and the Homebridge precedent (**L-3**) proves a process-agnostic narrow contract retrofits subprocess isolation as *pure configuration* — so waiting costs nothing, forever. **The distribution/index layer is the one with a clock, and the clock belongs to someone else.** → *§1.1, §1.2, §2.1, §2.3.*

2. **FACT — HIGH. Every trigger on the board reads ZERO or DOES-NOT-EXIST today, and two of the six cannot be measured at all until a prior decision lands.** T-1 needs the release cadence; T-4 needs Nick's attended-hours number. **The honest answer to the brief's question is therefore not a date and not even a condition: it is that no trigger is currently measurable, and the cheapest available act is to make them measurable rather than to move any of them.** That is the answer the founder's stated posture — *not interested in rushing into these* — should want, and it is fully supported. → *§1.3, §1.4.*

3. **INFERENCE — HIGH. The release-cadence decision is a hidden prerequisite to three separate things and this lane could not find it on any board.** It blocks (a) the wall-clock expression of the OQ-1 deprecation floor — ruled semantically at six release cycles precisely *because* the cadence is undecided; (b) the T-1 stability trigger, which is why §1.4's earliest-plausible column spans mid-2027 to late-2028; and (c) the externally-stated support period, which the CRA also touches and which the Commission's own draft says is not a default (*"A support period of five years is therefore not to be considered as the default for all products"* **[DRAFT ¶115]**). **One undecided input, three blocked outputs, and it is not a plugin decision.** → *§2.5; candidate charter row **LD-C7**.*

4. **INFERENCE — HIGH. The trigger set needed one replacement and two additions, and the replacement matters most.** **T-3 as briefed cannot work**: an inbound MCP server we build is a *first-party* consumer of our own read-API, so it proves the contract is *usable* but cannot prove *third-party demand* — Homebridge's `config.schema.json` proved the contract because outsiders built against it. **T-3′** ("an outside party builds against the contract unasked") is the trigger T-3 was reaching for, and it doubles as the event that starts the descriptor's cost curve. **The MCP act itself stays exactly where L-B and R-3 put it** — the correction is that it is an exhibit, not evidence. → *§1.3, §2.4(b).*

5. **INFERENCE — HIGH, and it is a warning about our own copy. "Contributors fork when extension points are missing" is a much thinner evidence base than it sounds.** Of nine classic forks examined, **exactly one (Neovim ← Vim, 2014-01-31) is cleanly caused by missing extension points**; Forgejo is a partial second, *enabled* by Gitea having no plugin system; the other seven are **licensing or governance**. **Any external sentence leaning on that claim over-claims, in the exact register where over-claiming costs us most.** The useful inversion is the counter-case: **Grafana relicensed its core to AGPLv3 on 2021-04-20 and was not forked, explicitly because plugins stayed Apache** — an extension point is what lets a project change the core's terms without losing its ecosystem. For us, committed to Apache-forever with a no-rug constraint, **that is insurance we are buying for a fire we have promised not to start: a reason to build it well, not early.** → *§1.6(b).*

6. **FACT — HIGH. Most of any mature registry is already dead before you break anything — and the metric everyone reports hides it.** **59.5% of Chrome Web Store extensions (73,865 of 124,094) have never been updated**; the median number of updates after one year is **0**; only ~60% survive a year (arXiv 2406.12710, AsiaCCS 2024). Chrome's *"Over 85% of actively maintained extensions… are running Manifest V3"* is true and excludes exactly the population that breaks. **Any future {PRODUCT} extension-health metric must report its denominator or it will lie to us the same way.** → *§1.5(a).*

7. **INFERENCE — HIGH. If you do not own the distribution layer, someone else will, and their bus factor becomes yours — and the distance between the two outcomes is three days of sequencing.** HACS: first commit **2019-02-26**, now **3,105 integrations against `home-assistant/core`'s 1,481 (2.1×)**, ~190–290 new submissions/month in 2026, **and no installer release since 2025-01-28 — 18 months and 4 days**, with 39 of 44 human commits in 2026 by one person. Obsidian: plugin API **2020-10-26**, community catalog **2020-10-28/29**; no unofficial store ever took root. **This is why T-5 exists and why the cheap response is prose (LD-C6), not infrastructure.** → *§1.6(a), §3.5.*

8. **INFERENCE — HIGH. The cloud platform is already promised, at a price — D-3 prices a promise rather than inventing one.** The Locked revenue strategy already specifies four of the five classes inside Connect at **$7.99/mo = $95.88/yr**, against a category incumbent at **$65/yr that has held that price flat for 4.5 years** while operating the service since ~Dec 2018 — and whose own answer to "how do you run five cloud services" was to fund **50+ full-time employees** first. **Read every cost figure in §3 against ~$55–63/subscriber/year net.** → *§3.1.*

9. **INFERENCE — HIGH. Four of five cloud classes are effectively free at our scale; the relay is the only one whose cost scales with user *traffic* rather than user *count*, and it is therefore the entire question.** The disciplined stack (GitHub Releases $0 + Mender OSS + WorkOS free tier + event-billed telemetry + AWS IoT Core) is **~$0.74/device/year plus the relay**. The naive stack (Balena Production + Grafana Cloud + Tailscale) is **~$128/device/year — over 200% of net revenue** — and each of its components looks reasonable in isolation. **In three of five classes the *billing unit* decides the bill by one to two orders of magnitude: screen on the unit before the price.** Per-host, per-user, and per-aDAU models are all structurally incompatible with always-on consumer hardware. → *§3.3–§3.7, PIR-3.*

10. **INFERENCE — HIGH, and it is the happiest finding in the return: on telemetry, honest and cheap are the same architecture.** The incumbent's opt-in analytics is a Worker + KV with **60-day maximum retention** and aggregate-only rollups — deliberately built so cost does not scale with cardinality. That is simultaneously the near-zero-cost shape **and** the shape that passes CA-4. **We are not paying a premium for the founding premise here; we are being paid by it.** And the CRA inverts the intuition alongside: **[DRAFT ¶176]** excludes *"remote analysis of telemetry data collected purely for statistical purposes"* from RDPS while ¶174 catches relay, sync, onboarding, configuration and identity. **The class that feels most dangerous is the least entangled; the ones that feel like plumbing are caught.** → *§3.4, §3.8(b).*

11. **INFERENCE — HIGH. Exactly one of the five cloud classes has a clock someone else controls; one has a statutory clock; two have clocks we set ourselves by choosing to publish something; one has no clock at all.** Registry/distribution ← the first unofficial installer (hostile). OTA ← first placing on the market in the EU (statutory; and **Art 69(3) means Art 14 reporting reaches products placed on the market before 2027-12-11 regardless of substantial modification**, so the transitional relief people expect does not reach it). Relay ← the first public pricing page that names remote access. Account/sync ← the first surface that cannot function without an identity. **Fleet/telemetry ← nothing.** → *§3.9.*

12. **INFERENCE — HIGH. Art 14 attaches to the **product**, so staying local-first does not avoid the pager — **operating cloud services multiplies it.** The available mitigations are: do not run the service, do not promise the availability, or buy it from someone who already has the rotation. **And publishing no SLA is free today and unretractable later — the same shape as the bug-bounty ruling at A-9.** → *PIR-1, PIR-2.*

13. **INFERENCE — MED-HIGH.
