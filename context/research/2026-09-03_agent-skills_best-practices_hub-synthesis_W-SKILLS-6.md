# Agent Skills — what the guidance actually says, measured against our three skills

## §0 The five facts that decide the refresh
1. **Only `name` + `description` load at startup; the SKILL.md body loads on trigger; referenced files load on demand.** So the body is paid on EVERY trigger and every referenced file is paid only when read. (platform.claude.com best-practices: "only the metadata (name and description) from all Skills is pre-loaded"; "once Claude loads it, every token competes with conversation history and other context".)
2. **"Keep SKILL.md body under 500 lines"** — and the intent is tokens, not lines: the Claude Code docs pair it with a compaction rule — **after auto-compaction each invoked skill is re-attached with only its FIRST 5,000 tokens, all re-attached skills sharing 25,000** (code.claude.com/docs/en/skills, verified 2026-09-03). Our skills run ~8.6k–12.5k tokens: **more than half of each is lost at every compaction**, which is exactly why they carry the "re-invoke after compaction" rule. A body ≤ ~5k tokens survives compaction whole.
3. **The description is the ONLY routing signal**: third person; what it does AND when to use it; concrete trigger terms; ≤ 1,024 chars (the open spec + Anthropic); in Claude Code the listing truncates description + `when_to_use` at 1,536 chars and shortens descriptions when the listing exceeds 1% of the context window (code.claude.com, verified). Vague descriptions fail; over-triggering is fixed by specificity.
4. **Progressive disclosure has a shape**: references ONE level deep, linked directly from SKILL.md (nested chains get partially read); a table of contents on any reference over 100 lines; SKILL.md is navigation + the operative procedure, never the encyclopedia. (platform best-practices, verified.)
5. **Content hygiene**: "Challenge each piece of information: Does Claude really need this explanation? Can I assume Claude knows this? Does this paragraph justify its token cost?"; no time-sensitive information (dates, versions, "current state") in the skill; one term per concept; checklists for multi-step workflows; validation loops; templates for strict output; exact scripts for fragile operations. (platform best-practices, verified.)

**Findings against §0.** (F1) Every body exceeds the compaction window by 1.7–2.5× — the top of each file (the masthead ledger) is what survives compaction, and it is the least operative part. (F2) The rule ledgers are law but not procedure: they are read once per session at best, yet paid on every trigger and every re-invoke. (F3) The FE body carries time-sensitive project state by construction (a named product candidate that has since changed twice; dated deploy facts; "HA-2026.7 verified" watch lines) — the skill's own SK-INV-01 names this as a defect. (F4) The PM body describes three operating modes of which one has been current since 2026-03; the MODULE_CONTEXT tables list 5–9 of 22 modules. (F5) Descriptions are within limits but front-load the role narrative; the trigger terms sit late, and none states when NOT to trigger (the coder/PM/frontend boundaries). (F6) No skill has evaluations; the pass discipline has been a byte census of law names, which protects content but never measures effect.

## §3 The checklist the refresh applies (ranked by expected effect per token)
1. **Body ≤ ~5k tokens (≤ ~200 lines, ≤ ~15 KB)** so a skill survives compaction whole — the single largest effect. Achieved by moving every rule LEDGER verbatim to `references/laws-ledger.md` (one level deep, with a table of contents), keeping in SKILL.md only the laws a session must hold at every beat (one line each, pointing at the ledger for the exhibit).
2. **Descriptions rewritten**: what + when + trigger nouns in the first 200 chars; the sibling-skill boundary stated ("not for … — that is nexsys-coder"); third person; ≤ 1,024 chars, no XML.
3. **Zero project state in the body** (names, dates, HEADs, endpoint partitions, deploy facts, candidate names): every such fact becomes a pointer to the spine or the file of record — the project's own pointer-not-copy law, finally applied to the skills themselves.
4. **One procedure per skill, numbered, with a copyable definition-of-done checklist** (the workflows-with-checklists pattern); the retired modes collapse to one line each with a pointer.
5. **One term per concept** across all three: the hub · the lane · the spine · the return · the WU · the gate of record.
6. **Delete what Claude already knows** (generic Java naming/error-handling prose; generic escalation platitudes) and keep only the project-specific rule.
7. **Rule census preserved by name** (the W-SKILLS discipline): every numbered arc-discipline/convention/law survives verbatim in the tree, moved not deleted; the pass ledger records the move.
8. **Evaluations are the next pass, not this one** (W-SKILLS-7): ≥3 eval prompts per skill in `evals/evals.json` (the skill-creator shape) — a trigger test (does the right skill fire on a Coder brief / an FE task / a hub boot?), a procedure test (does a fresh session run the preflight first?), a boundary test (does the coder skill refuse to write the spine?). Benchmark with-skill vs without; A/B the old vs new bodies blind.
9. **Keep the references' contents byte-unchanged in this pass** except the two additive files (the ledger, the pass-history entry): a small, auditable delta; the references' own trim is W-SKILLS-7's second half.
10. **`when_to_use`, `paths`, `context: fork`** are Claude Code–only or unverified; the account skills load through Cowork — not used.
