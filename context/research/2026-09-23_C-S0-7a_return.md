## §2 The act, and a stranger's verification
Tools: cosign v3.1.3; git 2.x; openssl 3.x (`ts` syntax NOTE); curl; jq. `M=ANCHOR-<date>.manifest.txt; B=ANCHOR-<date>.sigstore.json`.
```
cosign initialize                       # TUF root; then the two targets by hash (§4)
cosign generate-key-pair                # cosign.key / cosign.pub   [ANCHOR-ID: key]
cosign sign-blob --key cosign.key --signing-config signing_config_rekor_v2.v0.2.json --bundle $B $M
cosign verify-blob --key cosign.pub --bundle $B --use-signed-timestamps --trusted-root trusted_root.json $M
jq '.verificationMaterial.timestampVerificationData, .verificationMaterial.tlogEntries[0].inclusionProof' $B
openssl ts -query -data $M -sha256 -cert -out anchor.tsq
curl -sS -H 'Content-Type: application/timestamp-query' --data-binary @anchor.tsq http://timestamp.digicert.com -o anchor.digicert.tsr
openssl ts -verify -in anchor.digicert.tsr -queryfile anchor.tsq -CAfile DigiCertTrustedRootG4.cer -untrusted <DigiCert G4 timestamping CA .pem>
curl -sS https://log2025-1.rekor.sigstore.dev/api/v2/checkpoint -o checkpoint-at-act.txt
```
Why: cosign v3 takes log and TSA URLs from the signing config (CHANGELOG v3.0.0 #4428); a v2-capable client "MUST select Services with the highest API version… and… the newest validity start dates" (sigstore_trustroot.proto) → log2025-1. The upload response is a `TransparencyLogEntry` "which should be persisted in a bundle" (CLIENTS.md). The `jq` line is the gate: no TSA token or inclusion proof = not done. Per-upload co-signed checkpoints are planned, not shipped (CLIENTS.md: "we plan to support synchronous witnessing") — hence `checkpoint-at-act.txt`.
**Stranger, years later, offline, from the persisted folder:** (1) `sha256sum -c <repo>.sha256` at the stated commit (after the flip; 2–4 alone carry the existence claim); (2) `sha256sum` of the manifest equals the digest in `tlogEntries[0].canonicalizedBody | base64 -d`; (3) the `verify-blob` line against the persisted `trusted_root.json`: our signature; the inclusion proof against the checkpoint signed by log2025-1's Ed25519 key (README: clients "fetch both active and inactive shard public keys from the TrustedRoot"); the TSA token against a chain valid to 2035-04-06; (4) `openssl ts -verify` with DigiCert's public chain. ## §3 `ANCHOR-ID: key | keyless`
**key** — a company-held key (`cosign generate-key-pair`, or a hardware token via `--sk`). Cost: one secret; a lost key ends the series, never a past anchor. Buys: the entry carries a bare public key — "a public key is not a name" (K-13 S0) — and existence-at-T never depends on who signed.
**keyless** — a Fulcio certificate bound to an OIDC identity (email or CI path), logged permanently. Cost: an identity string published forever, touching the no-public-name fence; verification adds CA-chain and CT-key windows. Buys: no key custody.
**Rec: key.** Refutable-by: step (3) failing offline with the persisted trusted root — the ruling then reopens.
