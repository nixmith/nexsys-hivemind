## §0 The five rules (17 lines; each cites its bytes; each rule closes on its price)
- **R1.1 The version is the TYPE's, stamped by the publisher.** One `currentVersion(type)` beside the type registry; `EventDraft` stops taking a free `schemaVersion` (or a mismatch fails the append under test). Today 26 `new EventDraft(` sites in 18 files each choose it at the call site: `Z/ZclIngestionUnit.java:936` literal `1`, `S/ProductionDerivationRule.java:131` literal `2`, `A/StandardRunManager.java:119`, and `command_issued` from two private constants (`api/rest-api/…/IssueCommandEndpoint.java:89`, `A/StandardActionExecutor.java:111`); `P/EventTypeRegistry.java` and `E/EventType.java` hold no version (`git grep -i version`: 0 hits).
- **R1.2 What increments: ANY change to a type's encoded JSON** — a key added, removed, renamed or retyped, or a value's meaning changed — bumps that type by one, and the same commit ships the `v(n)→v(n+1)` upcaster and the new golden fixture. Additive changes included: D01 §3.10 rule 2 (`D01:359`) already says so, and J3 T-B broke it — `skipped_unavailable`, the eighth component (`E/AutomationCompletedEvent.java:69`), is written at v1 (`A/StandardRunManager.java:119`, `:715`, `:784–785`), its old-row default chosen by Jackson's zero-fill (`P/PersistenceObjectMapper.java:102–111` enables neither `FAIL_ON_MISSING_CREATOR_PROPERTIES` nor `FAIL_ON_NULL_FOR_PRIMITIVES`). A change the old JSON alone cannot express stays a new type (`D01:360`) or a DEFINED degrade (AMD-52's gate, `P/EventPayloadCodec.java:166–181`).
- **R1.3 Where the upcaster lives: read-side, in the codec, between the registry lookup and the typed read** (`P/EventPayloadCodec.java:164` → `:184`): `PayloadUpcaster { String eventType(); int fromVersion(); JsonNode upcast(JsonNode) }`, pure, chained to the current version, lazy (`D01:361–363`), keyed `(event_type, schema_version)`, wired by the composition root (no ServiceLoader — AMD-47's posture, `core/device-model/…/AttributeValueUpcaster.java:14–15`); chain completeness is a unit test (§3 T-G3), never a boot check. AMD-47's value upcaster stays the later, inner stage (before derivation, AMD-47-INV-02, `…/AttributeValueUpcaster.java:30–33`).
- **R1.4 An unknown version degrades; it never fails the boot.** `schema_version > current` (a rollback reading a newer build's rows) is read by the current class — INV-ES-07's forward-compat (`P/PersistenceObjectMapper.java:42–45`, `:108`), sound only because R1.2 sends every non-additive change to a new type — and becomes a `DegradedEvent` on any failure; `< 1`, a chain gap or a throwing upcaster → `DegradedEvent` (`P/EventPayloadCodec.java:148–151`, `:187–195`). A core projection handed a `DegradedEvent` of a type it consumes skips it, counts it, marks that subject DEGRADED and goes on (`D01:861`); this narrows `D01:367`'s projection-wide "enters degraded state" to the subject and replaces the "halts" of `E/DegradedEvent.java:13–18`.
- **R1 price:** one coder unit (est. ≈ 1 day): the codec seam, the version map, `automation_completed` v2 with an idempotent `v1→v2` (absent `skipped_unavailable` → 0) that reads BOTH v1 shapes already on disk; one `JsonNode` parse per old-version row read, nothing per current row; the corpus (§3) is test-only.
- **R2.1 The retention predicate — a row is deleted iff** (a) its type is not in NEVER (R2.2); (b) it is past its window (R2.3), where a row whose `correlation_id` group holds any member outside {`state_reported`, `state_changed`} belongs to a CHAIN that ages as one — deleted whole, only when every member is past its own window — while a row of a state-only group ages alone; (c) `global_position <` F, F = min(every durable subscriber checkpoint, the newest `state_baseline`'s position) — never what a subscriber has not consumed (D01 §6.4, `D01:813–821`).
- **R2.2 NEVER deleted:** the registry's four types (`L/RegistryProjectionSubscriber.java:62–66`; `device_registered` and `entity_registered` are published NORMAL, `Z/ZigbeeAdoptionSlice.java:387/391`, `:446/450`, so 90-day priority retention — or D01's emergency step 5, `D01:839` — empties the registry at the next boot's four-type rebuild); `command_issued` and its terminal (`command_result`, `state_confirmed`, `command_confirmation_timed_out`: `E/EventTypes.java:56`, `:62`, `:79`, `:65`); the newest `state_baseline`.
- **R2.3 Windows, by TYPE, never by priority:** chain members 90 d (the explanation horizon) — today the terminal `command_confirmation_timed_out` is DIAGNOSTIC (`A/StandardPendingCommandLedger.java:899–900`) beside a NORMAL `command_issued` (`api/rest-api/…/IssueCommandEndpoint.java:216`), and so are `automation_run_skipped` / `_cancelled` (`A/StandardRunManager.java:725–726`, `:734–735`), so 7/90/365 strips them from their chains on day 7 and a timed-out command would then read as still DISPATCHED (inference from `A/StandardExplanationService.java:90–92`); `state_changed` 90 d (a "why didn't it fire" answer reads UNCHAINED state history); `state_reported` 7 d — the 64 % — which only a type rule can shed, because it is written NORMAL (`Z/ZclIngestionUnit.java:934–939`); CRITICAL 365 d; any other type keeps its priority's window (`P/RetentionPolicy.java:46–47`).
- **R2.4 Mechanics:** a nightly sweep (today nothing deletes but `truncateForTesting`, `P/SqliteEventStore.java:1145–1149`; `P/MaintenanceService.java:52` has no implementation) first appends `state_baseline` — the state view at its position, one row per consent category, encrypted as its sources are (INV-PD-07) — so a rebuild stays exact after deletion; the baselines are also the position calendar: a window is cut at the newest baseline whose trusted time is ≥ W old, never on raw `ingest_time` (R4). Then it deletes in 1,000-row chunks (`P/RetentionPolicy.java:16–19`, AMD-40) through `idx_events_type` / `idx_events_correlation` (`MIG/V001__initial_event_store_schema.sql:58–59`); freed pages are reused by later inserts, so `incremental_vacuum` (`P/DatabaseExecutor.java:402`) runs only to shrink a file.
- **R2 price (§1):** steady state 2.06 GB at the rig's posture (17.5 GB/yr unbounded), 0.86 GB at 12 metering streams × 60 s, 0.44 GB × 600 s; NEVER's commands ≈ 110 MB/yr at 200 commands/day × 3 rows; one coder unit (sweep + predicate + `state_baseline` and its fold in the state projection), est. ≈ 2 days; each deleted row costs about one insert's writes.
- **R3.1 The snapshot rule:** every projection whose boot work would otherwise grow with the store checkpoints at H with its state durable in the SAME transaction (AMD-45 §2.1, `S/StateProjection.java:796–800`; `view_checkpoints` lives in the events DB, `MIG/V001__initial_event_store_schema.sql:76`, so a power cut rolls log and checkpoint back together) and boots by reading (checkpoint, tail] only.
- **R3.2 What invalidates a snapshot:** the checkpoint records a reader fingerprint — the projection version plus `type → currentVersion` for the types its derivation reads (D01 §3.10, `D01:371`); a mismatch or a missing checkpoint rebuilds — from the newest `state_baseline` once a sweep has run, from 0 before. Today only the projection version is compared (`S/StateProjection.java:725–726`, then clear and cursor 0 at `:742–743`); the per-type versions `D01:371` asks for are recorded nowhere, so a payload bump today leaves a stale snapshot standing.
- **R3.3 Gates are progress-based, never fixed:** the state projection's ~30-s cap (`HSC:1555–1570`, `maxPolls = 1_500` at `:1556`) takes RegistryGate's stall rule (`HSC:1592–1600`), because a rebuild is O(retained): 44.7 s warm at the rig's R2 steady state of 4.11 M rows (92 k ev/s, the b2 audit §2.3) — past 30 s even WITH R2.
- **R3 price and instrument:** per projection one coupled blob (∝ entities; warned at `S/StateProjection.java:791`) per checkpoint cadence; a version bump costs one O(retained) replay at the next boot. Instrument: one line per projection per boot, `rows head checkpoint ms` (the shape of `HSC:643–644`); R3 holds iff ms is flat in head and linear in (head − checkpoint) across BC10's cold start and Sunday's rehearsal (the hub's rows).
- **R4.1 The clock — a separate SYSTEM event, not a column and not a payload field:** `clock_status { synchronized, wall_minus_head_ms, step_ms? }`, published once at boot before the first device event (synchronized ⇔ `/run/systemd/timesync/synchronized` exists; wall clock vs the head row's `ingest_time`) and once more at the first sync after an unsynchronized boot, with `step_ms` = Δwall − Δ`System.nanoTime()` since the boot mark. Nothing reads clock state today (`git grep` NTPSynchronized|timesync|timedatectl|adjtimex in `*/src/main/*`: 0 hits; the unit waits only for `network-online.target`, `distribution/systemd/homesynapse.service:17–18`).
- **R4.2 Readers:** order by `global_position` (one writer + AUTOINCREMENT, `HSC:630–631`); rows between an unsynchronized mark and the next synchronized one are "time approximate" — shown flagged, kept out of time-window lookups (K2 falls back to its type scan, `A/StandardExplanationService.java:103–108`), aged by R2 from the closing mark; an `event_id`'s ULID time is identity, never order. **Price:** one type and one fixture, one file check at boot, a 30-s tick until synced; ≈ 2 rows per outage, 0 B per row.
- **R5 (R8) Reserve, don't build:** `logical_time` and `node_id` stay written 0 (`P/SqliteEventStore.java:179`, `:527–528`) until a second hub exists; then `logical_time` = an HLC (48-bit ms high-water ‖ 16-bit counter in the 64-bit INTEGER), `node_id` = the hub's enrolled id (never reused; `setInt`'s 32 bits suffice), merge order `(logical_time, node_id, global_position)`. R1–R4 must not write either column, key anything cross-hub on `global_position`, or make an upcaster impure (§5). **Price now:** ≈ 2 B/row (two zero-valued columns' record-header bytes; 0.40 % of 501 B).

Until that number exists, `KIT-STORAGE: a` (the SSD at kit) stands; an SD card stays acceptable on the bench and for a pilot home at the 600-s posture with R2.

## §3 The golden-bytes test design (test-only, `core/persistence/src/test`)
**Layout.** `src/test/resources/golden/<event_type>/v<N>.json` — the payload bytes exactly as the build that introduced version N encoded them (compact UTF-8, `SNAKE_CASE`, `NON_NULL`: `P/PersistenceObjectMapper.java:106–110`). `golden/MANIFEST.sha256` lists every fixture. `GoldenInstances.java` holds one canonical instance per type at its current version and, per old version, the instance its upcast must equal. A type with two shapes under one version gets two fixtures: `automation_completed/v1.json` and `v1-tb.json` (before and after J3 T-B, both v1 on disk). Encrypted scopes pin the plaintext; one more fixture pins the at-rest framing (`ENVELOPE_VERSION_V1`, `P/SqliteEventStore.java:150`, `:473–476`, `:1046`) under a fixed test key and IV.

**`PayloadGoldenBytesTest` — one parameterized case per `(type, version)`:**
- **T-G1 `decodesEveryPastShape`** — `decode(type, N, bytes)` is not a `DegradedEvent` and equals `GoldenInstances.expected(type, N)`, field by field, defaults included.
- **T-G2 `currentShapeIsPinned`** — `encode(GoldenInstances.current(type))` is byte-equal to `v<current>.json`. **This is the test that would have caught J3 T-B:** the eighth component adds `"skipped_unavailable":0` to the encoded bytes → red at v1 → the author bumps to v2, adds `v2.json`, writes the `v1→v2` upcaster, and the old-row default becomes a reviewed line instead of Jackson's zero-fill. It also turns red, for every type at once, on a mapper change (naming, inclusion, date format).
- **T-G3 `everyTypeEveryVersion`** — every class `AllEventClasses` enumerates has a fixture for each version 1..current and an upcaster chain with no gap and no duplicate; a fixture for an unregistered type fails.
- **T-G4 `goldenIsImmutable`** — each fixture's SHA-256 equals its manifest line; adding a fixture appends a line, editing one fails.
- **T-G5 `unknownVersionNeverThrows`** — version current+1 carrying an extra key reads (INV-ES-07); versions 0 and −1, a chain gap and a throwing upcaster each yield a `DegradedEvent` holding the raw bytes; nothing throws.
- **T-G6 `fingerprintMovesWithVersion`** — bumping a type the state projection's derivation reads changes its R3.2 fingerprint; bumping a type it does not read leaves the fingerprint alone.

**What fails on a silent shape change:** a component added, removed, renamed or retyped (T-G2 at encode; T-G1 when the old fixtures decode); a version bumped without its fixture or upcaster (T-G3); a fixture rewritten to make a test pass (T-G4). **Price:** one fixture per `(type, version)` — about one per registered type today (the count was not read; `AllEventClasses.java` enumerates them) — generated once from today's encoder and reviewed by hand, then one per future version. Freeze-safe as a test-only change if the hub allows it; otherwise it lands with R1's unit.

## §4 The clock after a power cut — the rule and its cost
**Today.** `ingestTime` is the system clock at append and `eventTime` is the source's (`E/EventEnvelope.java:42–51`); nothing in `*/src/main/*` reads the clock's sync state (0 hits), and the unit waits only for `network-online.target` (`homesynapse.service:17–18`). On a board without a battery-backed RTC, systemd-timesyncd advances the clock at start to the mtime of `/var/lib/systemd/timesync/clock`, which it updates on every successful sync and, since systemd 250, every `SaveIntervalSec=` (default 60 s); `/run/systemd/timesync/synchronized` is touched on each successful sync (systemd-timesyncd.service(8), timesyncd.conf(5), read 2026-10-13). So, on systemd ≥ 250 (the rig's version was not read), after a cut of length D that also takes the router, the hub boots about D (+ ≤ 60 s) behind, appends rows on that clock until NTP returns, then steps forward by about D; a few rows can sit up to a minute before the head's time. (The rig was synced at the dry-run: `timedatectl yes`, b2 audit §1.)

**What `global_position` already gives:** the total order of appends on one hub, gap-free as the reader sees it (one writer and AUTOINCREMENT, `HSC:630–631`). **What it does not:** with `synchronous = NORMAL` in WAL (`P/DatabaseExecutor.java:446–447`), "a transaction committed in WAL mode with synchronous=NORMAL might roll back following a power loss or system crash" (SQLite, PRAGMA synchronous). The log and `view_checkpoints` roll back together (one file), but a position handed OUTSIDE the hub before the cut — an export, a dashboard cursor — can name a different row afterwards; outside consumers re-key on `event_id` across a `clock_status` boot mark.

**Options, priced.** (a) A column: a schema migration and ≈ 1–2 B on every row for what is a property of an interval, which every reader must then learn. (b) A payload field: a version bump of every type under R1.2 — out of proportion. (c) **A `clock_status` event — chosen:** ≈ 2 rows per outage, 0 B per row, no migration, readable by any consumer through the type index; it also gives R2 its trusted-time calendar and a future HLC (R5) its physical-clock quality. Not chosen: `After=time-sync.target` in the unit — it would hold the hub down until the router returns, and the hub must run offline.

**The rule (R4).** At boot, before the first device event, publish `clock_status{synchronized, wall_minus_head_ms}`. If unsynchronized, a 30-s scheduler tick checks the sync file and, at the first sync, publishes `clock_status{synchronized: true, step_ms}`. Readers order by position, flag times inside [unsynced mark, synced mark), and subtract the step from any duration measured across it; K2 falls back to its type scan for a run inside the interval (`A/StandardExplanationService.java:103–108`), as it already does on any miss. The R2 sweep skips a night on which the clock is unsynchronized, so no `state_baseline` ever carries an untrusted time.

## §5 What R1–R4 must not foreclose (R8, and R5's tamper evidence)
- **An HLC needs 64 bits and a node id, and both are reserved:** `logical_time` INTEGER and `node_id` are bound 0 (`P/SqliteEventStore.java:527–528`); Kulkarni et al.'s HLC packs a 48-bit physical high-water mark and a 16-bit counter into those 64 bits. Merge order `(logical_time, node_id, global_position)`; inside one hub, `global_position` stays the order.
- **Already enough:** `event_id`, `correlation_id` and `causation_id` are ULIDs (80 random bits), so chains from two hubs merge without collision, and R2's chain test keys on `correlation_id`, so it works unchanged on a merged log.
